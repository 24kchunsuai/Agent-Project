# drone-agent001 运维手册（数据备份与恢复）

> 版本：v1.0 ｜ 日期：2026-09-24 ｜ 对应规约：`docs/specs/企业级落地规约.md` **E-7**（判据 **C4 可恢复**），并衔接 E-3（可观测）

## §1 管哪些数据

系统有**四个 SQLite 库**，它们各自承载不可再生的状态：

| 逻辑名 | 库文件（相对 `agt_python/data/`） | 装什么 | 丢了会怎样 |
|---|---|---|---|
| `governance` | `governance/governance.db` | 文档治理元数据、版本链、巡检工单、治理审计流水 | **不知道有哪些文档、版本链断、审计断** |
| `observability` | `metrics/observability.db` | 四类事件表（会话/工具/委派/故障）+ 日指标 + 反馈 + **前端报错 `client_error`**（E-12） | 看板与知识缺口分析全部归零（历史不可补）；前端「前端错误」看板随之清空 |
| `session_memory` | `memory/session_memory.db` | 会话消息（M-1 持久化） | 重启后用户发现"它不认识我了" |
| `user_profile` | `memory/user_profile.db` | 用户偏好 KV（M-5） | 个性化注入失效 |

> **向量库（Milvus）不在本手册范围**：它可由 `data/kb/**` 的源文件重新灌库
> （`scripts/` 的语料回填流程），属于"可重建数据"，风险等级低于上面四库。

## §2 备份在哪

```
agt_python/data/backups/
├── 2026-09-24/                  ← 一天一份（目录名即备份日期）
│   ├── manifest.json            ← 备份清单（下面 §2.2 逐字段解释）
│   ├── drill-report.json        ← 恢复演练报告（跑过演练才有）
│   ├── governance.db
│   ├── observability.db
│   ├── session_memory.db
│   └── user_profile.db
└── .staging/                    ← 写入中的暂存区（正常时不存在）
```

- 位置**刻意放在 `DATA_ROOT` 之内**：备份跟数据一起被搬走，不会出现
  "迁了数据目录、备份还留在旧盘"的错配。可用 `backup_dir` 配置项外迁。
- 备份根目录随数据目录走：`DATA_ROOT=<x>` 时备份落在 `<x>/backups/`。
  临时换目录做演练：`python scripts/backup_dbs.py --data-root D:/tmp/dd`。

### 2.1 一个库的备份文件是**自洽**的

备份出的是**单文件一致快照**，恢复时**不需要**携带 `-wal` / `-shm`。
（规约原文写的是"连同 `-wal`/`-shm` 一起复制"，实现改为 SQLite 在线备份 API，
理由与证据见 §7「有意偏离」。）

### 2.2 `manifest.json` 字段

| 字段 | 含义 | 出问题时看它 |
|---|---|---|
| `generatedAt` | 备份生成时间（本地） | 判断备份新鲜度 |
| `dataDir` | 备份时的数据目录 | 确认备的是不是那一套数据 |
| `keep` | 本轮生效的保留份数 | 与预期不符 → 检查 `backup_keep_days` |
| `databases[].name` | 逻辑名（§1 那张表的键） | — |
| `databases[].sourceBytes` / `sourceMtime` | **源库**大小与最后修改时间 | 源库是不是很久没写过了 |
| `databases[].sourceWalBytes` / `sourceWalBytes` | 源库 `-wal`/`-shm` 现状 | 判断备份时刻源库是否处于写入中 |
| `databases[].journalMode` | 源库 journal 模式（`wal`/`delete`） | 解释"为什么有的库有 `.db-wal`、有的没有" |
| `databases[].integrity` | **备份副本**的 `PRAGMA integrity_check` | 必须是 `ok` |
| `databases[].tables` | **每张表的行数** | 恢复演练的行数比对基准 |
| `databases[].sha256` | 备份文件摘要 | 校验备份文件本身有没有被改动/损坏 |
| `databases[].rowCount` | 行数合计 | 一眼看趋势（今天比昨天少很多就要问为什么） |
| `databases[].skipped` | 该库被跳过的原因 | 源库不存在时**不创建**，如实记录 |

## §3 备份怎么跑

### 3.1 自动（默认开）

备份挂在**既有的常驻任务表**上（与对账/巡检/TTL 同一机制），因此它天然具备
"开关 / 手动触发 / 状态上报"三件事：

| 项 | 默认值 | 配置项 |
|---|---|---|
| 总开关 | 开 | `backup_enabled` |
| 周期 | **86400 秒（每天一轮）** | `backup_interval_sec` |
| 启动后首次延迟 | 300 秒（避开冷启动与首轮对账） | `backup_initial_delay_sec` |
| 保留份数 | **14 份** | `backup_keep_days` |

> **每日幂等（重要）**：当天已有且校验通过的备份**不会被再写一遍**——
> 默认触发只会回一句"今日已有备份（…），未重复备份"。
> 这条规则是为 §4.1 那句"演练过的备份"服务的：服务**每次重启**都会让启动延迟
> 再走一遍，若不幂等，则每次重启都换掉当天备份、顺手冲掉 `drill-report.json`，
> 于是"演练过"永远立不住（2026-09-24 实测踩到）。要强制重备见 §3.2。

看它跑没跑（需 8000 在运行）：

```bash
curl -s --noproxy '*' http://127.0.0.1:8000/v1/kb/governance/tasks \
  -H "X-Agent-Key: $(cat deploy/secrets/agent.key)"
```

输出里找 `"name":"db_backup"`：`runs` 是已执行轮数，`enabled` 是开关现状，
`lastError` 非空就是上一轮失败了（原因在里面）。

### 3.2 手动触发（三种，按场景选）

```bash
# ① 服务在跑、想立刻补一份（走后端接口，写进同一天的目录）
curl -s --noproxy '*' -X POST \
  "http://127.0.0.1:8000/v1/ops/backup/run?operator=你的名字" \
  -H "X-Agent-Key: $(cat deploy/secrets/agent.key)"

# ①b 强制重备当天（覆盖已有快照；会让当天的 drill-report.json 失效 → 记得重跑演练）
curl -s --noproxy '*' -X POST \
  "http://127.0.0.1:8000/v1/ops/backup/run?operator=你的名字&force=true" \
  -H "X-Agent-Key: $(cat deploy/secrets/agent.key)"

# ② 服务没起 / 上线上副本前 / 迁移前（脚本不依赖服务）
python scripts/backup_dbs.py
python scripts/backup_dbs.py --force     # 强制重备当天

# ③ 只看现在有哪些备份，不写盘
python scripts/backup_dbs.py --list
```

> **没有 `force` 时是每日幂等**（理由见 §3.1）。**什么时候该 force**：刚发生了重要数据变更、
> 想立刻把"变更后"的状态备下来。代价是当天那份已演练的备份被替换 → **必须重跑一次演练**。

> **两条铁律**：备份**只读源库**（连接以 `PRAGMA query_only=ON` 打开，不 checkpoint、
   不建库、不改一行）；**失败的备份不许覆盖成功的备份**（先写 `.staging`，
> 全部校验通过后才换名到日期目录）。

### 3.3 保留策略与滚动清理

- 保留最近 **14 份**（按目录名倒序），更老的自动删除。
- 清理的**三条护栏**（`backup_service._prune`）：
  1. 只删备份根目录的**直接子目录**，且名字必须形如 `YYYY-MM-DD`；
  2. 目录内**必须有 `manifest.json`**（这是"我们建的"凭证）——手工放进去的备份不会被删；
  3. 只删该目录自身，不做通配、不越出备份根目录。
- **`.staging` 永远不在清理范围**；且备份失败时会主动删掉，不残留（见 §8.3）。

### 3.4 实测数字（本机，2026-09-24，四库共 1872 KiB / 5822 行）

| 操作 | 耗时 |
|---|---|
| 完整备份一轮（4/4 库 + 校验） | **57 ~ 125 ms** |
| 其中单库 `integrity_check` | 毫秒级（库是 MB 级；GB 级会明显变长，见 §5） |

## §4 恢复

「恢复」在本项目里是一件**必须先演练**的事。所以这一节先讲演练，再讲真出事怎么用。

### 4.1 恢复演练（规约要求的那个"演练过的"）

```bash
# 演练最新一份备份（默认：恢复到临时目录 → 校验 → 逐表行数比对 → 应用读一遍 → 出报告）
python scripts/restore_drill.py

# 指定某一天 / 指定备份根目录（例如从 U 盘/U 盘上的备份验）
python scripts/restore_drill.py --date 2026-09-24
python scripts/restore_drill.py --backup-root D:/usb/backups

# 排查用：保留临时目录；或输出 JSON 供流水线消费
python scripts/restore_drill.py --keep
python scripts/restore_drill.py --json
```

演练做四件事，**每一步都是断言**：

| 步骤 | 断言 | 不过意味着 |
|---|---|---|
| ① 恢复 | 快照按原目录结构放回**临时目录** | 布局/权限问题 |
| ② 完整性 | 每库 `integrity_check=ok`，且恢复出的 sha256 **与清单一致** | 文件在复制中坏了 |
| ③ 行数比对 | 恢复后**逐表**行数 == 清单里的行数 | **数据丢了**（最要命的失败，通常 PIT） |
| ④ 应用读取 | 用应用自己的 store（治理/埋点/记忆/画像）各做一次真实读取 | schema 不兼容，或库根本打不开 |

> 顺序有讲究：**行数比对必须在应用读取之前**。应用打开库时会跑
> `CREATE TABLE IF NOT EXISTS` 与幂等迁移，先读会被这些动作掩盖掉真实差异。

**实测输出（2026-09-24，本机）**：

```
演练结果：✓ 通过（这份备份可以恢复）
  恢复耗时   : 41 ms
  库                完整性      sha256   行数比对       行数
  governance       ok       一致       逐表一致       2598
  observability    ok       一致       逐表一致       3113
  session_memory   ok       一致       逐表一致       111
  user_profile     ok       一致       逐表一致       0
  应用读取：governance ✓ / observability ✓ / session_memory ✓ / user_profile ✓
```

报告落 `data/backups/<日期>/drill-report.json`，含"备份时间 / 恢复耗时 / 逐表行数比对结果"。

> ⚠️ **什么时候演练报告会失效**：当日备份被**整份替换**时，旧的 `drill-report.json`
> 随旧快照一起消失。两种触发方式：① 显式 `force`（见 §3.2）；② 同一天第二次**非幂等**的写入。
> 这是**有意为之**——旧报告对应旧快照，留着它会让人误以为"当前这份已被演练过"。
> **反向的好消息**：定时备份是每日幂等的，所以**服务重启不会冲掉演练报告**
> （这条是被实测逼出来的，见 §3.1 的说明）。重备之后要**重跑一次演练**才算数。

### 4.2 真出事时怎么恢复（按场景）

> 下面每条都**先停服务再动库**：SQLite 被进程占着时替换文件，轻则读不到新数据，
> 重则下次写入把覆盖的文件又改回旧状态。
> 停服务：`powershell -File deploy/scripts/stop-all.ps1`；恢复后 `start-all.ps1`。

**场景 A：单个库被误删/损坏（最常见）**

```bash
# 1) 停 8000（其它服务可不停；若确认没人用，整体停更省心）
powershell -File deploy/scripts/stop-all.ps1

# 2) 把坏掉的库改名留证据（不要直接删——先留着给事后分析）
cd agt_python/data/governance
mv governance.db governance.db.broken-20260924

# 3) 从备份恢复（恢复的是**备份里的单文件**，不需要 -wal/-shm）
cp ../../backups/2026-09-24/governance.db ./governance.db

# 4) 起服务并验证
cd ../../../ && powershell -File deploy/scripts/start-all.ps1
python scripts/restore_drill.py     # 演练会给出一份"当前备份可恢复"的结论
```

**场景 B：整个 `data/` 目录丢了**

```bash
# 1) 确认备份还在（备份与数据同一棵树时，这条路依赖"备份被单独拷走过"——
#    所以生产上建议定期把 data/backups/ 同步到另一块盘/另一台机）
ls /path/to/copy-of-backups/2026-09-24/

# 2) 重建目录并按 §2 的布局放回四个库
mkdir -p agt_python/data/{governance,metrics,memory}
cp .../governance.db    agt_python/data/governance/governance.db
cp .../observability.db agt_python/data/metrics/observability.db
cp .../session_memory.db .../user_profile.db agt_python/data/memory/

# 3) 起服务；语料源文件若也丢了，按语料回填流程重灌 Milvus（向量可由源文件重建）
```

**场景 C：换机器 / 从别处的备份恢复**

```bash
python scripts/restore_drill.py --backup-root D:/usb/backups          # 先验，再上
python scripts/restore_drill.py --backup-root D:/usb/backups --serve  # 连服务一起冒烟
```

`--serve` 会起一个隔离实例去读恢复库并打 `/v1/health`（需 Milvus 在线），
这是"整条应用能在这份数据上启动"的端到端证据。

### 4.3 恢复耗时怎么估

实测（1872 KiB / 5822 行）：**恢复 + 校验 + 应用读取 ≈ 40 ms**。经验规律：

- 备份与恢复耗时基本与**库体量**成正比（`integrity_check` 要读全库页）；
- 到 GB 级时按"每 GB 十秒级"预留窗口；
- 演练报告里 `restoreMs` 就是可引用的实测值——**别口头估**，
  拿最近一次演练的数字说话。

## §5 演练频率

| 项 | 建议 | 说明 |
|---|---|---|
| **恢复演练** | **每月一次**（规约 E-7 建议） | 演练要花的是注意力，不是时间——实测 40 ms，难的是"想起来做" |
| 备份 | 每天自动 | 已在任务表里，见 §3.1 |
| 演练触发时机 | ① 每月固定一次；② **改过数据层/迁移/schema 之后立刻一次**；③ 发布前一次 | ②最重要：迁移是唯一能"把可恢复变成不可恢复"的改动 |
| 演练通过判据 | 脚本退出码 `0`，报告 `"ok": true` | 非 0 就必须当故障处理，不许"先放着" |

**把它挂进发布流程**（可选但推荐）：`scripts/release.sh` 发布前跑
`python scripts/restore_drill.py || exit 1`——一份不能恢复的备份等于没有备份。

## §6 排障

| 症状 | 大概原因 | 怎么办 |
|---|---|---|
| 触发备份返回"今日已有备份（…），未重复备份" | **每日幂等**在生效（正常） | 想覆盖就加 `force=true` / `--force`（并记得重跑演练） |
| `--list` 说"还没有任何备份" | 从未跑过，或 `DATA_ROOT` 指到了别处 | 跑 `python scripts/backup_dbs.py`；确认 `--data-root` |
| 备份报告里某库 `skipped: 源库不存在（不创建）` | 该功能从未落盘过（如画像库 0 行时从未写入） | **属正常**。要它出现就得先有真实使用数据 |
| `integrity` 不是 `ok` | 源库本身页损坏 | 先跑 `PRAGMA integrity_check` 定位；从更早的备份恢复 |
| 备份目录里出现 `.staging` | 上一次备份被**强杀**（任务被 kill / 断电） | 下次备份会先清掉它；也可手工删（只删这一个目录） |
| 演练报"行数比对不一致" | 快照不一致（PIT）或备份时源库正被大事务占住 | 立刻查 `backup_busy_timeout_ms`；这份备份**不要当数**，用更早的一份 |
| 演练报"应用读取失败" | schema 与当前代码不兼容（降级版本去读新库更常见） | 用与备份**同版本**的代码恢复；或先升级 schema |
| 同一天备份两次后演练报告不见了 | `force` 重备会把当日目录整份替换（§4.1） | **正常**，重跑演练即可 |
| 备份任务 `lastError` 非空 | 见任务状态里的具体原因 | 常见是磁盘满 / 权限 |

**日志类排障不在本手册**：
- 「服务起不起来 / 报了什么错」→ `docs/部署手册.md` **§7 故障对照表** 与 **§7.7 日志怎么看**；
- 「日志字段是什么、怎么按 `traceId` 串起一次请求、日志为什么不会无限增长」→ **`docs/日志规范.md`**（E-6）。
- 记一句最常用的：`grep -h "<traceId>" deploy/logs/8080-agt_backend.jsonl deploy/logs/8000-agt_python.jsonl`
  —— 一次命令串起 Java 与 Python 两侧的同一请求（`traceId` 由 Java 生成，响应头 `X-Trace-Id` 可取）。

## §7 有意偏离（相对规约原文）

| 规约原文 | 实际实现 | 为什么 |
|---|---|---|
| "连同 `-wal`/`-shm` 一起复制" | **SQLite 在线备份 API**（`Connection.backup`）产出单文件快照，不携带 `-wal`/`-shm`；源库 `-wal`/`-shm` 现状仍记入 manifest 供排查 | ① 裸拷在"服务正在写"时可能读到**不同时刻**的 `db` 与 `wal`，得到"页结构完整（`integrity_check` 过）但丢数据"的备份——最危险的失败模式：校验全绿、恢复时才发现少一天；② 在线备份走 SQLite 自己的页级读锁，产出天然自洽；③ 不携带 `-wal` 让恢复少一类"忘了带 wal"的坑。<br>证据（单测）：`tests/test_backup.py` T1/T2——T1 证明"只在 `-wal` 里的数据能被备走"，T2 是反面证明"只拷主库文件连表都读不到"。验红时把实现换回 `shutil.copy2`，T1 立刻红而其余 14 项仍绿。 |

> 本偏离**不改变验收标准**：`integrity_check` 全 ok、可恢复、演练通过，四条验收全部照做。

### 8.2 相关代码与配置

| 位置 | 作用 |

| `agt_python/app/services/backup_service.py` | 备份核心（四库发现 / 快照 / 校验 / 清单 / 滚动清理） |
| `agt_python/app/services/scheduler.py` | 任务表（`db_backup` 条目） |
| `agt_python/app/api/v1/endpoints/ops.py` | `POST /v1/ops/backup/run`、`GET /v1/ops/backup/status` |

| `agt_python/tests/test_backup.py` | 18 项单测（WAL 一致性正反两证 / 每日幂等 / `force` 语义 / 滚动清理护栏 / 路径防漂移） |
| 配置项 | `backup_enabled` / `backup_interval_sec` / `backup_initial_delay_sec` / `backup_keep_days` / `backup_dir` / `backup_busy_timeout_ms` |

### 8.3 三条不变量（改代码时别破坏）

1. **备份不改源库**：源连接必须 `query_only=ON`，且不许在建库逻辑里"顺手创建"。
2. **失败不覆盖成功**：先写 `.staging`，全部校验通过才换名；失败路径必须清掉 `.staging`。
3. **每日幂等优先于"再备一份"**：默认路径不许重写当天已有的好备份——
   它保护的是"演练过的备份"这个状态本身（§3.1）。
