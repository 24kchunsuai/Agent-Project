# 依赖与漏洞处置流程（E-11）

> 版本：v1.0 ｜ 日期：2026-09-24 ｜ 对应规约：`docs/specs/企业级落地规约.md` E-11（判据 C1 可交付）
>
> 依赖清单与许可证见 **`docs/依赖清单.md`**。
> 本文件回答的是"**扫出来之后怎么办**"——定级、处置、豁免、复扫、关闭。

---

## 1. 阈值与判定（用户 2026-09-24 决策）

| 级别 | 处置 | 说明 |
|---|---|---|
| **Critical** | **阻断** | 未处置则 CI 判红、发布被拒 |
| **High** | **告警** | 进报告，不阻断 |
| **MEDIUM / LOW** | 记录 | 进报告，不阻断 |
| **UNKNOWN** | 记录 | **不阻断，但显式标出**（见 §7 第 3 条） |

扫描器的退出码（`scripts/scan_deps.py`）：

| 退出码 | 含义 |
|---|---|
| `0` | 通过（可带 High/Medium 告警；或 Critical 已被**有效豁免**覆盖） |
| `1` | **阻断**：存在未豁免的 Critical，**或豁免台账自身违规** |
| `2` | **快照/覆盖问题**：闭包与快照不一致、某端一个依赖都没采到 → 需先 `--refresh` |

阻断点落在**两处**（这是有意设计的）：

1. **本地 CI**：`bash scripts/ci.sh deps`（改代码/改依赖时立刻拦住）；
2. **发布前**：`scripts/release.sh` 的 3.5 步（拦住出厂）。

> 为什么不落"阻断合并"？按约定本仓库尚未 push，远端门禁不生效。
> 与其把阻断点写在一个不会执行的地方，不如落在**真正会跑的两处**。

## 2. 发现 → 处置五步

1. **扫描**：`bash scripts/ci.sh deps`（离线、秒级）或 `python scripts/scan_deps.py --refresh`（联网刷新后再扫）。
2. **定级**：由扫描器按**四档回退链**给出（人不必也不该手判）：
   `database_specific.severity`（GHSA 自带）→ 顺 `aliases` 找 GHSA →
   用 CVSS v3.1 向量自算基础分 → 仍拿不到则标 `UNKNOWN`。
3. **处置决策**：**升级 > 覆盖 > 豁免**（优先级顺序，理由见 §3、§4）。
4. **豁免（如确需）**：写进 `security/deps-allowlist.json`，必须五项俱全（见 §5）。
5. **复扫与关闭**：处置后 `--refresh` 重扫；漏洞消失后**删掉那条豁免**
   （残留的豁免会被报成"悬空豁免"，提示清理）。

---

## 3. 处置优先级：先升级，再考虑豁免

| 方案 | 何时用 | 代价 |
|---|---|---|
| **升级依赖** | 默认首选。有修复版本就直接升 | 需回归测试；可能要重建产物 |
| **显式覆盖版本** | 上游 BOM 托管了一个仍带高危的版本时（本项目就遇到了） | 需自行确认同线兼容性 |
| **豁免 + 到期日** | 无修复版本、或该特性在本系统**确实不可达** | 需论证"不可达"并设定复评期限，是**负债**不是解决方案 |

## 4. 实测案例：tomcat 10.1.28 → 10.1.60（本项目第一次真实处置）

**发现**：E-11 扫描器落地后首次全量扫描，Java 侧出现 **7 条 Critical**，
全部集中在 `org.apache.tomcat.embed:tomcat-embed-core@10.1.28`（DIGEST/FORM 认证绕过、
HTTP/2 头未校验、SecurityConstraints 未生效等）。这个风险此前**完全不可见**。

**第一个反直觉结论**：**"顺手升 Spring Boot 小版本"修不掉**。
实测各版本的漏洞分布（数据源 OSV，2026-09-24）：

| `tomcat-embed-core` | CRITICAL | HIGH | 备注 |
|---|---|---|---|
| 10.1.28 | **7** | 14 | 当前（Spring Boot 3.3.3 托管） |
| 10.1.42 | **6** | 11 | Spring Boot **3.3.13（该线最新）** 托管的版本 |
| 10.1.54 | **6** | 3 | |
| 10.1.57 | 3 | 0 | |
| **10.1.60** | **0** | **0** | 选它 |
| 11.0.26 | 0 | 0 | 跨大线，未选 |

**处置**：`agt_backend/pom.xml` 加一行显式覆盖
`<tomcat.version>10.1.60</tomcat.version>`（同一 10.1 线，Tomcat 在同 minor 线内保持向后兼容），
然后停 8080 → `mvn package` 重打 fat jar → 重启 → `--refresh` 重扫。

**效果（实测，非估算）**：

| 指标 | 处置前 | 处置后 |
|---|---|---|
| Critical | **7** | **0** |
| High | 25 | 11 |
| 总命中 | 74 | 41 |
| 扫描结论 | 阻断（退出码 1） | 通过（退出码 0） |
| Java 测试 | — | **151 项全绿，BUILD SUCCESS** |

> 剩下 11 条 High 全在 Jackson 2.17.2 与 Spring Framework 6.1.12（Spring Boot 3.3.3 托管）。
> 按阈值它们**只告警不阻断**，本轮不动。若将来要清，方向是整体升 Spring Boot 线
> （实测 spring-webmvc 6.1.21 的 High 由 4 条降到 2 条），属独立任务。

## 5. 豁免台账格式与门禁

文件：`security/deps-allowlist.json`

```json
{
  "entries": [
    {
      "id": "GHSA-xxxx-yyyy-zzzz",
      "package": "Maven:org.example:demo@1.0.0",
      "reason": "本系统未启用相关特性（未开 WebDAV / 未使用容器管理认证），不可达",
      "disposition": "接受风险，等上游修复版本；90 天后复评",
      "owner": "责任人（邮箱或工号）",
      "expiresAt": "2026-12-31"
    }
  ]
}
```

**六项一个都不能少**，且台账本身**也有门禁**：

| 违规情形 | 结果 |
|---|---|
| 缺 `id` / `package` / `reason` / `disposition` / `owner` / `expiresAt` 任一项 | **判红**（退出码 1） |
| `expiresAt` 已过期 | **判红** |
| `expiresAt` 不是 `YYYY-MM-DD` | **判红** |
| `severity` 写了无法识别的取值 | **判红** |
| 条目指向的漏洞已消失（悬空豁免） | 仅提示清理，**不阻断** |

> 为什么台账违规也要判红：**写得残缺的豁免看上去像"已处置"，比没有豁免更危险**。
> 一个"看起来处理过了"的台账会让人停止追问，而真相是没人处理。

## 6. 快照与漂移：什么时候要 `--refresh`

漏洞库与依赖闭包都以**快照**形式随仓库走（`security/*.json`），所以 CI **离线**可跑、
断网不会因此变红。代价是快照会过期，需要用 `--refresh` 刷新：

| 时机 | 动作 |
|---|---|
| 改了任何依赖（`requirements.txt` / `pom.xml` / `package-lock.json`） | 必须 `--refresh`，否则 CI 报"未在漏洞快照中"（退出码 2） |
| 处置完一个漏洞后 | `--refresh` 复扫，确认降级或消失，并删掉对应豁免 |
| 发版前 / 定期（建议每月） | `--refresh` 拉取最新漏洞库——**不刷新就永远看不到新披露的漏洞** |
| Java 侧改了依赖 | 记得先 `mvn package` 重打 fat jar（闭包来源是构建产物） |

⚠️ **快照过期是"判红"而不是"警告"**：`未评估 ≠ 安全`。
若做成警告，就会出现"CI 一直是绿的，但扫的是三个月前的世界"。

## 7. 四个容易踩的坑

1. **`npm audit` 在本机默认用不了**：npm registry 指向淘宝镜像
   `registry.npmmirror.com`，该镜像不实现 `/-/npm/v1/security/*`，会报
   `404 [NOT_IMPLEMENTED]`。必须显式 `--registry=https://registry.npmjs.org`。
   （本项目走 OSV，不受影响，但别被这条误导以为是"没漏洞"。）
2. **"扫环境"会淹没你**：共享 conda 环境 77 个包里 15 条命中**全是无关包**
   （jupyter 生态）。必须扫**闭包**。
3. **`UNKNOWN` 不能当成"安全"处理**：定级失败的漏洞会被显式列出并计数。
   把 `UNKNOWN` 当安全 → 真漏洞静默消失；当 Critical → 门禁长期红着然后被人绕过。
   所以选"列出但不阻断"，并在报告里可见。
4. **别只看退出码**：`deps` 作业绿只代表"没有未处置的 Critical"，
   不代表没有 High。要看 High 请读报告：`python scripts/scan_deps.py`。

---

## 8. 已知边界

- **不覆盖镜像与运行期**：只扫仓库里声明/锁定的依赖，不扫容器镜像层、OS 包、动态加载。
- **不做许可证合规判定**：只列不判（见 `docs/依赖清单.md` §6）。
- **CVSS 仅实现 v3.1**：v4 向量标 `UNKNOWN`（不猜分数）。
- **首次必须联网一次**：`--refresh` 需要访问 `api.osv.dev`；此后 CI 全离线。
- **豁免是负债**：每条豁免都应指向一个具体的复评日期；到期未处置会直接判红，
  这是**刻意**的——不让"以后再说"变成"永远不说"。
