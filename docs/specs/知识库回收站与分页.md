# 知识库回收站（软删除）与列表分页

> 状态：已实现 | 范围：agt_python / agt_backend / agt_web 三端
> 前置：`知识库数据准备方案.md`、`链路设计-检索过滤与证据充分性评审.md`

## 1. 背景

在线知识库管理上线后暴露两个使用问题：

1. **文档列表穷举全库**：全库 78 篇文档一次渲染成一张长表，翻找困难、首屏无意义加载。
2. **删除是硬删除**：`delete_document` 直接 `client.delete()` 抹掉 Milvus 切片并删掉落盘源文件，
   误删后**无法恢复**——对管理界面而言是不可逆操作，风险过高。

本 spec 定义：**列表分页** + **删除改为移入回收站（软删除）**，并保证回收站内容
在语义上"已删除"——不再参与智能体检索。

## 2. 关键约束：软删除必须真的不可检索

软删除最容易出的问题是**标记式假删除**：仅在元数据上写一个 `deleted=true`，
但检索链路的过滤表达式没有把它排除，导致"界面上已删除、智能体照样答出来"。
这类问题不会报错，只会让用户对系统失去信任。

因此本方案的**第一原则**：删除后该文档的切片必须**物理上不在检索集合中**，
而不是依赖过滤条件写正确。

## 3. 方案取舍

| 方案 | 做法 | 检索安全 | 恢复代价 | 其他 |
|---|---|---|---|---|
| A. 标记式 | 给切片置 `visibility=recycled`，检索表达式排除 | ⚠️ 依赖过滤条件写对，一旦某处漏改即泄漏 | 瞬时（改回标记） | 需 upsert 全字段回写（含向量） |
| **B. 移除 + 本地备份（采用）** | 切片从 Milvus 删除，同时把元数据与全文备份到本地回收站目录 | ✅ 数据真不在集合里，不存在漏过滤的可能 | 需重新 embedding（实测 2–3 秒/篇） | 不改 Milvus schema |

选择 B 的理由：

- **不依赖 Milvus schema 变更**。给 `kb_drone` 加字段需要重建集合与全量重灌
  （见 `切片方案与元数据设计.md`），代价与风险都远超本需求。
- **检索侧零改动**。`retriever._auth_expr` 与 `kb_service._scope_expr` 保持原样，
  不需要新增 `deleted == false` 之类的条件——少一处需要同步维护的地方，就少一处出错可能。
- 语料规模小（百篇级），恢复时重算向量的 2–3 秒开销可接受。

代价与缓解：备份文件在磁盘上，磁盘损坏即不可恢复。教学与内网场景可接受；
若后续要求更高，可把回收站目录挂到独立卷或改为写独立 Milvus 集合。

## 4. 数据结构

回收站目录：`agt_python/data/kb/recycle/`（**已加入 .gitignore**，不入版本库）

每篇被删除的文档一个 JSON：`<doc_id>.json`

```jsonc
{
  "docId": "无人机锂电池保养与续航管理",
  "docTitle": "无人机锂电池保养与续航管理",
  "category": "manual",
  "owner": "admin",                 // 原归属，恢复时保持
  "visibility": "private",          // 原可见性，恢复时保持
  "source": "uploads/xxx.md",
  "sourceType": "upload",
  "docUpdated": "2026-09-17",
  "chunkCount": 10,                 // 删除时的切片数
  "charCount": 2145,
  "fileName": "无人机锂电池保养与续航管理.md",  // 含扩展名，恢复时用于重新落盘
  "deletedAt": "2026-09-17 17:40:12",
  "deletedBy": "admin",
  "deletedByAdmin": true,
  "chunkTexts": ["原文按原顺序拼接的切片文本…"]  // 源文件缺失时的兜底恢复依据
}
```

**同时保留 `data/kb/raw/uploads/` 下的源文件**——它是未经切片的完整原文，
恢复保真度高于用切片拼接。源文件只在该文档被**彻底删除**时才清理。

## 5. 接口契约

### 5.1 Python（8000）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/kb/documents?owner=&scope=&page=&pageSize=` | 文档列表，**新增分页** |
| DELETE | `/v1/kb/documents/{docId}?owner=&is_admin=` | 改为**移入回收站**（软删） |
| GET | `/v1/kb/recycle?owner=&scope=&page=&pageSize=` | 回收站列表 |
| POST | `/v1/kb/recycle/{docId}/restore?owner=&is_admin=` | 从回收站恢复 |
| DELETE | `/v1/kb/recycle/{docId}?owner=&is_admin=` | 彻底删除（不可恢复） |

分页响应统一为：

```jsonc
{ "total": 78, "page": 1, "pageSize": 20, "totalPages": 4, "items": [ ... ] }
```

### 5.2 Java（8080）——前端唯一入口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/kb/documents?page=&size=` | 分页透传，`owner/scope` 由登录态注入 |
| DELETE | `/v1/kb/documents/{docId}` | 移入回收站 |
| GET | `/v1/kb/recycle?page=&size=` | 回收站列表 |
| POST | `/v1/kb/recycle/{docId}/restore` | 恢复 |
| DELETE | `/v1/kb/recycle/{docId}` | 彻底删除 |

权限收口**只在 Java 层判断**（与既有设计一致）：`is_admin`、`owner` 均由登录态注入，
前端参数一律不采信。Python 侧保留同名参数仅为直接调试用。

权限矩阵（在既有基础上补充回收站列）：

| 操作 | 匿名 | 登录用户 | 管理员 |
|---|---|---|---|
| 文档列表 / 统计 / 检索 | 仅 public | 自己的 + public | 全库 |
| 上传 | ❌ 4010 | ✅ | ✅ |
| 移入回收站 | ❌ 4010 | 仅自己上传的 | 任意文档 |
| 回收站列表 | ❌ 4010 | 自己删除的 | 全部 |
| 恢复 / 彻底删除 | ❌ 4010 | 自己删除的 | 全部 |

回收站列表要求登录：它是"已删除内容"的索引，匿名不应可见。

## 6. 关键流程

### 6.1 删除（移入回收站）

```
校验存在 + 归属 → 查询该文档全部切片（含 text，按 chunk_index 排序）
  → 写 recycle/<doc_id>.json（先写文件、后删向量）
  → 从 Milvus 删除切片并 flush
  → 保留 uploads/ 源文件
```

**顺序上先落备份、再删向量**：若在删除过程中失败，最坏情况是回收站里多一条记录
（可再彻底删除），而不会出现"向量删了、备份没写"的数据丢失。

### 6.2 恢复

```
读 recycle/<doc_id>.json
  → 若 Milvus 已存在同 doc_id → 报错，要求先处理冲突（不静默覆盖）
  → 正文来源：优先 uploads/ 源文件；缺失则用 chunkTexts 拼接
  → 复用 ingest(...)：切片 → embedding → 写入，owner/visibility/category 保持原值
  → 成功后删除回收站 JSON
```

同名冲突**不自动覆盖**：恢复是把内容"放回"，而覆盖会连带丢掉用户新上传的版本，
应由用户明确决策。

### 6.3 彻底删除

```
删除 recycle/<doc_id>.json → 清理 uploads/ 源文件
```

前端需**二次确认**，并在文案中明确"不可恢复"。

## 7. 分页设计

- 默认 `pageSize=20`，前端提供 10 / 20 / 50 三档。
- **接口层设硬边界 `1 ≤ pageSize ≤ 100`，超限直接返回 422 拒绝**——对外契约明确，
  不静默改用户传的值；服务层另有一层 `normalize_page` 收敛兜底，防止内部调用
  （或未来新增的调用方）传入脏值导致 500。两层分工：接口管契约，服务管健壮性。
- `list_documents` 的实现是"拉元数据后在进程内按 doc_id 聚合"（Milvus 无 GROUP BY），
  分页发生在**聚合之后**——即先聚合出全量文档，再切页。当前规模（2010 切片 / 80 文档）
  聚合耗时在 1 秒内，可接受；若切片数增长到十万级，需改为 Milvus `query_iterator`
  或引入独立元数据表（记录在"明确不做"）。
- 前端"共 N 篇"显示 `total`（全量），而非当前页条数，避免用户误以为只有当前页这么多。
- 页码越界（`page > totalPages`）不报错，返回空 items——越界是浏览行为，不是错误。

## 8. 边界与异常

| 场景 | 处理 |
|---|---|
| 删除不存在的文档 | 业务错误"文档不存在：xxx"（映射 3002 → DATA_UNEXISTS） |
| 删除他人文档（非管理员） | 业务错误"只能删除自己上传的文档" |
| 删除时备份写入失败 | 中断删除，返回失败——不允许在无备份的情况下删向量 |
| 回收站 JSON 损坏 | 列表时跳过该条并记警告日志；恢复时报"回收站记录已损坏" |
| 恢复时源文件缺失 | 降级用 `chunkTexts` 拼接正文 |
| 恢复时同名文档已存在 | 报错提示，不覆盖 |
| 恢复时 embedding 失败 | 保留回收站记录（**不删 JSON**），用户可重试 |
| 彻底删除后源文件残留 | 一并清理 `uploads/<doc_id>.*` |

## 9. 验收标准

1. 上传文档 → 检索可命中
2. 删除（移入回收站）→ **检索不再命中**（核心安全项，必须验证）
3. 回收站列表可见该文档，含删除时间与删除人
4. 恢复 → 检索重新命中，且 owner / visibility / 分类与删除前一致
5. 彻底删除 → 回收站记录与源文件均消失
6. 分页：总数、页码、翻页数据正确；每页条数切换生效
7. 权限：普通用户看不到他人删除的文档，也无法恢复/彻底删除
8. 匿名调用回收站任何接口均 4010

## 10. 明确不做

- 回收站自动清理（TTL 过期自动彻底删除）——本期手动清理，避免用户未察觉即丢数据
- 分页的游标式实现与深分页优化——当前规模无必要
- 独立元数据库（把文档元数据从 Milvus payload 迁到 MySQL）——架构级改动，另立 spec
- 批量恢复 / 批量彻底删除——先验证单条流程
