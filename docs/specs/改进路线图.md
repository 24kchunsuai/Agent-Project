# 改进路线图：参照 AgentCraft 与 open-agent-master 的差距盘点

> 版本：v1.0 ｜ 日期：2026-09-19 ｜ 状态：待评审（清单性质，不是开工令）
> 调研方法：两个探索代理分别盘点 `D:/install/java/javaworkspace/AgentCraft` 与
> `D:/install/java/javaworkspace/open-agent-master` 的能力面，再回 drone 代码逐项核实
> （铁律：**判定以代码为准**——代理初报的 6 个"可能缺"，核实后 3 个实际已有）。
> 结论性质：分「已对等勿重复建设 / 建议补 / 不建议做」三类。

## §1 已对等或更强的部分（勿重复建设）

| 能力 | drone 现状 | 对比参照 |
|---|---|---|
| 防环熔断 | 循环指纹：同工具+同参数第 2 次提醒、第 3 次熔断收尾（`agent_loop.py`） | = open-agent `LoopDetector` |
| 危险操作人工确认 | 危险白名单 + 确认词只认用户字面消息 + admin 角色校验（`guard.py`） | **强于** open-agent `PendingConfirmation`（确认词不认模型/工具内容，天然防注入授权） |
| LLM 故障转移 | 多供应商链序 failover + 冷却 + 429/5xx 退避重试（`core/llm.py`） | = open-agent `LlmClient` |
| RAG | BM25+dense 混合检索 + rerank + 证据充分性拒答 + 查询改写 | **强于两个参照**（AgentCraft 单集合向量；open-agent 纯 dense、无 rerank/改写/拒答） |
| 数据中台 | 四类事件表 + DWS 预聚合 + trace 七段还原 + 知识缺口聚类补库 | **两个参照都没有** |
| 会话记忆 | M-1~M-5 全套：持久化 / token 双锚点 / 相关性过滤 / 埋点 / 用户画像 | 参照均无画像与过滤闭环 |
| 子代理委派 / 复杂度路由 / Plan-and-Execute | 均已有 | = 两者对等 |
| 治理工单 / 审计 / 知识库治理 | 巡检开单 + 回收站 + TTL + 对账 + 审计 | 对等（"无人访问"维度除外，见 §4.10） |

## §2 P1：建议下一批（约 2~3 天）

### 2.1 澄清追问（轻量 HITL）
- **参照**：AgentCraft `python-service/agent/planner.py`——模糊/过短问题触发澄清，前端 `requires_input`。
- **drone 现状**：意图三分类后直接作答，模糊问题硬答。
- **建议落点**：intent 识别后加"澄清判定"（复用短查询/指代判据，禁止第二套阈值）；命中则返回澄清追问而非硬答。
- **验收**：模糊问法（"帮我查一下"）返回追问；正常问法不受影响；有单测。

### 2.2 间接注入防护
- **参照**：open-agent `guardrail/InjectionGuard.java`——检索/工具内容加边界标记 + 注入模式检测。
- **drone 现状**：确认门挡住了"模型自说自话执行危险操作"，但知识库语料可由用户上传，恶意文档污染答案的攻击面真实存在，且无显式防护。
- **建议落点**：RAG 证据与工具返回进 prompt 前加统一边界标记；对内容里的"忽略以上指令"类模式打标并计数（对齐全链路容错规约的降级计数风格）。
- **验收**：注入样本被边界标记隔离且不改变回答行为；检测命中落 `fault_event`。

### 2.3 CI 流水线
- **参照**：AgentCraft `.github/workflows/ci.yml`（pytest + mvn test + 前端 build）。
- **drone 现状**：无任何 CI（本地手工 pytest）。
- **建议落点**：GitHub Actions 单 workflow：`agt_python` pytest（排除既有基线 4 败口径）→ `agt_backend` Maven package → `agt_web` build。推到 gitee 则用 gitee Go/Gitee CI 或仅 GitHub 镜像。
- **验收**：push 触发全绿一次。

### 2.4 日志/落库脱敏
- **参照**：open-agent `evaluation/LogSanitizer.java`（PII 清洗）。
- **drone 现状**：telemetry 只存长度/摘要（内容不落库），但异常 message、trace 明文里可能带用户输入片段，无清洗。
- **建议落点**：埋点写入前统一走一个 `sanitize()`（手机号/身份证/邮箱模式替换）；日志与 `agent_chat_log` 明细同用。
- **验收**：含 PII 样本的入参经脱敏后落库；单测覆盖三种模式。

## §3 P2：有价值，排后面

| # | 事项 | 参照 | drone 现状 | 建议落点 |
|---|---|---|---|---|
| 3.1 | **MCP 外部工具接入** | open-agent `McpClientManager`（HTTP/Stdio + 健康探活 + 单点失败不阻断启动） | 工具全内置 | AgentLoop 工具注册表加 MCP provider；健康探活复用 scheduler 任务表模式 |
| 3.2 | **工具统一重试策略** | AgentCraft `tools/registry.py`（超时/重试/权限统一框架） | 仅 HTTP 层超时，无统一重试 | biz 工具 manifest 加 `idempotent` 标记；幂等工具失败按策略重试并计数 |
| 3.3 | **整栈容器化** | AgentCraft docker-compose（全服务一键起） | `deploy/` 只有 milvus，四服务手工拉起 | 补 3 个 Dockerfile + compose（Python/Java/前端），Milvus 已有 |
| 3.4 | **成本视图** | 两个参照均无（drone 离得最近） | chat_log 已有 prompt/completion tokens | 按模型单价折算，DWS 加日粒度成本聚合，看板加一卡 |
| 3.5 | **空结果 vs 失败区分** | open-agent `ResultValidator` | 工具返回空与报错在上报里未细分 | `agent_tool_call` 加结果分类；空结果按 warn 观测 |

## §5 不建议做（已论证，防返工）

| 事项 | 理由 |
|---|---|
| 用户管理 / 公告管理 | 用户体系在 jsdstu-3（8060），自建即双写用户；公告与中台无关 |
| Redis 多级缓存 | 单实例部署收益为零，可靠性反而更差（会话记忆规约 §2 已论证） |
| 问答日志页 / 执行记录页 | drone 会话明细 + trace 追溯已覆盖且更强 |
| ragas 类重评估 | 已有 questions.jsonl 静态评估集 + 知识缺口闭环 |
