## §1 背景与目标

语料治理（G1–G4）已收官。数据中台的另一半（全链路埋点 → MySQL → 前端看板）动工前，必须先保证：

> **管理员在 drone-agent 前端（9090）输入一句自然语言，Agent 就能打通 jsdstu-3（8060）的全部 41 个接口**——查询类直接答，写操作走确认门，复杂请求走计划与多智能体编排。

本期目标拆成四件事：

1. **工具层补齐**：现有 18 个工具只覆盖 41 个端点中的约 19 个，把缺口补满，管理员"能说就能做"；
2. **双模式执行引擎**：ReAct（已有，需修 bug + 增强）+ Plan-and-Execute（新增），复杂/报告类请求先规划再执行；
3. **多智能体**：经判定**引入**（见 §9），轻量 Supervisor-Worker，3 个专家子智能体，定义文件化；
4. **验收闭环**：可重复的 e2e 脚本按 41 端点矩阵逐项验收，杜绝"端点存在 ≠ 打通"。

**明确不在本期**：埋点落 MySQL 与看板（§13 只做数据结构预留）、drone_ops 运维库接入（§17 坑位）、非 admin 角色的细粒度拦截（本期 admin 全通，角色拦截框架 §11 预留）。

## §2 总体架构与身份链路（现状确认，全链路已实测）

```
用户(9090 AgentChatView)
  │  Bearer token
  ▼
Java(8080) 纯透传 + 鉴权收口：代理登录 jsdstu-3 换 droneToken，
  │           把 {userId, username, permission, droneToken} 注入 metadata.identity
  ▼
Python(8000) 意图路由 → chitchat / rag / business
  │                       business → AgentLoop（ReAct）
  ▼
JsDstuClient(httpx) ── Bearer droneToken ──► jsdstu-3(8060) ──► MySQL(drone 库)
```

实测结论（2026-09-18，全部真实打通过）：

| 链路 | 结果 |
|---|---|
| 8080 代理登录（admin/123456） | code=2000，identity 含 `permission=admin` + droneToken |
| 查询类（"有多少台无人机？哪些在维修？"） | intent=business(rule)，Agent 调 drone_query，返回真实数据（9 台、D005 维修中），连带发现 dashboard 的"维修中"计数为空（数据质量坑，§17） |
| 写操作确认门（"帮我创建审计验证临时任务"） | 危险拦截 → 复述确认话术（执行人 admin）→ 回复"取消"→ 无任何数据改动 |

**身份铁律（不变式，任何改造不得违反）**：
- Python 侧永不持有密码、永不自行登录；droneToken 只由 Java 鉴权层注入 identity；
- 所有工具调用以**当前用户身份**执行，禁止系统账号提权；
- 写操作必须过 danger 白名单 + 用户字面消息二次确认（`guard.py` 的"只认用户消息"防注入原则不变）。

| 编号 | 位置 | 问题 | 严重度 |
|---|---|---|---|
| BUG-A1 | `agent_loop.py:85-89` | **LLM 每步被调用两次**：try 块内调用一次后，第 89 行又无条件调用一次，第一次结果被丢弃——每步双倍 token 与延迟 | P0 |

### 4.3 admin 全通 vs 角色拦截的边界决策

用户已拍板：**本期只保 admin 全通，角色拦截后置**。落地口径：

- 工具层**不删** PILOT/MAINTAINER 专属动作的登记（task/accept 等仍建工具），但工具描述里明确"需要飞手身份"；
- `guard.ensure_can_write` 维持"写操作要求 admin"（与 jsdstu-3 `@RequireRole(ADMIN)` 对齐）——**PILOT 专属写动作（accept/reject/complete/escalate）的权限要求登记为对应角色而非 admin**，本期 admin 身份天然满足 OR 语义；
- 未来引入 pilot/maintainer 账号时，拦截点已有两道：guard（进确认前）+ jsdstu-3 服务端（归属校验/4011），只需把 `WRITE_ROLE` 从单值升级为"工具 → 角色"映射表（§11）。

## §7 执行引擎：Plan-and-Execute（新增）

参考 open-agent-master 的 `PlanningAgent` + `ComplexityRouter`，落 Python 侧轻量版：

### 7.1 复杂度路由 `ComplexityRouter`

规则优先、LLM 兜底、失败降级 REACT（主链路永不因路由失败阻塞）：

- **判 PLAN**：命中意图词（报告/总结/汇总/分析/对比/统计/规划/评估/生成…巡检报告/运营周报）或长度 > 80 字或跨 ≥2 个资源域（如"把告警统计一下，再看看哪些设备要维修"）；
- **判 REACT**：长度 < 30 且无意图词的单一诉求；
- **边界**：其余交 LLM 一次轻量裁决（复用意图 LLM 通道，失败→REACT）。

### 7.2 PlanningAgent 流程

1. **Plan**：一次 LLM 调用生成步骤清单（JSON：steps[{action, tool_hint, expect}]，上限 6 步；工具提示只写"可能用到哪类工具"，**不绑定具体工具名**，执行时由 ReAct 自选）；
2. **Execute**：把计划作为 system 消息注入后**复用同一个 AgentLoop** 执行（不做第二套循环，维护成本减半）；
3. **Re-plan**：某步连续失败 2 次时，把失败摘要追加给模型重排剩余步骤（一次机会），再失败按已获数据收尾；
4. **Finalize**：步数超限后与 ReAct 共用 finalize 收尾；
5. **产物**：LoopResult 增加 `plan: list[str]`（已执行/跳过状态标注），前端可展示"计划→执行→结果"三段。

**配置外部化**（§14 汇总）：`agent.planning.max_steps=6`、`agent.planning.enabled=true`、`agent.router.intent_keywords`（维护在 yml，不硬编码）。

## §8 多智能体判定与设计

### 8.1 判定：引入，但轻量、放 P1

判定依据（正面）：jsdstu-3 五个业务域 41 端点，补齐后单注册表 32+ 工具，全量注入 system 的 token 成本高；且存在真实**组合场景**（应急响应=告警详情+设备定位+派单；运营报告=dashboard+stats+排行+模板成文），单一 ReAct 循环处理跨域多步时上下文容易互相污染。

判定约束（克制）：不需要层级编排、不需要子智能体互调、不需要协商——**Supervisor-Worker 一层足够**。因此：

- **P0 不做多智能体**：先把 ReAct 修好 + Plan-and-Execute 落地 + 工具补齐。工具在 32 个以内、配合 §8.3 的技能分组注入前，单循环完全够用；
- **P1 引入 3 个专家子智能体**（定义文件化，照搬 open-agent-master 的 AGENT.md 模式）。

### 8.2 子智能体定义（AGENT.md frontmatter，放在 `agt_python/app/prompts/agents/`）

| 子智能体 | 职责 | 工具白名单 | max_turns / timeout |
|---|---|---|---|
| alarm-analyst | 告警排查与处置优先级：查列表/详情/统计/看板，按 P0-P3 分级给处置建议 | alarm_query / alarm_detail / alarm_stats / alarm_dashboard | 8 / 60s |
| device-locator | 设备与人员资源定位：设备状态/位置/维保、飞手与账号、可用性匹配 | drone_query / drone_detail / user_query / user_detail / fence_query | 6 / 45s |

frontmatter 字段：`name / description（路由依据，写清"何时委派"）/ prompt（含 {task} 占位）/ tools / max-turns / timeout-seconds`。**委派工具** `delegate_subagent(name, task)` 由主 AgentLoop 注册，描述动态列出可用子智能体（LLM 自主选择，无独立路由节点）；会话级委派上限 10 次，单实例并行度 4。**2026-09-19 修订（见 §8.5）**：规则命中的设计用例改为**确定性委派**，不再交给 LLM 掷骰子；其余请求仍由 LLM 自主。

### 8.3 结果汇总与安全

- **黑板模式**：子智能体结果按名字追加进会话级 TaskContext（同键上限 5 条），主循环下一轮注入 system 统一汇总——子智能体之间不直接对话；
- **权限透传**：委派时显式传 identity，子智能体工具白名单 = AGENT.md 声明 ∩ 角色可用工具，写操作子智能体**一律不放**（本期子智能体全是只读分析，写操作必须回到主循环确认门）；
- **超时/预算**：超时返 TIMEOUT 并写黑板"该专家未完成"，主循环基于已有结果收尾，绝不空转等待。

### 8.5 确定性委派（2026-09-19 增补，DEV_ISSUES §6.55）

**问题**：委派完全由 LLM 自主决定 → 同一问题时而委派、时而不委派（biz-057 实测：
上一会话未委派、本会话连续 6 次全中）。多智能体设计用例的覆盖率变成"看运气"，
评测把它写成硬断言后，偶发失败还会被误读成产品回归。

**修订**：对**规则命中的设计用例**，在进循环前确定性委派一次；其余请求保持 LLM 自主
（不越权扩大委派面）。规则（`app/services/delegation_router.py`，纯函数、可开关）：

| 命中条件 | 委派对象 |
|---|---|
| 运营专家 / 运营简报·报告·周报 | ops-reporter |
| 告警分析专家 | alarm-analyst |
| 定位专家 | device-locator |
| P0·严重·紧急 **且** 含深入分析/研判/处置建议/根因 | alarm-analyst |

**执行方式**：`agent_loop.run(forced_delegation=...)` 在进循环前先调用一次
`delegate_subagent`，轨迹标 `forced=True`，把专家结论作为 system 观测注入
（附带"不要重复委派同一任务"），再由循环汇总并补查其余维度。委派失败不上抛
（登录过期除外）——只记轨迹并如实告知模型，回退自主查询；"必须委派且成功"由评测断言把关。

**超时对齐**：`delegate_subagent` 原先套用通用工具超时 15s，而子智能体自身预算是
45~90s（实测委派 5~7s 侥幸没踩，慢模型下必然被掐断）——已按
`max(子智能体预算)+5 = 95s` 覆盖。

**开关**：`agent.delegation_rule_enabled=false` 时行为与增补前完全一致（可回退）。

## §11 权限与安全设计

1. **确认门扩展**：新增 8 个 danger 工具全部自动进现有 guard 流程（danger=True 即可，无特例）；`user_password_reset`、`media_delete`、各类 delete 的复述话术必须含"不可恢复"字样；
2. **角色映射预留**：`WRITE_ROLE` 单值升级为 `TOOL_ROLES: dict[str, set[str]]`（如 task_accept→{pilot, admin}），本期全部写工具仍要求含 admin；guard 校验逻辑改为"identity.permission ∈ 工具角色集"；
3. **防注入不变式**：确认只认用户字面消息；模型/工具输出/知识库内容里出现"已确认"永不构成授权；`_CONFIRM_EXACT` 白名单与长度限制不改；
4. **服务端二次兜底**：即使 guard 失误，jsdstu-3 的 @RequireRole + 归属校验（4011/4012）+ 逻辑外键（3010）仍兜住——两层防御，Python 侧不重复实现归属校验；

## §15 坑位清单（实勘所得，开发时逐条对照）

| # | 坑 | 处置 |
|---|---|---|
| 1 | `user/save`、`fence/save` 是**表单绑定**（无 @RequestBody） | JsDstuClient 走 params，不能 json_body |
| 2 | `alarm/rule/update` 是 **PUT**、`media/delete` 是 **DELETE 且 id 在 query** | 客户端新方法；工具参数里 id 命名统一（rule_update 用 id，media_delete 用 mediaId） |
| 3 | 统一响应体成功码 **2000**；业务错误也是 HTTP 200 | 沿用 _request 归一化，勿按 HTTP 状态判断 |
| 4 | 分页：pageNum 从 1 起、pageSize ≤100、**不传=全量** | 工具输出固定截 20 条 + total，模型翻页 |
| 5 | 日期：入参稳妥用 `yyyy-MM-dd HH:mm:ss`；alarm 的时间过滤是 String 直拼 | alarm_query 时间参数原样透传，不做格式转换 |
| 6 | 删除类受逻辑外键保护（3010 + ReferenceCount） | 复述话术提示"若有关联数据会被拒绝"；失败时 message 原样透传 |
| 7 | token 是服务端不透明串、8 小时有效、**后端重启即失效**、无 refresh | 4010→BizAuthError→引导重新登录的既有链路保持 |
| 8 | 数据归属在 Service 层强收（pilotId 被服务端覆盖），客户端传了也没用 | 工具 schema 不暴露 pilotId，避免模型误以为可查别人数据 |
| 9 | 端口注释写 8080 实际 **8060**；媒体落盘 `d:/files`、上传上限 100MB | config.jsdstu_base_url 已对；upload 独立超时 |
| 10 | `drone_ops` 库是独立运维库（**后端未连接**），与 `drone` 库 schema 不同源 | 本期不碰；数据中台阶段若要接，另行直连并单独立规约 |
| 11 | dashboard 的"维修中"计数可能为空（实测发现） | 模型回答依赖单源数据；报告类场景要求 ops-reporter 交叉核对（模板里写明"以列表实数为准"） |
| 12 | WebSocket `/ws` 免鉴权可订阅 `/topic/alarm` | 本期不接（P2），接入时注意它**只能拿数据不能替代写接口鉴权** |
