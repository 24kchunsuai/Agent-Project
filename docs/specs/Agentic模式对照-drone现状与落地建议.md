## §2 已对等或更强（明确列入"勿重复建设"）

1. **RAG（第 14 章）**：书中把混合检索、可归因列为"标准组成"——我们不仅做了混合检索（BM25+dense RRF）与引用元数据，还多做了 rerank、查询改写、证据充分性拒答。**结论：RAG 线不因读书而改，只可能从 GraphRAG / Agentic RAG 找增量（见 §4）。**
2. **记忆管理（第 8 章）**：书里讲的是"用框架 API（ADK Session/State/MemoryService、LangGraph Store）"。我们的 M-1~M-5 是自研闭环，且多了三样书中没有的：**相关性过滤（M-3）**、**用户画像（M-5）**、**TTL 定时清理**。**结论：架构不动。** 详见 §3 补"程序记忆"。
3. **异常处理与恢复（第 12 章）**：书中是"重试/回退/降级"三件套；我们有 failover 冷却链 + 退避 + 降级计数 + 熔断 + 兜底收尾，层级更完整。**结论：不动。**
4. **HITL（第 13 章）**：书中担心"可扩展性不足"，我们的确认门只拦危险写操作，天然规避了这个缺点。**结论：不动。**
5. **评估与监控（第 19 章）**：我们的四类事件表 + DWS + trace 七段还原，比书中"日志轨迹"更结构化。**结论：不动主体，只补轨迹评分口径（见 §3）。**
6. 其余 ✅ 项（提示词链 1、路由 2、并行化 3、工具使用 5、规划 6、多智能体 7）：逐项已对位，无新增动作。

## §3 部分实现项：差在哪、怎么补

### 3.1 反思（第 4 章）— 有评审无重写

- **现状**：`rag_service.py` 有评审员（judge）判定证据覆盖情况，并把结论注入生成 prompt；judge 失败时**跳过评审继续生成**（fail-open，正确）。
- **差距**：书中是「执行 → 评审 → 重写 → 再评审」的迭代循环（含明确停止条件）。我们是**单轮评审**，不做重写。
- **建议**：**暂不补**。单轮评审 + 证据充分性拒答已覆盖"证据不足时如实拒答"的场景；引入重写循环会让每次问答多一次 LLM 调用（成本与延迟翻倍），而收益未经验证。若未来评估集显示"答案质量受生成措辞影响显著"，再立项——**判据是评估集，不是书上写了**。

### 3.2 目标设定与监控（第 11 章）— 有预算无目标

- **现状**：`max_steps` 步数预算、LoopDetector 指纹熔断、无工具兜底收尾。
- **差距**：书中要求"显式目标 + 持续对比进度 + 达成判定"。我们只有"防跑偏"，没有"判达成"。
- **建议**：低优先。当前任务多为单轮问答型（复杂度路由已分流），长任务的"目标达成判定"要等长任务场景真实出现（与改进路线图 P3 的长任务能力同批）。**降级方案已够用**：步数触顶即交付阶段性结论，不抛异常。

### 3.3 资源感知优化（第 16 章）— 有路由无账本

- **现状**：复杂度路由已做（≈ 书中 Router Agent）。
- **差距**：① 缺**成本视图**（token × 单价折算，chat_log 已有 tokens 字段，只差聚合页）；② 书中 Critique Agent 会**反哺改进路由逻辑**，我们的路由阈值是静态配置。
- **建议**：成本视图列入改进路线图 P2（成本视图项），一次埋点聚合即可，收益确定。**路由反哺暂不做**——静态阈值在语料与用户量稳定时可预测，动态反哺需要大量样本，属于过度设计。

### 3.4 推理技术（第 17 章）— 只有 ReAct

- **现状**：ReAct（agent_loop）已实现；无 ToT、无 self-consistency、无代码执行（PAL）、无论辩链（CoD）。
- **建议**：
  - **self-consistency**：若出现"同一问题多次答案不稳定"的埋点证据，可对高风险问答（如告警处置建议）做 N 次采样投票——**需评估集裁决**。
  - **PAL / 代码执行**：无人机数据里有统计类问题（飞行时长汇总、故障率），若发现 LLM 算术不可靠（书中第 1 章明确警告过），可加一个受限计算工具。**当前无证据，不立项**。
  - **ToT / CoD**：成本高、场景不明，**不做**。

### 3.5 护栏（第 18 章）— 缺注入防护与脱敏

- **现状**：确认门、角色校验、危险白名单。
- **差距**（与书中第 18 章对照）：① **间接注入防护**（用户上传的语料/工具返回内容加边界标记 + 注入模式检测）；② **输出侧过滤 / PII 脱敏**。
- **建议**：**与 `生产级改进规约.md` 的 S-7（注入防护）、S-8（PII 脱敏）完全重合，随该规约 P1 一起做**，本书第 18 章可作为实现参考（Jailbreak / Instruction Subversion 的拦截清单）。

## §7 铁律（避免"读完书就改架构"）

1. **判定以代码为准**：本表的 ✅/🟡/⬜ 全部回代码核实过；日后如需复核，用 grep 证据（如"全仓 grep `mcp` = 0"）而非印象。
2. **不因读书而改架构**：本书的教学栈是 LangChain/LangGraph/ADK/CrewAI，我们是自研栈；**模式可以借，框架不要搬**。
3. **新增能力需双门槛**：① 真实需求出现；② 评估集能证明变好。缺一不动（与 `会话记忆规约.md`、`改进路线图.md` 既有纪律一致）。
4. **冲突以既有规约为准**：`生产级改进规约.md` / `改进路线图.md` 优先级高于本文件。
5. **不做清单要留痕**：§4.3 的"不立项"同样是有价值的结论，避免半年后重新讨论同一件事。
