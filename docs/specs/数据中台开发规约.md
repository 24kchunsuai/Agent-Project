# Spec：数据中台开发规约

> 版本：v1.0（2026-09-18）
> 关联文档：`数据库设计规约.md`（存储细节）、`语料治理规约.md`（语料治理层，数据中台第一块已交付资产）、`全链路容错规约.md`（故障路径=本规约的核心数据源之一）

## 1. 背景与定位

### 1.1 数据中台在项目中的位置

drone-agent001 三模块划分中的**模块 3**。它消费的是模块 1（RAG）与模块 2（Agent 编排）运行时产生的行为数据，以及 jsdstu-3 的业务数据，产出"给人看"的观测与应用能力。

### 1.2 现状盘点（2026-09-18，勿重复建设）

| 层 | 资产 | 状态 |
|---|---|---|
| 采集 | `agt_python/app/services/telemetry.py`：四类埋点（chat/tool_call/delegation/fault_event×10 路径）、ContextVar trace_id 贯穿、降级计数（内存+JSON 落盘） | ✅ 已建 |
| 存储 | `data/metrics/observability.db` 四表（SQLite）、`data/governance/governance.db`（语料账本） | ✅ 已建 |
| 服务 | `GET /v1/agent/metrics/overview`（近 24h 聚合），Java :8080 `metricsOverview` 透传 | ✅ 已建，能力薄 |
| 应用 | 看板 `/dashboard/metrics`（四视图+trace 追溯+反馈面板+联动视图+CSV 导出，admin-only）；**P2+ 起可发起告警处置**（B1：跳对话页走确认门） | ✅ 已建 |

### 1.3 目标

1. 看板可看：四视图（会话/工具/委派/故障）+ 总览卡片 + 单次对话 trace 追溯；
2. 查询可用：时间范围、聚合趋势、失败 TopN；
3. 口径可信：指标字典统一口径，同一指标全系统只有一个算法；
4. 演进可迁：SQLite 起步，迁 MySQL 的路径与触发条件明确（见数据库规约 §7）。

## 2. 参考与取舍（不照搬 AgentCraft）

### 2.1 从 AgentCraft 借什么

- `agent_run` / `agent_step` 的"一次运行 / 每步一行"行为记录思想 → 已落为我们的 `agent_chat_log` / `agent_tool_call`；
- `doc_view_log`、`message_feedback_stats` 的"用户行为+反馈统计"表形态 → P2 业务联动与反馈闭环时参考；
- 治理三件套（audit_log / upload_task / ticket）→ 已在语料治理规约中移植；
- MySQL 建表规范（bigint 主键、表/列 COMMENT、utf8mb4、uk_/idx_ 前缀）→ 作为**迁 MySQL 后**的建表规范，见数据库规约 §7。

### 2.2 与 AgentCraft 的关键差异（为什么不照抄）

| 决策 | AgentCraft | 本项目 | 理由 |
|---|---|---|---|
| 存储 | MySQL 8.0 单库 | SQLite 单文件起步 | 单机部署、运维零成本；迁移触发条件明确（数据库规约 §7），不预付 MySQL 运维成本 |
| 数据粒度 | run/step 两级 | chat/tool/delegation/fault 四类事件表 | 事件表比层级表更适合"看板聚合 + trace 追溯"两类读模式 |
| 反馈闭环 | message_feedback_stats | 暂缺 | P2 引入：前端点踩 → 按 trace_id 追加反馈事件 → 进评测金标集 |

### 2.3 行业实践引入（联网调研结论，按需裁剪）

- **OpenTelemetry GenAI 语义约定**：采纳其字段思想——模型名、token 数、耗时、finish 原因必须结构化字段而非叙述文本；**元数据全量记、内容不落库**（现状即如此：`args_digest` 只存摘要，prompt/回复原文不进埋点库，此为铁律，见 §4.2）。
- **采样策略**：元数据类埋点 100% 采集；内容类（prompt/回复原文）默认 0%——若未来调试需要，必须走"显式开关 + 定时清理 + 独立表"，不得写进四表。
- **SLO 先于看板**：没有阈值约定的看板只是装饰。每张看板卡片须在指标字典中登记口径与告警阈值（§5）。
- **数据分层（ODS/DWS/ADS 裁剪版）**：明细表=ODS（只增不改），预聚合表=DWS，看板数据集=ADS。本项目规模**不设独立 DWD/DIM 层**，但单向流动铁律保留：ADS 只读 DWS/ODS，禁止跨层逆引用；看板前端永远调 API，不直连明细。

## 3. 总体架构

```
模块1 RAG ─┐
模块2 Agent ─┤→ [采集层] telemetry.py 埋点（非阻塞，绝不抛异常）
jsdstu-3 ──┘        │ 5s 批量 flush
               [存储层] observability.db 四表（ODS）+ metrics_daily（DWS，P1）
                    │
               [服务层] /v1/agent/metrics/*（overview / timeseries / traces/{id}）
                    │ Java :8080 纯透传（沿用 metricsOverview 模式）
               [应用层] agt_web :9090 看板（ADS 消费方）+ 导出报表（P2）
```

**三条架构铁律**（与容错规约同源）：

1. 埋点写入永不阻塞业务、永不抛异常（现实现已保证，改动不得破坏）；
2. 埋点关闭（`telemetry_enabled=false`）时全链路静默降级，接口返回 `enabled:false`；
3. 采集、存储、查询只增不改明细：修正错误用新事件（补偿事件），不 UPDATE 历史行。

## 4. 埋点规约

### 4.1 事件类型与必填字段

| 事件 | 表 | 必填 | 说明 |
|---|---|---|---|
| 对话 | agent_chat_log | trace_id, session_id, user_id, intent, mode, duration_ms | 一次 chat 一行 |
| 工具调用 | agent_tool_call | trace_id, step, tool, ok, duration_ms | 每步一行；拦截/熔断也记（blocked 字段） |
| 委派 | agent_delegation | trace_id, agent, status | status ∈ DONE/TIMEOUT/FAILED |
| 故障 | fault_event | path, detail | path 取值=容错规约 10 条路径常量；**P1 补 trace_id 列** |

**v4 增列（`agent_chat_log`，只加列不重建表）**：

| 列 | 含义 | 取值 |
|---|---|---|
| `rag_decision` | RAG 链路判定（知识缺口的唯一来源） | `kept` / `cross_domain` / `no_hit` / `insufficient_evidence`；**非 RAG 链路留空串**；`degraded` 归一为空串（属故障域，`degraded` 列已单独记） |
| `rag_docs` | 命中文档 docId 列表（逗号分隔，限 20 篇/行） | 供 B 类"无人访问文档"巡检的已访问侧；**只存 ID 不存正文** |

为什么加列而不是像 AgentCraft 那样新开一张 `qa_unanswered` 表：那次判定（decide）本就是"一次对话"的属性，独立成表会让同一轮会话的轨迹被拆到两处，违背 §2.2 单一事实来源；加列后未命中分析 = 对 `agent_chat_log` 的一个 GROUP BY，**无需新增采集点**。
`rag_docs` 截断到前 20 篇/行：对"是否从未被访问"这个二值判断无影响（从未访问仍为 0），只有极端长尾的引用计数会偏低——口径已在 §5 注明。

新增事件类型的准入条件：能回答一个现有四表回答不了的问题，且已有两处以上埋点调用点。

### 4.2 脱敏与内容红线

- **禁止落库**：prompt 原文、模型回复原文、用户身份凭据（droneToken）、jsdstu 返回的完整业务对象；
- 允许落库：长度（content_chars）、摘要哈希（args_digest，SHA-1 截断）、计数与耗时；
- 理由：埋点库是泄露面最大的库（谁都能查），按"allowlist 优先"原则默认什么都不放行。

### 4.3 字段语义对齐 OTel（便于未来接外部 APM）

| 本项目字段 | OTel GenAI 对应 |
|---|---|
| trace_id | trace_id（W3C traceparent 低 64 位可映射） |
| model / prompt_tokens / completion_tokens | gen_ai.request.model / gen_ai.usage.input_tokens / output_tokens |
| duration_ms | span duration |
| blocked / error | span status + error.type |

## 5. 指标字典（口径唯一，改口径必须改这里并升版本）

| 指标 | 口径 | 展示 | 告警阈值（建议初值） |
|---|---|---|---|
| 会话量 | agent_chat_log 按天计数（含失败） | 趋势线 | 环比 ±80% 观察 |
| 会话成功率 | ok=1 / 总数 | 卡片+趋势 | < 95% 告警 |
| 降级率 | degraded=1 / 总数 | 卡片 | > 10% 告警 |
| 端到端时延 p50/p95 | duration_ms 分位数，按 intent 分组 | 卡片+趋势 | p95 > 30s 告警 |
| 工具成功率 | tool_call ok=1/总数，按 tool 分组 | TopN 表 | 单工具 < 90% 告警 |
| 工具耗时 TopN | avg(duration_ms) 倒序 | TopN 表 | — |
| 委派完成率 | status=DONE / 总数，按 agent 分组 | 卡片 | < 80% 告警 |
| 故障路径频次 | fault_event 按 path 计数 | 排行+趋势 | 单路径日增 > 50 观察 |
| Token 消耗 | sum(prompt_tokens+completion_tokens)，按 model 分组 | 趋势 | 成本=token×外部价格表，价格表不入库 |
| 反馈保留（P2+） | `agent_feedback` 事件表保留 `feedback_ttl_days`=90 天；`feedback_content` 内容表 30 天。两者故意不同：内容含原文该短命，事件表是金标集候选来源该更长寿 | 不展示 | 无 |
| 反馈满意率（P2） | agent_feedback 近 24h up/(up+down)，二值评分（开放问题 2 拍板） | 卡片 | < 80% 观察 |
| 告警处置联动（P2，近似口径） | 委派(alarm-analyst)↔jsdstu 告警按 triggeredAt 落在委派时间 ±30 分钟内视为疑似处置对象（委派表无 alarm_id，**近似关联**，前端必须标注）；同 trace 故障为精确关联。**另独立提供待处置告警（`source=pending`）**，与委派无关，供看板发起处置 | 联动视图 | 无阈值（观察项） |
| 知识缺口量（v4） | `agent_chat_log.rag_decision IN (no_hit, insufficient_evidence)` 的会话数。**kept 不算**（答上了）；**cross_domain 必须排除**（问"今天天气"不是知识库的锅，混进来会淹掉清单）；`degraded` 也不记（检索链路故障属故障域，与知识空白处置动作不同） | 卡片 | 环比 +50% 观察 |
| 缺口主题数（v4） | 缺口问题按关键词聚类后的簇数。聚类=**实词切段 + 重叠系数**（|A∩B|/min(|A|,|B|)，阈值 0.5），**不调 LLM**（要可复现、可批跑、零 token） | 卡片+条形 | — |
| 补库优先级（v4） | **高**=insufficient_evidence 且同主题 ≥`kb_gap_min_occurrences`(默认3) —— 库里有但不够用，补一篇即可救活；**中**=no_hit 且同主题 ≥阈值 —— 库里真没有，需新增；**低**=同主题出现 1~2 次 —— 先观察攒样本 | 建议卡（红/黄/绿） | — |
| 文档命中次数（v4，B 类已访问侧） | 只统计 **kept** 会话的 `rag_docs` 引用；拒答会话即使召回到文档也**不计入**（它没答上，说明那份文档答不了这个问题）。与知识库文档清单做差集 = 从未被命中的文档（P3 才做差集视图） | 表格 | — |

分位数算法：SQLite 无内置 p95，P1 用"按天预聚合 + 近似分位（排序取第 95 百分位行）"实现，并在指标字典注明"近似值"。

### 6.1 v5：链路阶段还原（`pipeline` 字段）

**不新增接口、不新增表**——`trace_detail` 在原有四表查询之上追加一个 `pipeline` 键，把该次会话的四表痕迹**按真实控制流还原成阶段序列**，供会话明细弹窗渲染「执行流程」。

```jsonc
"pipeline": {
  "stages": [ { "key": "recall", "name": "召回", "note": "BM25 + 稠密向量双路混合检索（RRF 融合）",
                "status": "ok", "durationMs": null, "detail": "召回成功，进入重排", "error": "" } ],
  "worstStatus": "gray",     // 全链路最严重状态，前端据此显示总览标签
  "totalMs": 2900.0
}
```

**两套链路（以代码实际控制流为准，不是设计文档的链路）**

| 意图 | 阶段序列（渲染顺序） |
|---|---|
| `rag` | 意图识别 → 召回 → 重排 → 精选 → 评估 → 回答 |
| `business` | 意图识别 → 复杂度路由 → 任务规划 → 专家委派 → 工具调用 → 回答 |
| `chitchat` | 意图识别 → 回答 |

⚠️ **三处与「直觉链路」的差异（照搬会画错）**

1. **没有「query 改写」阶段**。代码全文检索 `rewrite`/`改写` 只命中语料治理的版本号改写，RAG 链路不存在查询改写环节。**不画该节点**——画了就是点了没内容的假节点，与本视图「还原真实执行」的目的相悖。
2. **「召回」是双路融合，不是单路**。`retriever.search` 用 `AnnSearchRequest(sparse/BM25)` + `AnnSearchRequest(dense/COSINE)` 两路并发，再经 `RRFRanker` 融合，之后才进 rerank。展示为单节点但说明里写明双路（用户 2026-09-19 确认此折中）。
3. **业务链路的「参数提取/槽位填充」不是独立阶段**。模型在 `tool_calls` 里直接产出 JSON 参数，工具侧才校验——没有可观测的独立阶段。参数摘要挂在**工具调用的每一步**上（`args_digest`），不单开节点。

**四色状态口径（用户 2026-09-19 定）**

| 状态 | 色 | 语义 | 典型来源 |
|---|---|---|---|
| `ok` | 绿 | 正常执行 | 无异常痕迹 |
| `warn` | 黄 | 重试 / 降级 / 兜底——仍在服务，路径不理想 | `refusal_retry`、`marker_leak_retry`、`rag_degraded`、`llm_failover`、`plan_replan`、工具被权限拦截 |
| `gray` | 灰 | **如实拒答**（`insufficient_evidence` / `cross_domain`）——设计内行为，不是故障 | `rag_refused` |
| `error` | 红 | 熔断 / 失败——真故障，用户拿不到答案 | `loop_fingerprint_break`、`tool_fail_break`、`llm_fallback`、`chat.ok=0` |

**为什么拒绝把 `rag_refused` 一律标红**：实测库里 78 条拒答，远超真故障数。一律标红会让看板"满屏红"，把设计内的如实拒答误读成系统不可用。灰/红拆分的依据是**处置动作不同**——灰 → 补语料，红 → 查系统。

**`idle` 阶段不渲染**：未参与本轮链路的阶段（如 REACT 模式下的「任务规划」）`status=idle`，前端过滤掉不画连接线。没发生的阶段画出来就是假节点。

**path → stage 映射**（`_PATH_TO_STAGE`，改映射必须同步本节）：`rag_degraded→recall/warn`、`rag_refused→evaluate/gray`、`plan_degraded→route/warn`、`plan_replan→plan/warn`、`loop_fingerprint_warn→tools/warn`、`loop_fingerprint_break→tools/error`、`tool_fail_break→tools/error`、`subagent_timeout→delegate/warn`、`subagent_budget_exhausted→delegate/warn`、`llm_fallback→answer/error`、`llm_failover→answer/warn`、`tool_timeout→tools/warn`、`reply_cleaned→answer/warn`。

**同阶段多条痕迹取最严重**（`error > warn > gray > ok`）。

**用户问题原句**：埋点不落正文（§10），只从 `feedback_content.question`（点踩时捕获）取；取不到时 `question=""`，前端显示「原句不可得」+ traceId，**不伪造**。

Java 侧实现：`AgentClient.metricsGet(path)` 通用透传（限 `/v1/agent/metrics/` 前缀），controller 对 trace_id 做十六进制白名单校验（非法返回 `found:false`，不用 3001——该码在前端语义是确认门）。

参数校验：时间区间最长 90 天；limit 上限 100；`metric`/`groupBy` 白名单枚举，防 SQL 注入（拼接前校验）。

### 7.2 列表分页约定（2026-09-19）

**页面上还有可视化内容占位时，一屏再塞 20 行表格既看不到图表、也让页面重新变回"数据坟场"**。因此每页条数**按页面构成分流**，而不是全局一个默认值：

| 每页条数 | 适用条件 | 页面 |
|---|---|---|
| **10** | 页面除列表外还有 KPI 卡片 / 趋势图 / 条形榜 / 交互区 | 工具调用、智能体委派、故障与降级、反馈与金标集、告警处置、报表导出（口径速查）、**知识缺口** |
| **20** | 页面主体就是这张列表 | 会话明细 |

常量定义在 `utils/metrics.js`：`PAGE_SIZE_WITH_CONTENT=10`、`PAGE_SIZE_LIST_ONLY=20`、`METRICS_PAGE_SIZE_OPTIONS=[10,20,50]`（两档默认值都必须在候选里，否则下拉框显示不出当前值）。

**为什么是前端内存分页而非后端分页**（关键取舍）：

- 知识库页走的是**后端分页**（`page`/`pageSize` → `{total,page,pageSize,totalPages,items}`，见 `api/kb.js` 的 `toPageQuery`）；
- 但 **metrics 系列接口只支持 `limit`、不支持 `page`/`offset`**——`/metrics/chats`(≤100)、`/metrics/tools/top`(默认 10)、`/metrics/feedback`(≤200) 只有条数上限；`delegations`/`faults` 来自 `/metrics/overview` 聚合（固定 `LIMIT 20`/`LIMIT 100`），`/metrics/alarms/link` 固定 `LIMIT 100`，全都没有分页参数。
- 数据量上限明确（最大 100～200 条），**改后端加 page/offset 要同时动 Python SQL、Java 透传与三个接口的契约**，收益不抵成本。故看板统一采用「**一次多取 + 前端切片**」：各页按较大 `limit` 一次拉齐，页面内 `paginate()` 切片渲染，复用知识库页同一套 `PaginationBar` 组件，翻页**零网络请求**。
- 取舍的代价与边界：若某天单窗口数据超过 `limit` 上限，前端分页只能翻到已取回的部分——**届时必须改后端分页**。这是已知边界，不建议在超过上限的数据量下继续用内存分页。

**实现要点**：

- 切片与页数计算收敛在 `utils/metrics.js` 的 `paginate(rows, page, pageSize)`，八个页面共用；它**夹紧页码**（过滤条件变化后原页码可能越界）并保证**空列表也返回 `totalPages=1`**（否则分页条显示"1 / 0 页"）。**不要各页各写一份 `slice()`**——边界会各错一遍。
- 筛选/窗口/刷新导致数据变化时**必须重置回第 1 页**；换每页条数同样回第 1 页。
- 一页有多张表时（告警处置页 3 张）**每张表各自独立翻页**：它们条数不同、阅读顺序不同，共用一个 `page` 会出现"翻告警列表把委派明细也翻走了"的错觉。
- 列表数据源有过滤时（故障页 `pathFilter`、会话页 `intentFilter`/`sessionFilter`），**切片要作用在过滤后的行上**，`totalPages` 才与用户所见一致。

- **验收**：`data_platform_p2_e2e.py` 第 7 节扩展为双表用例（含"未超期行必须保留"的防误删断言），

- **教训关联**：TTL 涉及"删除真实数据行"，验收用例必须同时断言**该删的删掉**与**不该删的还在**
  （本例用"未超期行必须保留"覆盖后者）；只断言前者会把"误删全部"也判为通过。

**B. 看板从「只读观测」到「可发起处置」（B1 方案）**

- **关键发现**：处置工具**早已存在**（`alarm_acknowledge` / `alarm_resolve` / `alarm_ignore`），
  看板此前只能看到「哪条告警被处置了」，却无法发起处置——缺的是最后一段入口。
- **方案 B1（用户拍板）**：看板告警行加「确认/解决/忽略」按钮 → 跳转对话页并预填自然语言消息
  → 由 **既有确认门**（复述对象与影响 → 用户字面确认 → 才执行）完成处置。
- **为什么不选 B2（看板内直接处置）**：写操作必须走 guard.py 确认门，且"确认只认用户下一条字面消息"
  是防注入的关键。在看板内另建一套确认，等于在确认门之外开**第二条写路径**，安全边界分叉——
  与本项目"判定逻辑只许有一份"的一贯教训（见 DEV_ISSUES §6.54/§6.57）同源。
- **前端约定**：预填消息**只填输入框、绝不自动发送**。自动 send 等于替用户点了确认，
  剥夺"看到复述再决定"的机会。预填文本用完即从地址栏清除（`replace`），避免刷新重复填入。
  预填文本长度也截断到 200 字（`slice(0, 200)`），防止把超长文本塞进输入框。
- **B2 明确不做（记录决策而非待办）**：看板内直接处置会在 guard.py 确认门之外开出第二条写路径，
  判定逻辑分叉。本项目此前已有两次同类教训（DEV_ISSUES §6.54 评测断言两套口径、§6.57 净化两套判定），
  结论一致：**同一判定只许有一份实现**。B2 不列为技术债，列为**否决项**（见 §9 反模式清单第 7 条）。
- **顺带修复的真实缺陷**：`alarm_link` 原实现把告警拉取整个挂在 `if times:`（委派时间窗口）之下，
  导致**没有委派记录时，明明系统里还有 pending 告警也返回 0 条**——看板作为处置入口却看不到待处置对象。
  修法：在窗口拉取之外**独立拉一次 `status=pending`**，新增 `source` 字段区分三类来源：
  - `linked`：落在某次委派时间窗内，属**关联分析**结果（可回溯到 trace）；
  - `window`：在窗口时间段内被拉到、但没命中任何委派（时间上相关、因果上未证实）；
  - `pending`：独立拉取的**待处置**告警，与委派无关（B1 处置入口的数据源）。
  `source` 不是展示字段而是**语义字段**：前端据此分组，避免把"疑似被处置过"与"还没处置"
  两类含义不同的行混在一张表里。已在 §5 指标字典登记口径。
- **验收实测**：经 8080 网关走完整链路——看板预填「帮我确认告警 5」
  → Agent 正确判为写操作、复述「执行人 admin / 将执行 确认告警 ID=5 / 10 分钟内有效」
  → 回复「确认」→ 真正调 jsdstu 执行 → **8060 真库告警 5 状态 `pending` → `acknowledged`**（已复核）。
  修复后 `alarms/link` 能看到 `id=1 / P0 / pending` 的待处置告警。
- **⚠️ 本期最大的教训（已升级为操作纪律）**：B1 验收直接改了**真实业务库的告警状态**（告警 5：
  `pending` → `acknowledged`），而 biz 评测集的断言绑定了这些业务数据（"待处理告警有几条"、

## 9. 反模式清单（评审一票否决项）

1. 业务代码里直接写 SQL 查埋点表（必须走 telemetry/查询服务）；
2. 埋点失败重试或阻塞主流程（降级方向只能"丢数据"，不能"卡业务"）；
3. 在 ADS/看板接口里写新业务规则（新指标先进字典，再落 DWS）；
4. 把 prompt/回复原文塞进四表（要内容开独立表+开关+TTL）；
5. 迁移 MySQL 时保留双写超过一个观察周期（双写是过渡态不是稳态）；
6. 看板前端绕过 API 直连明细表；
7. **在看板/其他旁路另建一套写操作确认逻辑**（B2 方案）。写操作只能有一条路径：guard.py 确认门。
   旁路确认 = 安全边界分叉，且判定逻辑出现第二份实现——与 §6.54/§6.57 的教训同源。
8. **用被评测断言引用的真实业务数据做写操作验证**（P2+ 期中招一次，见 §8 教训）。
   要验证写链路，用自建临时对象；用了真实对象就必须在跑回归前还原并复核状态。
