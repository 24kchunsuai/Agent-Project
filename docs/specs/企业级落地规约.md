## §1 为什么在「内部生产」之上还要再定一档

### 1.1 四档口径（把"企业级"从形容词变成位置）

| 档位 | 一句话判据 | 使用方 | 现状 |
|---|---|---|---|
| **L1 演示级** | 自己人点开能看 | 开发者 | ✅ 已达标 |
| **L2 内部生产** | 小团队真用：可信内网、数据不丢、故障有人知道 | 自己团队 | 🟡 S-1 ✅ 2026-09-24；S-2~S-10 未做 |
| **L3 企业级可交付** | **陌生人照手册能部署、坏了能自己修、问得出账** | 企业客户 / 他方运维 | ⬜ **本规约目标** |
| **L4 规模化生产** | 多实例、公网、对 SLA 负责 | 多客户 / 公有云 | ⏸ 只划界（§8） |

### 1.2 L2 → L3 的本质差别是「责任转移」

L2 的隐含前提是「出问题就找作者」；L3 必须做到「**不找作者也能跑**」。三条推论：

1. **判据必须第三方可验证** —— 不是"我觉得稳"，而是别人照着做能得到同样结果。
2. **知识必须外化成手册与自动化** —— 只存在于作者脑子里的运维知识，在企业里等于不存在。
3. **必须留下可追溯的账** —— 出事能复盘到"谁、何时、做了什么"，而不是互相猜。

> 一句话：**L2 是把系统跑起来，L3 是把系统交出去。**

### 1.3 为什么不能先做 E 再回头补 S

S-1（服务间信任边界）没做之前，Python 侧对网络可达者零鉴权、`userId` 由 body 自证——
**在这个状态下谈"部署给企业"，等于把伪造身份的通道一起交付**。
故本规约的推进顺序强制为 **S-1 先行**，其余 S 项与 E 项按依赖融合推进（见 §6）。

## §2 企业级的七条判据（每条都能被外人验）

这七条是 L3 的**验收定义**，不是愿景。每条给出"外行也能验"的方式。

| # | 判据 | 外人怎么验 | 对应任务 |
|---|---|---|---|
| **C1 可交付** | 给一个陌生运维一份交付包 + 手册，他能在干净机器上把系统跑起来 | E-2 · E-14 · E-15 |
| **C2 可复现** | 问他"现在跑的是哪个版本"，答得出；且能从源码重建出该版本 | E-1 · E-4 |
| **C3 可观测** | 造一个故障，他能在 5 分钟内指出是哪个服务的哪一环，而不是翻日志猜 | E-3 · E-6 · E-9 · E-12 |
| **C4 可恢复** | 删掉一份数据，他能从备份恢复；且**这份备份是演练过的**，不是"有脚本" | E-7 |
| **C5 可追溯** | 问"上周三谁停用了那篇文档 / 谁改了配置"，查得到 | E-8 · E-10 |
| **C6 可回归** | 改一处代码，有自动化在 10 分钟内告诉他有没有改坏三端 | E-4 · E-5 |
| **C7 可计量** | 问"这个月大模型花了多少钱、哪个部门用的"，答得出 | E-13 ✅ |

**七条全绿 = L3 达成。** 缺任一条，都还有"必须找作者"的环节。

**口径调整（实施时定，三条）**

1. **Java 自身可达性归 8080 侧，不放 8000 的聚合里。**
   若让 Python 去探 8080，而前端又要经 8080 转发这个接口，就形成 8080→8000→8080
   的**自环**——探自己必然成功，这个指标毫无信息量。改为分层：8000 报"它看得见的"
   （自身/Milvus/四库/scheduler/降级计数/8060），8080 报 `java` 自身 + 转发 8000 的组件。
   于是 **8080 那个端点才是"一个 URL 回答整套系统"**，前端顶栏调它。
2. **`down` 的实际触发路径在 8080 侧。** 8000 能返回就说明进程活着，单点数据依赖失败
   只降级，所以 **8000 侧正常不会返回 `down`**；8080 连不上 8000 时插入一条
   `python-service: down (required=true)`，整体判 `down`——这才是"核心链路不可用"。
   两端 `required` 与归并规则逐字对齐（Java 侧 `OpsServiceImpl.mergeStatus` 复刻同一套）。
3. **鉴权：8000 侧要 key（不放白名单），8080 侧匿名可读。**
   8000 受 S-1 保护的理由：它暴露内部组件拓扑与故障原因，信息量远大于 `/v1/health`。
   8080 侧匿名可读是**有意识的取舍**——状态灯要对所有人可见，而明细已保证不含密钥/token/
   用户数据（只有内网地址、库文件名、任务名）。要收紧就在 `AuthInterceptor` 加一条路径规则。

**其它实现要点**：聚合结果带 **3s TTL 缓存**（防止"看健康的人把被看的服务压垮"）；
SQLite 探针**只读不建库**（文件不存在报 degraded，不在产品目录留任何东西）；
8080→8000 用**独立的 5s 读超时**（`agent.ops-read-timeout`）——业务那 240s 的超时
会让 Python 僵死时状态灯 4 分钟才变红，等于没有告警；8060 探测显式 `trust_env=False` 绕代理。

- [x] 全部正常时 `status=up`，响应 < 2s（实测 8000 侧 335ms / 8080 侧 142ms）
- [x] 单测：mock 依赖失败场景，断言状态与不回抛异常（13 项，`tests/test_ops_health.py`）

```
E-P0+    E-14 容器化（含 S-2 的 nginx 配置）  （1d）
E-P1     E-6 → E-7 → E-9 → E-8              （3d）  E-7 ✅ / E-6 ✅ / E-9 ✅ 2026-09-24
E-P2     E-10 → E-11 → E-12                 （1.5d）  E-10 ✅ / E-11 ✅ / E-12 ✅ 2026-09-24
E-P3     E-14 → E-15                        （1.5d）  E-14 ✅ 2026-09-24 / E-15 ✅ 2026-09-25，**L3 全案收官**
```

> **实际执行顺序与上表有两处出入（据实记录）**：
> ① E-P0 收官后没有先做 E-14 容器化，而是先做了 **E-P1 的 E-7**。理由是 C4（可恢复）是七判据里**缺口最大**的一条
> ——四个 SQLite 库当时**零备份**，属于"多跑一天就多一天不可恢复风险"；
> 而 E-14 是交付形态问题，晚做不影响现有系统的数据安全。E-14 仍按 D1 保留在 E-P0+ 位置。
> ② E-P1 内部也**先做了 E-7、再回头做 E-6**（与规划的 E-6 → E-7 相反）。理由是 E-7 属于"防数据丢失"，
> 时间敏感度高于日志格式；E-6 是**可观测性收口**，早做晚做都不增加新的丢失风险，且需要等 E-3/E-7 的
> 端点与日志面都稳定后再统一字段口径，返工更少。E-P1 四项（E-6 / E-7 / E-9 / E-8）已于 2026-09-24 全部完成。
> ③ E-9 之后按顺序做了 **E-8**（与规划的 E-9 → E-8 一致）。E-8 收尾时把"配置变更"这一项
> 落地为**启动时比对配置指纹**——因为本系统**没有运行时改配置的入口**（配置来自 `.env` /
> `application.properties` + 重启），"配置变过"这件事只有启动那一刻能观测到。
> 这是配置机制的固有边界，已写入 `docs/审计清单.md §10`。

## §9 铁律（新增，与 README §8 叠加）

1. **可验证优先**：任何"已就绪"的结论必须附**第三方能重跑的验证方式**（命令 + 期望输出）；无验证方式的一律视为未完成。
2. **一处配置只写一份**：nginx 配置（S-2/E-14）、审计机制（治理 `audit` 复用）、脱敏（S-8/E-6）、
   判定逻辑（README §8.7）——出现第二份即为缺陷。
3. **fail-closed 只用于鉴权与 preflight**：preflight 失败必须拒绝启动；
   健康聚合 / 指标 / 日志 / 上报类增强，异常一律降级计数，绝不阻断主链路。
4. **交付物不得包含密钥**：`.env`、证书、token 一律不进交付包（`release.sh` 须校验）。
5. **文档与代码同步**：本规约每完成一项，同步更新状态列与 `README.md` §5，并在 `DEV_ISSUES.md` 追加章节。
6. **8060 jsdstu-3 只包装不改**（既有铁律，不变）。
7. **git 提交等用户明确开口**（既有约定，不变）。
