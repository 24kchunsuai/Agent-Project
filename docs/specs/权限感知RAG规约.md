# 权限感知 RAG 规约（多部门 / 多等级文档访问）

> 版本：v1.0 ｜ 日期：2026-09-20 ｜ 状态：待评审（**仅设计，未立项**）
>
> 立项条件：出现真实的多部门文档需求（本节防过度设计）。立项前本文档只作为方案存档。
> 讨论背景：2026-09-20 深夜方案讨论，源于"部门 / 等级 / 交接 / 密级变更"四类权限场景。

## 1. 目标与非目标

**目标**：不同部门、不同等级员工检索到不同结果；人员换部门 / 升降级、文档交接、
密级变更三类变更即时生效且不漏改。

**非目标**（立项时也不做，防过度设计）：
- 字段级 / 行级细粒度权限（只做到文档级 chunk 可见性）
- 权限申请审批流（走线下 / HR 系统口径）
- 历史会话中已回答内容的撤回（已发生的阅读无法撤回，审计可查即可）

## 2. 核心决策

### 2.1 权限真源在业务库，向量库只管语义 ⭐

`doc_permissions(doc_id, dept, min_level, updated_by, updated_ts)` —— **每篇文档一行**。
主键 doc_id；dept = 归属部门；min_level = 可见最低等级。

- Milvus 元数据中的权限字段（owner/visibility 保留，作为兜底标记）**不再承担判定职责**
- 权限的增删改查全部是普通 SQL，不碰向量库
- 入库流程**同事务**写权限行（见 §5 一致性）

### 2.2 存"文档属性"，不存"部门→文档列表"（反向表，勿改成正向）

正向表 `(dept, level) → doc_id 列表` 是物化了规则的计算结果——**规则一变要重算全表**，
且行数 = 部门×等级×文档（爆炸）。反向表存属性，规则永远查询时现算，
规则变化只改代码、表零动作，行数 = 文档数。

### 2.3 判定规则（查询时实时计算）

```
可见 ⇔ (doc.dept == 用户当前部门) AND (doc.min_level <= 用户等级)
```

- 用户属性（当前部门、等级）**每次查询实时读取**，不缓存进会话/画像
- 等级映射为密级档（公开/内部/秘密…），升降级自动生效
- 例外规则（如"某类文档全公司可见"）以规则代码表达，不物化进表

## 3. 查询链路

```
1. 读用户属性（部门、等级）——实时，禁止用画像/会话里的旧值
2. SELECT doc_id FROM doc_permissions WHERE dept = ? AND min_level <= ?
3. Milvus 检索 expr = "doc_id IN [列表]"，带 overfetch（候选 = topk × 3）
4. 过滤后不足 topN → 分批 IN 扩大候选补拉
5. 证据全被挡 → 回答"您没有该文档的权限"，不得伪装成"知识库没有相关内容"
```

- **过滤必须在 Milvus 服务端做**（expr），禁止检索完在应用层删
- **拒绝 ≠ 不存在**：权限不可见要如实说无权限，否则越权被伪装成查无此料
- 拒绝查询必须记埋点（agent_chat_log 加权限判定结果列），高频撞墙
  = 权限配置错误或试探爬库，复用 M-4 埋点闭环出看板

## 4. 三类变更的处理（不对称规则）

| 变更 | 动作 | 生效时机 |
|---|---|---|
| 员工换部门 / 升降级 | 改用户属性一条记录，文档零动作 | 下次查询 |
| 文档交接给 B 部门 | UPDATE 权限行 dept 字段（不重嵌入） | 立即 |
| 密级变化 | UPDATE min_level + 失效相关查询缓存 | 立即 |

**不对称规则**：放宽（降密/扩权）零清理；**收紧**（升密/交接走人）才需处理泄漏面——
查询缓存键必须含用户属性（或按 doc 维度失效）；历史会话已答内容接受不撤回、审计可查。

## 5. 一致性与对账（必须，不是可选）

1. **同事务双写**：知识库入库接口在处理函数内同步写 doc_permissions，禁止异步补写
2. **孤儿对账**：巡检新增一类比对——"向量库有、权限表无"的孤儿 chunk；
   复用现有治理巡检框架（inspection_service），发现即开工单
3. **fail-closed 铁律**：权限表无记录的文档一律视为不可见（默认拒绝），
   绝不"查不到权限就放行"。此条与全链路容错规约的 fail-closed 口径对齐
4. 指针型泄漏：引用/工单里出现的 doc_id 引用，在用户无权限时同样按 §3.5 拒答

## 6. 规模边界与升级路径

| 可见文档规模 | 方案 |
|---|---|
| 单部门 ≤ 1 万 | 本规约方案（业务库算列表 + Milvus IN） |
| IN 列表过万变慢 | 分批 IN + overfetch 补拉（过渡） |
| 更大规模 | 属性下推 Milvus 标量过滤（dept/level 进 Milvus 元数据，ABAC 全下推）——检索免一次 SQL，但权限变更回到"改向量库元数据"，是本规约方案的置换而非推翻 |

## 7. 立项时的落地改动路径（四步，全在现有骨架上生长）

1. chunker 元数据补 `dept / classification`（入库时定，沿 owner/visibility 同路）
2. 新增 doc_permissions 表 + 入库同事务写入 + 孤儿巡检项
3. 用户模型加部门/密级属性（Java 侧透传给 Python，沿用身份注入链路）
4. 检索层加 expr 过滤 + overfetch + 拒绝语义 + 埋点列

## 8. 验收标准（立项时启用）

- 换部门 / 交接 / 升降级三类变更后，下一次查询结果即符合新权限（秒级）
- 权限表无记录的 chunk 在任何检索路径（含混合检索双路）都不可见
- 证据全被挡时回答"无权限"而非"无资料"；拒绝有埋点
- 孤儿 chunk 巡检可检出并开工单；规则变化不改表
