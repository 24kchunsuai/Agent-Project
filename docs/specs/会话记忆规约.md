# 会话记忆规约：持久化、裁剪与相关性过滤

> 版本：v1.1 ｜ 日期：2026-09-19 ｜ 状态：已落地（M-1~M-5 全部完工；完工检查与验收遗留见 DEV_ISSUES §6.70）
> 范围：`agt_python` 会话记忆（`app/services/memory.py` + 读取/写入调用点）
> 依据：`AgentCraft` 与 `open-agent-master` 记忆设计对比结论（本文 §2/§3）
> 第一目标：**重启不丢记忆、兜底文案不中毒、长会话不炸窗口**——先补可靠性，再谈语义增强。

---

## §1 为什么需要这份规约

现状是一份 66 行的内存版实现（`SessionMemory`：内存 dict + 两个上限 + 滑动窗口），
只覆盖了参考项目 5 层记忆中的第 1、2 层。三轮实测暴露出的具体症状：

1. **重启即失忆**。`uvicorn --reload` 一次、或改配置重启服务，全部会话历史归零。
   用户上一轮说的"3 号无人机""刚才那个任务"下一轮模型完全不知道。
2. **长会话上下文污染**。`window=10` 是**纯尾部窗口**：会话聊到第 20 轮时，开头的
   "我是 XX 公司的巡检员、只负责 3 号机"已被挤出窗口，模型开始给出不针对该用户的通用答案。
3. **跨话题串味**。用户先聊"炸机处置"，再问"实名登记"，前 10 条里混着大量炸机内容，
   既浪费 token 又干扰判断（open-agent 把这叫"上下文污染"，有专门设计文档）。
4. **无法回答"这一轮用了哪几条历史"**。数据中台 v5 会话详情弹窗已能还原 7 段链路，
   但记忆段是空的——因为记忆没有埋点。
5. **多轮改写的输入质量无约束**。P0 的 `rewrite_query(question, history)` 直接吃
   `session_memory.get()`，而这份历史**包含兜底文案以外的所有内容**，且没有相关性筛选。

本规约把"存什么、存哪、给多少、怎么挑、怎么观测"一次定清，作为后续实现与 e2e 的依据。

## §2 参考来源与取舍

| 来源 | 取什么 | 不取什么 |
|------|--------|---------|
| `open-agent-master/server/.../memory/MemoryService.java` | 内存+文件双写、**增量基准自维护**（不依赖索引统计）、三条件 OR 触发同步（token/轮次/时间）、`@PreDestroy` 关停冲刷、启动回放预热 | 无 |
| `open-agent-master/server/.../memory/FileMemoryStore.java` | 日期滚动 + 大小拆分、**滚动后同步修正索引文件名**、LRU 读缓存、"索引脏了不影响正确性"的防御 | `memory.md` + `.idx` 的文件形态（本项目改用 SQLite，复用 `observability.db` 那套建表/迁移模式，省掉索引一致性与文件锁） |

| `open-agent-master/server/.../memory/HistoryFilter.java` | 5 步流水线结构、**以"轮"为最小过滤单位**、按原始时间序重建、相似度阈值归零防低分堆叠、详尽分步日志 | **关键词打分项（`KEYWORD_PATTERN` 无中文分词，整段中文被当作一个 token，0.3 权重在中文下接近噪声）**；要用必须降权或接中文分词 |
| `AgentCraft/python-service/agent/memory_agent.py` | **记忆作为编排内的显式节点**（`StepType.MEMORY_READ/WRITE`，可观测/可跳过/可单测）、记忆写回 `state.context` 供后续步骤消费 | 无 |
| `AgentCraft/python-service/tools/memory_read.py` | 超阈值时"摘要 + 最近 N 轮"的组合返回结构 | `COMPRESS_THRESHOLD`/`KEEP_RECENT` 魔数重复定义在两处且语义冲突（超阈值反而少给一半）、无配置项可调 |

**一句话结论**：主骨架抄 open-agent（落盘 + 双锚点裁剪 + 相关性过滤），编排形态抄 AgentCraft（记忆节点显式化 + 用户画像），**存储介质换成 SQLite**（复用现有基础设施）。

### 4.2 缺口清单（本规约要补的，按危害排序）

| 编号 | 缺口 | 危害 | 期 |
|------|------|------|-----|

## §5 数据与接口契约

### 5.1 存储介质：SQLite（复用 `observability.db` 模式）

沿用 `TelemetryStore` 已验证的三件事：建表 + 迁移（`ALTER TABLE ... ADD COLUMN` 容错）、
后台批量落库（间隔可配）、启动时幂等初始化。**不新增外部依赖**（不用 Redis/MySQL）。

```sql
-- 表 1：会话消息（append-only）
CREATE TABLE IF NOT EXISTS agent_memory_message (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT    NOT NULL,
    user_id     TEXT    DEFAULT '',
    role        TEXT    NOT NULL,          -- user / assistant
    content     TEXT    NOT NULL,
    turn_index  INTEGER NOT NULL,          -- 轮次序号，从 0 开始；同轮 user/assistant 相同
    ts          INTEGER NOT NULL,          -- epoch 秒
    persisted   INTEGER DEFAULT 1          -- 0=不入历史（占位/仅存档），见 §6.2
);
CREATE INDEX IF NOT EXISTS idx_mem_session_ts ON agent_memory_message(session_id, ts);

-- 表 2：会话摘要（压缩产物，每会话一行）
CREATE TABLE IF NOT EXISTS agent_memory_summary (
    session_id   TEXT PRIMARY KEY,
    summary      TEXT NOT NULL,            -- 累积摘要（递归压缩）
    covered_turn INTEGER NOT NULL,         -- 摘要覆盖到第几轮（不含）
    updated_ts   INTEGER NOT NULL
);
```

**保留策略（TTL，对齐数据中台规约 §4.2 的思路）**：
- 会话消息默认保留 **30 天**（`memory_ttl_days=30`），每天清理一次；
- 会话数上限沿用 500（超出淘汰最久未访问的会话，会话级而非消息级）；
- **清理必须走产品内定时任务**，不得手工删文件（对齐用户铁律：不擅自清理数据目录）。

### 5.2 `MemoryStore` 接口（存储可替换，调用方不感知）

```python
class MemoryStore(Protocol):
    def get(self, session_id: str) -> list[dict[str, str]]: ...
    def append(self, session_id: str, role: str, content: str) -> None: ...
    def record_turn(self, session_id: str, user_message: str, assistant_reply: str) -> None: ...
    def stats(self) -> dict[str, int]: ...
    def flush(self) -> None: ...                      # 冲刷待落盘增量（M-1）
    def load_all_session_ids(self) -> list[str]: ...  # 启动回放预热（M-1）
```

**关键约束：`agent_service` 只依赖这套接口，切换实现（内存 → SQLite）不改调用点。**
这是现状代码已经写好的设计（`memory.py` 头注释第 6-8 行），本规约只是把它兑现。

### 5.3 新增配置（`app/core/config.py`，同时同步 `.env.example`）

```python
# ---------- 会话记忆（docs/specs/会话记忆规约.md）----------
memory_store: str = "sqlite"              # memory(内存) / sqlite；降级开关：sqlite 异常自动回退内存
memory_ttl_days: int = 30                 # 会话消息保留天数
memory_max_sessions: int = 500            # 会话数上限（沿用现值）
memory_sync_round_threshold: int = 10     # 增量落盘：累计轮次阈值（M-1）
memory_sync_interval_seconds: int = 60    # 增量落盘：最长间隔（M-1）
memory_token_budget: int = 3000           # 单次注入历史的 token 预算（M-2）
memory_head_turns: int = 2                # 头部锚点轮数（保留会话开头的身份/约束）
memory_tail_turns: int = 6                # 尾部保留轮数
memory_summary_min_turns: int = 8         # 触发摘要的最小轮数（M-2）
memory_filter_enabled: bool = True        # 相关性过滤总开关（M-3）
memory_filter_min_turns: int = 8          # 少于该轮数不触发过滤（短会话过滤无收益）
memory_filter_top_k: int = 6              # 过滤后最多保留轮数
memory_filter_similarity_weight: float = 0.9   # 相似度权重（关键词权重 = 1 - 此值）
memory_filter_min_similarity: float = 0.35     # 低于此相似度直接归零
memory_filter_min_score: float = 0.2           # 综合分阈值，不达标不保留
```

> **为什么 `memory_filter_similarity_weight` 默认 0.9**：open-agent 用 0.3/0.7，
> 但其关键词项在中文下**无分词**（`[\\u4e00-\\u9fa5]{2,}` 会把"无人机飞行高度限制"
> 整体当成一个 token），0.3 的权重接近噪声。本项目先按 0.9（关键词仅占 0.1）保守起步，
> **待 M-3 实测数据回来后**再决定是否接中文分词并提权（见 §8 开放问题 1）。

## §6 分期任务与验收标准

### M-1 持久化 FileMemoryStore（P1，最小可用）— G10

**改动点**
- [ ] 新建 `app/services/memory_sqlite.py`，实现 §5.2 接口；`SessionMemory` 保留为内存实现
- [ ] `memory.py` 增加工厂 `get_memory_store()`，按 `settings.memory_store` 返回实例；模块级仍暴露 `session_memory` 名以兼容调用点
- [ ] **增量同步基准自维护**：每会话维护 `synced_turn`（已落盘轮次），**不依赖 SQL 聚合统计**
      ——open-agent 的注释指出过真实坑：索引计数与文件实际不一致时会误判"无增量"导致永不写入
- [ ] 三条件 OR 触发落盘：`累计轮次 ≥ memory_sync_round_threshold` **或** `距上次落盘 ≥ memory_sync_interval_seconds`
- [ ] 启动时回放：`load_all_session_ids()` → 逐会话加载最近 N 轮到内存（**N = head + tail + filter_top_k**，不必全量）
- [ ] 关停冲刷：`app/main.py` 的 `lifespan` 关闭阶段调 `flush()`（现有钩子已存在：
      `await telemetry.stop()` / `scheduler.stop()` / `llm_client.close()` 之后追加一行），
      保证未达阈值的增量不丢
- [ ] **降级路径**：SQLite 打开/写入异常 → `logger.warning` + `telemetry.record_fault(PATH_MEMORY_SQLITE_DEGRADED)` + 自动切内存实现，**主链路绝不因记忆故障中断**

**验收标准**
- [ ] 单测 `tests/test_memory_store.py`：存入 → `flush()` → 新建实例（模拟重启）→ `get()` 内容与顺序一致
- [ ] 单测：未达阈值时 `flush()` 仍能落盘（关停路径）；达阈值时自动落盘
- [ ] 单测：`synced_turn` 与 DB 实际行数不一致时，仍能正确识别增量（回归 open-agent 的坑）
- [ ] 单测：SQLite 路径不可写 → 不抛异常、主链路照常返回、`fault_event` 有一条 `memory_sqlite_degraded`
- [ ] e2e：多轮对话跑完 → 重启 `agt_python` → 追问"我上一轮问的是什么" → 能答对
- [ ] **人工确认**：重启后弹窗"执行流程"里记忆段能显示历史条数

### M-2 token 计量 + 双锚点裁剪（P1）— G11 / G12

**改动点**
- [ ] 新增 `TokenEstimator`（`app/services/memory_token.py`）：优先 tiktoken（若已装），
      否则用保守估算 `中文 1 字 = 1 token，英文 4 字符 = 1 token`，并**乘安全系数 1.2**（对齐 open-agent 承认的 ±20% 误差，但方向取保守）
- [ ] 窗口从"条数"改为"**token 预算**"：`_build_history` 按预算装配，不再固定 `window=10`
- [ ] 裁剪策略改为 **头部锚点 + 尾部保留 + 中间摘要**：
      - 头部：最近会话开头的 `memory_head_turns` 轮（承载身份/约束）
      - 尾部：最近 `memory_tail_turns` 轮（承载当前话题）
      - 中间：**仅在超预算时**压成摘要（`memory_summary_min_turns` 条数门槛 + 中间占总量 ≥ 30% 的占比门槛，双条件）
      - 递归：新摘要的 prompt 里带上旧摘要，`agent_memory_summary.covered_turn` 记录覆盖边界
- [ ] **裁剪后追加系统提示**："（对话历史较长，早期部分已自动压缩为摘要）"——成本近零，防模型基于残缺历史编造
- [ ] 摘要生成失败 → 降级为**直接丢弃中间段**（不阻断），`logger.warning`

**验收标准**
- [ ] 单测：构造 50 轮、每轮 500 字的历史 → 装配后 token 数 ≤ `memory_token_budget`
- [ ] 单测：头部锚点轮**必须保留**（断言第 0、1 轮内容出现在结果中）
- [ ] 单测：未超预算时**原样返回、不触发摘要**（不白花 LLM 调用）
- [ ] 单测：中间占比 < 30% 时不摘要；LLM 摘要抛异常时结果仍非空且含头部+尾部
- [ ] 单测：连续两次超限触发压缩时，第二次摘要 prompt 包含第一次摘要内容（递归）
- [ ] 实测：`questions.jsonl` 全量评估跑通，**hit@1 / hit@3 不得低于 M-2 之前基线**

### M-3 相关性过滤（P2）— G13

**改动点**
- [ ] 新建 `app/rag/history_filter.py`，实现 5 步流水线：**指代消解 → 轮次分组 → 相关性打分 → topK 筛选 → 按时间序重建**
- [ ] **复用 P0 已有的短查询判定**：`app/rag/rewrite.py:128 _needs_llm()` / `:49 _PRONOUNS`
      的判据直接用于"是否需要指代消解"，**不允许两套阈值**
      （P0 用 `_normalize(q) <= 12`（`:133`）、open-agent 用 `len < 10`，必须统一为一个常量）
- [ ] 打分 = `相似度 × memory_filter_similarity_weight + 关键词命中率 × (1 - weight)`
      - 关键词：**若采用则必须接中文分词**（优先复用 BM25 侧已有 tokenizer）；暂缺则可先只跑相似度项（权重设 1.0）
      - 相似度：复用 `glm.embed_query` + 历史向量缓存；**低于 `memory_filter_min_similarity` 归零**（防低分堆叠挤占 topK）
- [ ] **轮次不够 `memory_filter_min_turns` 时直接返回全量**（短会话过滤无收益，白付 embedding 成本）
- [ ] 历史向量缓存的写入**必须异步或批量补算**，不得放在 `save()` 主链路同步阻塞
      （open-agent 是同步阻塞 HTTP，本项目避免）
- [ ] 与 P0 改写的职责边界：**改写层负责"把查询规范化给检索用"；过滤层负责"挑相关轮次给生成用"**，
      输入同为 history，输出不同用途，共享同一个短查询判定

**验收标准**
- [ ] 单测：10 轮混合话题历史 + "实名登记"查询 → 断言选中轮次**不含**炸机话题轮次
- [ ] 单测：轮次数 ≤ `memory_filter_min_turns` 时返回全量且**不调用 embedding**
- [ ] 单测：结果消息**保持原始时间升序**（不是按分数排序）
- [ ] 单测：轮内 user 与 assistant **成对保留**，不出现"有问无答"断头上下文

## §8 开放问题（需拍板）

1. **中文关键词分词**：M-3 的关键词项，是接 BM25 侧已有 tokenizer（推荐，一致性最好），
   还是先按相似度单权重（1.0）跑、拿到实测数据再决定？**倾向后者先跑**——P0 的教训是
   "词典/规则不是越全越好"，没有实测支撑的权重调整容易做负功。
   > **落地备注（2026-09-19，M-3 时核实）**：BM25 中文分词在 **Milvus 服务端**
   > （`vector_store.py` 的 `analyzer_params={"type":"chinese"}`），Python 侧没有可复用
   > 分词器，且不为此新增 jieba 依赖（§5.1 不新增外部依赖）→ 已按"先只跑相似度（权重
   > 1.0）"实施；`memory_filter_similarity_weight=0.9` 配置保留，接分词后启用关键词项。
2. **`window=10` 是否保留为上限**：改为 token 预算后，条数上限仍需要一层保护（防 100 条超短消息）。
   建议保留为硬上限（`min(条数上限, token 预算)`）。
3. **摘要的持久化**：`agent_memory_summary` 是否随消息一起 TTL 清理？
   倾向**不清理**（摘要体积小、清掉会导致重建成本，且重建后信息更少）。
4. **P0 多轮改写是否改用过滤后的历史**：改写需要的是"最近上下文"（尤其是紧邻前一轮），
   过滤后可能把紧邻轮次筛掉。**建议改写仍用未过滤的尾部窗口，过滤只服务生成**。此项须在 M-3 落地时验证。
   > **落地备注（2026-09-19，M-3 已按此实施）**：改写层走 `_raw_history`（全量、未裁剪、
   > 未过滤）；相关性过滤只服务生成（`_build_history`），并有接线单测锁住"改写层全量"口径。

## §9 铁律（与全链路容错规约 §9 对齐）

1. **记忆故障绝不中断主链路**：落盘失败、embedding 失败、摘要失败，一律降级 + 计数 + WARN。
2. **兜底文案不入历史**（已实现，禁止回退）：`fault.py` 哨兵常量全等比对，宁缺毋滥，不做模糊匹配。
3. **降级必须计数**：每个新增降级点必须有对应 `PATH_MEMORY_*` 常量，不允许静默 `except: pass`。
4. **不擅自清理数据**：TTL 清理只能由产品内定时任务执行；排查时以只读为主，不靠"造文件/删文件"推进。
5. **判定以代码为准**：本文档写的每个"已有/缺失"，实现前必须**回代码核对**——
   本文 §4.1 的纠偏记录就是这么发现的（G5 已实现却被误判为缺口）。
