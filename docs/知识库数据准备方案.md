# RAG 知识库数据准备方案

> 时间：2026-09-16
> 前置决策：embedding 与 reranker 均选智谱 GLM（`embedding-3` + `rerank` API）；向量库 Qdrant 1.11.4（本地 Docker，6333 端口已验证）；RAG 服务用 Python 搭建
> 本文档只做数据规划，不含代码实现

---

## 一、核心结论：培训班项目没数据，就自己建三层语料

「没有数据」不是阻塞项，反而是一次机会——**数据质量我们自己说了算**。建议按三个来源建语料，优先级从高到低：

### 第 1 层：自己的 drone 项目文档（最现实，先做）

您昨天完成了无人机项目，它自带一批真实文档——**这就是第一批知识库数据**：

| 文档类型 | 内容举例 | 来源 |
|---|---|---|
| 项目 README / 部署文档 | 环境搭建、启动步骤、端口配置 | 项目仓库里已有 |
| 接口文档 | 无人机控制 API 的路径、参数、返回值（如起飞/降落/航点） | 代码注释 + 导出 |
| 硬件说明 | 机型参数、传感器、电池/续航、遥控器配对 | 项目资料或手写 |
| 操作手册 | 起飞前检查清单、故障排查、常见错误码 | 手写或 LLM 辅助整理 |

**为什么先做这层**：零版权问题、内容最贴合真实业务（问答效果立即可验证）、而且"自然语言控制无人机"那条业务线也需要这些文档做底座——两个业务线共用一份语料。

### 第 2 层：公开权威资料（补领域广度）

| 资料类型 | 具体来源 | 说明 |
|---|---|---|
| 法规文件 | 《无人驾驶航空器飞行管理暂行条例》（2024-01-01 施行）、CCAR-92 部 | 政府公文无版权问题；法规问答是高频真实需求 |
| 厂商公开文档 | DJI 官网的产品规格页、安全指南（网页可另存为 md） | 仅个人学习项目内部使用，**不要二次分发** |
| 百科/科普 | 无人机分类（多旋翼/固定翼）、飞控原理、空域划分 | 维基百科等，补基础概念 |

### 第 3 层：LLM 辅助生成 FAQ（补密度，必须标注来源）

- 用 GLM/DeepSeek 从第 1、2 层文档生成问答对（一篇文章抽 5~10 个 QA）
- **每条标注 `source: synthetic`**，与真实文档严格区分
- 生成后人工抽检 20%，错的删
- ⚠️ **评估集的绝不能从 FAQ 生成种子来**（否则是自我抄袭，评估虚高）——评估问题要么手写，要么找真人问

### 不要做的事

- ❌ 不爬知乎/CSDN 文章（版权 + 质量参差 + 广告噪音）
- ❌ MVP 阶段不追求大而全（几千篇低质文档不如 50 篇高质量）
- ❌ 不用纯英文语料（中文场景下切片和检索行为完全不同）

## 二、格式与元数据规范（现在定，避免入库后返工）

### 格式：Markdown 优先

- 所有原始文档统一转成 `.md`（PDF 用工具转后**必须人工校对表格**）
- 切片器会按标题层级切，所以**每篇文档必须有清晰的 `#` / `##` / `###` 层级**
- 一篇文档 500~3000 字为宜；超长的拆成多篇

### 每篇文档带 frontmatter（入库时变成 Qdrant payload）

```markdown
---
doc_id: uav-manual-001          # 全局唯一，格式：{分类}-{短名}-{序号}
title: M350 RTK 起飞前检查清单
category: manual                # manual | faq | regulation | project-doc
source: dji                     # dji | caac | self | synthetic
version: v1.0
updated: 2026-09-16
owner: default                  # 预留用户隔离字段（后续做 per-user 知识库）
---
正文……
```

**`owner` 字段现在就带上**——之前评审确认过"知识库用户隔离"是两家参考项目的共同空白，字段从第一天进 payload，比以后迁移数据便宜得多。

### 目录约定（agt_python 下）

```
agt_python/data/kb/
├── raw/            # 原始文档（markdown，带 frontmatter）
│   ├── manual/     # 产品/操作手册
│   ├── regulation/ # 法规
│   └── project/    # 自己的项目文档
├── faq/            # 问答对（jsonl，每行一条 QA + 来源标注）
└── eval/           # 评估集
    ├── questions.jsonl    # 评估问题 + 期望命中的 doc_id
    └── golden_chunks.jsonl # 人工标注的相关片段（阈值标定用）
```

## 三、MVP 规模目标

| 项 | 目标 | 说明 |
|---|---|---|
| 文档数 | **30~50 篇** | 每篇 500~3000 字 |
| FAQ 条数 | 100~200 条 | synthetic 为主 |
| 预计 chunk 数 | 300~800 | 600 字/片、80 重叠估算 |
| 主题覆盖 | 5 类 | 操作流程 / 参数规格 / 法规 / 故障排查 / 项目接口 |
| 评估问题 | **50 个** | 见下 |

**主题多样性比数量重要**——特意保证五类主题都有，否则检索质量的评估结论会被单一主题绑架。

### 评估集 50 问的构成（与阈值标定同步做）

| 类型 | 数量 | 用途 |
|---|---|---|
| 可答（知识库内有答案） | 40 | 测召回/生成质量 |
| 其中 10 个换说法 | — | 同一知识点用口语/术语两种问法，测鲁棒性 |
| 边界（知识库只覆盖一半） | 5 | 测"部分回答"的诚实度 |
| 超纲（知识库完全没有） | 5 | 测**空召回兜底**——必须如实说不知道 |

每条记录：`question / 期望命中的 doc_id / 期望相关片段 / 问题类型`。这份文件就是之前评审里说的「检索层评估数据集」，rerank 阈值标定、混合检索收益对照全靠它。

## 四、执行清单（按顺序）

1. **收集第 1 层**：从 drone 项目仓库导出 README/接口文档/部署文档，转成 md + frontmatter（半天）
2. **手写 10~20 篇**核心手册：起飞检查、常见故障、参数表（1~2 天，可让 LLM 起草、您校对）
3. **收集第 2 层**：下载条例全文（gov 官网）、抓 3~5 个 DJI 规格页（半天）
4. **生成 FAQ**：对已有文档跑 LLM 生成，人工抽检（半天）
5. **写评估集 50 问**：边写边标 doc_id（半天）
6. **交叉校验**：每篇文档检查标题层级、frontmatter 完整性、超长文档拆分

总计约 2~3 天，做完即可进入 M6 的 spec（解析 → 切片 → embedding → 入库 Qdrant）。

## 五、为 Qdrant 提前想好的三件事（写 spec 时用）

1. **中文 BM25**：Qdrant 的 sparse vector 不带中文分词，混合检索的词法通路需要 jieba 分词后自己算 sparse embedding（或先砍掉 BM25，纯向量起步——M6 先纯向量也符合之前定的"先闭环再加深"节奏）
2. **payload 过滤**：`category` / `owner` / `source` 三个字段建索引，检索时按 owner 过滤实现隔离
3. **标量量化**：50 篇文档规模用不上，等 chunk 上万再开 int8 量化，现在不用管

## 七、实际交付情况（2026-09-16 已完成）

### 7.1 语料落地位置

```
agt_python/data/kb/
├── raw/
│   ├── regulation/    7 篇  法规类（分类标准、实名登记、执照、空域、申请、保险处罚、禁止行为）
│   ├── manual/       10 篇  操作手册（检查清单、起降、飞行模式、电池、指南针IMU、返航、故障、图传、相机、应急）
│   ├── drone-models/  3 篇  机型参数（Mini 系列、Mavic 系列、选型指南）
│   └── project/       5 篇  项目文档（架构、接口、响应码、部署、踩坑记录）
├── faq/faq.jsonl     72 条  问答对（合成，均标注 from_doc 溯源）
└── eval/questions.jsonl 50 条  评估集
```

### 7.2 规模统计

| 项 | 数量 | 字符数 | 预估 chunk |
|---|---|---|---|
| 原始文档 | 25 篇 | 43,048 | 约 82 |
| FAQ | 72 条 | 18,154 | 72（每条一片） |
| **合计可入库** | — | **61,202** | **约 154** |
| 评估集 | 50 条 | 14,573 | 不入库 |

### 7.3 评估集的分支覆盖设计 ⭐

评估集刻意**不采用「召回 4 条高相关 → 评估通过 → 生成」的顺利路径为主**，50 条中仅 8 条（16%）是基准顺利路径，其余 42 条覆盖各类异常与边界：

| 类型 | 条数 | 覆盖的设计分支 |
|---|---|---|
| answerable_direct | 8 | 基准路径（对照组） |
| answerable_paraphrase | 8 | 口语化/同义替换，测语义检索鲁棒性 |
| multi_hop | 6 | 跨文档综合（分类+执照+保险等组合推理） |
| partial_coverage | 5 | 知识库只覆盖一半 → 测「部分回答 + 诚实说明缺口，不编造」 |
| out_of_scope | 5 | 完全超纲 → 测空召回硬兜底（不得退回模型记忆瞎答） |
| threshold_boundary | 5 | 分数落在中间地带 → 测低分噪音不进入生成 |
| hard_retrieval | 5 | 抽象表述、错别字、超短查询、口语术语 → 测 Query 改写/重试 |
| chitchat_route | 5 | 闲聊类 → 测不进入检索链路（省成本） |
| control_intent | 3 | 高危控制指令 → 测二次确认；含**反向用例**（「起飞流程是什么」绝不能被误判为控制） |

关键分布：

- 期望命中程度：`high` 20 条 / `medium` 13 条 / `none` 12 条 / `partial` 5 条 —— **60% 的样本不是高分命中**
- 期望路由：`rag` 38 / `chitchat` 8 / `rag_then_fallback` 2 / `control_confirm` 2

**两个精心设计的对照用例**：

- `eval-048`「帮我起飞」 vs `eval-049`「起飞流程是什么」——前者必须走确认流程，后者必须走知识问答且**绝不能触发控制动作**。这是代价不对称里最危险方向的守门测试
- `eval-040`「无人机黑飞会有什么后果」——「黑飞」是口语术语，法规原文用的是「未经批准在管制空域内飞行」，字面零重合，专门用来验证 Query 改写/重试分支是否真的生效

### 7.4 校验工具与结果

新增 `agt_python/scripts/validate_kb.py`，校验三项：

1. `raw/` 文档的 frontmatter 必填字段完整性与 `doc_id` 唯一性
2. `faq.jsonl` 的 JSON 合法性、`from_doc` 是否都指向真实存在的文档
3. `questions.jsonl` 的 JSON 合法性、`expected_doc_ids` 引用完整性、类型分布统计

**运行结果：0 错误**（25 篇文档 / 72 条 FAQ / 50 条评估集全部通过引用完整性检查）。

### 7.5 已知局限（重要）

1. **规模偏小**：约 154 个 chunk，而 M6 设计的召回 topK 是 20。候选池偏小会让召回指标**偏乐观**——20/154 的采样比例下，几乎每篇文档都能被覆盖到。**建议后续扩充到 300+ chunk 再定检索参数**，否则标定出的阈值在真实规模下会失效
2. **机型参数覆盖窄**：只有 Mini 与 Mavic 系列，行业机型（Matrice 等）仅有概述。评估集 `eval-025` 专门用于验证「参数未收录时不编造」
3. **法规时效性**：引用的是 2024-01-01 施行的《无人驾驶航空器飞行管理暂行条例》与 CCAR-92 部。法规会更新，**语料需要标注版本并定期复核**
4. **FAQ 为合成内容**：基于已核实文档生成，人为抽检建议在正式评估前补一轮（重点看答案是否与源文档一致）

### 7.6 下一步（M6）

语料已就绪，可以进入 M6 的 spec 编写：解析 → 切片（标题感知 + 中文分隔符递归 600/80）→ GLM embedding-3 向量化 → 入 Qdrant → 检索 + GLM rerank → 按之前评审的三件套过滤 → 分级充分性判断 → 生成。

评估集与校验脚本都已就位，M6 每完成一步都可以立刻用 `questions.jsonl` 跑一遍基线，量化收益。
