# drone-agent001 日志规范

> 版本：v1.1 ｜ 日期：2026-09-25 ｜ 对应规约：`docs/specs/企业级落地规约.md` **E-6**（判据 **C3 可观测**），并收口 **S-8（PII 脱敏）**
>
> **本规范要回答四个问题**：日志长什么样、写到哪里、怎么按一次请求串起来、哪些东西绝不能写进去。
>
> E-6 的验收原话是：**"按 `traceId` 一次 grep 能串起三端同一请求；日志文件不会无限增长。"**
> 所以本文件里的每条字段名与每个文件名，都是**两侧代码照此实现**的契约——
> 改字段名要同时改 `agt_python/app/core/logging_setup.py`、`agt_backend/.../base/log/JsonLogLayout.java` 和本文件。

---

## §1 一条日志长什么样

**结构化日志（机器读、按 traceId 查）**——应用自己写，一行一条 JSON：

```json
{"ts":"2026-09-24T12:40:01.123+08:00","level":"INFO","service":"agt_backend","traceId":"8f3c1a92d47b05e6","userId":"1","event":"http.request","durationMs":57,"msg":"POST /v1/agent/chat -> 200","err":""}
```

**控制台日志（人读、看启动过程）**——同一事件，人读格式，被计划任务重定向进 `.log`：

```
12:40:01.123 INFO  c.t.a.agent.client.AgentClient - POST /v1/agent/chat -> 200
```

**为什么两套**：排障时"按 id 精确串链路"和"肉眼扫一遍看哪儿断了"是两种动作。
JSON lines 机器好处理但人读累；控制台人读舒服但没法精确过滤。两者都留，但**只有 `.jsonl` 是可查询的口径**（§4）。

## §2 字段契约（Python 与 Java **逐字同名**）

| 字段 | 类型 | 恒在 | 语义 | Java 取值 | Python 取值 |
|---|---|---|---|---|---|
| `ts` | string | ✅ | ISO-8601 带毫秒与本地时区偏移 | `%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX}` | `now().astimezone().isoformat(timespec="milliseconds")` |
| `level` | string | ✅ | `DEBUG`/`INFO`/`WARN`/`ERROR`（大写） | `%level` | `record.levelname` |
| `service` | string | ✅ | 产生日志的服务，见 §2.1 | 常量 `agt_backend` | 常量 `agt_python` |
| `traceId` | string | ✅ | 一次请求的链路 id，16 位十六进制；**不在请求上下文中为 `""`** | MDC | ContextVar |
| `userId` | string | ✅ | 登录用户 id 的十进制字符串；未登录/不在请求上下文为 `""` | MDC（认证拦截器写入） | `X-User-Id` 请求头 |
| `event` | string | ✅ | 结构化事件名，见 §3；未显式命名时**取 logger 名** | MDC，缺省 `%logger` | `extra={"event":...}`，缺省 `record.name` |
| `durationMs` | number | ✅ | 整数毫秒；**不适用时为 `-1`**（不是 `null`，避免消费者做两种空值判断） | MDC | `extra={"durationMs":...}`，缺省 `-1` |
| `msg` | string | ✅ | **人读消息**（本规范在规约八字段之外追加，理由：没有消息文本就没法 grep 与肉眼排障） | `%msg` | `record.getMessage()` |
| `err` | string | ✅ | 异常摘要 `类名: 消息`，**单行**（换行转义为 `\n`）；无异常为 `""` | `%ex{short}` 处理后 | `record.exc_info` 处理后 |

**三条硬规则**：

1. **八字段（+`msg`）必须恒在**。没有值就写 `""` 或 `-1`，**不许省略字段**——
   省略会让下游 `jq '.traceId'` 时而拿到字段时而拿到 `null`，脚本就开始"时好时坏"。
2. **允许追加字段，不许改名或删除**。追加（如 `sessionId`、`clientIp`）不破坏契约；改名是破坏性变更。
3. **`ts` 必须带时区偏移**。只写 `12:40:01` 的话，跨机器对齐时间线时会错 8 小时——
   这在"8080 与 8000 谁先超时"这类问题上直接把人带偏。

### §2.1 `service` 取值表

| 值 | 归属 | 结构化日志 | 说明 |
|---|---|---|---|
| `agt_python` | 8000 | ✅ | 智能体服务 |
| `agt_backend` | 8080 | ✅ | 业务后端 |
| `agt_web` | 9090 | ⏳ | 预留；前端错误上报是 **E-12**，届时同名字段 |
| —— | 8060 / 外部系统 | ❌ | jsdstu-3 是外部系统，只有 stdout 捕获（§4），字段不受本规范约束 |

## §3 `event` 命名法

格式：`域.动作`，全小写、点分隔。已登记的事件名（新增需在本表登记）：

| event | 时机 | 侧 |
|---|---|---|
| `http.request` | 一次入站 HTTP 请求完成（带 `durationMs`） | 8080 |
| `agent.call` | Java 调用 Python 的某次出站请求 | 8080 |
| `chat.request` | 一次对话请求开始/结束 | 8000 |
| `chat.stream` | 流式对话结束（带 `durationMs`、`err`） | 8000 |
| `kb.search` | 检索一次 | 8000 |
| `llm.call` | 大模型调用一次 | 8000 |
| `task.run` | 常驻任务跑一轮（备份/对账/巡检） | 8000 |
| `ops.health` | 健康聚合取数 | 两侧 |
| `startup` / `shutdown` | 进程生命周期 | 两侧 |

**缺省规则**：没显式指定 `event` 时填 **logger 名**（Java `%logger`、Python `record.name`）。
好处是"没登记的地方也不会出现空字段"，代价是那几个事件名不好过滤——所以关键路径必须显式命名。

## §4 日志落在哪（双轨，各有分工）

```
deploy/logs/
├── 8000-agt_python.jsonl        ← 结构化（应用自己写 + 自己轮转）★ 查询口径
├── 8000-agt_python.jsonl.1      ← 轮转的历史文件（.1 最新 … .10 最旧）
├── 8000-agt_python.log          ← 控制台捕获（计划任务 cmd 重定向）
├── 8080-agt_backend.jsonl       ← 结构化（logback 自己写 + 自己轮转）★ 查询口径
├── 8080-agt_backend.jsonl.1
├── 8080-agt_backend.log         ← 控制台捕获
├── 8060-drone.log               ← 外部系统，只有控制台捕获
└── 9090-agt_web.log             ← dev server，只有控制台捕获
```

| 轨道 | 谁写 | 谁轮转 | 装什么 | 用途 |
|---|---|---|---|---|
| **结构化 `.jsonl`** | 应用（Python `logging.handlers.RotatingFileHandler` / Java logback `RollingFileAppender`） | **应用自己**（50MB × 10 份，§5） | 全过程日志（含调试） | 按 `traceId` 查、按 level 过滤、喂给日志分析 |
| **控制台 `.log`** | 计划任务命令行 `cmd /c "... > log 2>&1"`（`deploy/scripts/_services.ps1` 的 `Get-AgtTaskArguments`） | `scripts/trim-logs.ps1` | 进程原始输出（含崩溃前的输出、第三方库输出、**进程起来之前**的报错） | "服务根本没起来"这类问题的唯一线索 |

> ⚠️ **为什么控制台捕获不能删**：结构化日志是**应用内**的 handler。
> 如果进程在 logging 初始化之前就死了（缺依赖、密钥没配、jar 不存在），
> 只会出现在 `.log` 里而**不会**出现在 `.jsonl` 里——那正是最需要线索的时刻。
>
> ⚠️ **控制台捕获为什么不由应用轮转**：它不是应用写的，是 cmd 的重定向。
> 由 `scripts/trim-logs.ps1` 按大小/天数收口（用法见 §8.3），
> 并在 `start-all.ps1` 启动前自动跑一次（`-KeepDays` 默认 14）。

## §5 轮转

统一口径：**单文件 50MB，保留 10 份历史，产物命名规律两侧一致**（`<file>.1` 最新、`.10` 最旧）。

| 侧 | 实现 | 配置项 |
|---|---|---|
| Python | `logging.handlers.RotatingFileHandler` | `LOG_MAX_BYTES`（默认 `52428800`）、`LOG_BACKUP_COUNT`（默认 `10`）、`LOG_DIR`（默认为 `<仓库根>/deploy/logs`） |
| Java | logback `RollingFileAppender` + `FixedWindowRollingPolicy` + `SizeBasedTriggeringPolicy` | `logback-spring.xml`（阈值写死为 50MB×10，与 Python 对齐；改就两侧一起改） |

- Java 的 `FixedWindowRollingPolicy` 与 Python 的 `RotatingFileHandler` **产物命名规律相同**（都是追加 `.1`…`.10`），
  所以一句 `ls deploy/logs/8080-agt_backend.jsonl*` 就能看全，运维不需要记两套规则。
- 磁盘上限可估算：结构化日志 ≈ (10+1) × 50MB × 2 侧 ≈ **1.1GB** 上限；控制台捕获由 `trim-logs.ps1` 另行收口。

## §6 `traceId` 怎么串起三端

**生成方只有一处：Java（8080）。** 前端不生成（前端代码不可信，且多页签会撞号）。

```
① 前端  POST /v1/agent/chat            （不带 traceId）
        │
② 8080  TraceIdFilter：入站头 X-Trace-Id 为空 → 生成 16 位 hex
        → MDC{traceId} + 响应头 X-Trace-Id 回写给前端
        → AuthInterceptor 解析会话成功后再 MDC{userId}
        │
③ 8080 → 8000   出站自动加 X-Trace-Id / X-User-Id
        （RestClient 走 AgentAuth 注册的拦截器；**SSE 流式走 JDK HttpClient，必须单独加**）
        │
④ 8000  TraceIdMiddleware：采纳入站 X-Trace-Id（**不自造**）→ 写入 ContextVar
        → 日志 filter 取 ContextVar；响应头 X-Trace-Id 回写
        │
⑤ 8000  埋点表 agent_chat_log.trace_id 用同一个 id（E-3 的 trace 追溯接口按它聚合）
```

| 端 | 生成 | 采纳 | 写日志 | 回写响应头 |
|---|---|---|---|---|
| 9090 前端 | ❌ | —— | 浏览器控制台（E-12 再收口） | —— |
| 8080 Java | ✅ 仅当入站为空 | ✅ 入站 `X-Trace-Id` | ✅ MDC | ✅ `X-Trace-Id` |
| 8000 Python | ⚠️ 仅当入站为空（**正常路径不该发生**） | ✅ `X-Trace-Id` | ✅ ContextVar | ✅ `X-Trace-Id` |

**两条容易踩的点**：

1. **SSE 流式调用不共享 RestClient 的默认头**（`AgentClient.chatStream` 走 JDK `HttpClient`），
   必须显式 `.header("X-Trace-Id", ...)`。这与 S-1 的 `X-Agent-Key` 是**同一条教训**（见 `DEV_ISSUES.md` §6.71）。
2. **SSE 的回调在另一个线程执行**（`SseEmitter` + 线程池），`MDC` 是 `ThreadLocal`，
   不会自动跟过去。所以流式worker 线程启动时必须显式 `MDC.put("traceId", ...)`，
   否则"整条链路就流式那段没有 traceId"，而这种缺失只在排查流式问题时才被发现。

## §7 脱敏（与 S-8 同源，一处收口）

**禁止出现在任何日志里**（两轨都不行）：

| 类别 | 例子 | 处理 |
|---|---|---|
| 服务间密钥 | `X-Agent-Key` 的值 | 只允许出现掩码形态（`AgentAuth.mask()`：`ab***yz(len=43)`） |
| 用户令牌 | `Authorization: Bearer xxx`、`X-Token` 的值、session id | 一律不记；需要时只记"有/无" |
| 第三方 API key | `LLM_API_KEY`、`EMBEDDING_API_KEY`（形如 `sk-...`） | 不记 |
| **完整用户输入** | 用户问句原文、工具入参快照、知识库文档正文 | **只记长度**（如 `questionLen=37`） |
| **PII（S-8，2026-09-25 收口）** | 手机号（`1[3-9]` 开头 11 位）、身份证（18 位含 X）、邮箱 | 出口正则替换为 `***`（规则单点 `app/core/pii.py`，Java `LogRedactor` 同规则镜像） |

**S-8 三条正则的顺序与环视契约**（两侧同源，改一侧必须同步另一侧）：

1. **邮箱 → 身份证 → 手机号**：邮箱必须最先——`13812345678@139.com` 若先被
   手机号规则吃掉数字，剩下的 `***@139.com` 里 `*` 不在邮箱字符集里，永远救不回来；
2. **数字类用 hex 感知环视**（`(?<![0-9a-fA-F])` 而非 `(?<!\d)`）：真机存量扫描实证，
   16 位 hex traceId `1db4f13378864346` 内嵌 11 位十进制段 `13378864346`，
   纯数字环视会把 traceId 打坏（"一次 grep 串链路"直接失效）；
3. 身份证不做校验位验证：**宁可把 18 位订单号误脱，也不放过真身份证**。

规则落地方式：**两侧各有一个脱敏函数，在格式化出口统一过一遍**——
Python `app/core/logging_setup.py::redact()`（在 Formatter 里，密钥层之后叠加
`app/core/pii.py::redact_pii()`），
Java `cn.tedu.agt.base.log.JsonLogLayout`（在 layout 里，`LogRedactor` 内含 PII 规则）。
**不是"写日志时记得别写"**——靠自觉迟早会漏，漏一次密钥就永久留在磁盘上。
同一出口还覆盖：埋点文本摘要（`telemetry._digest` 先脱敏再截断）、`client_error`
message/stack、缺口视图展示的原句。**刻意不覆盖**：`feedback_content` 表的原文
（规约 §4.2 口子的内容表，开关 + TTL 治理的产品数据）——库内存原文、出口处一律脱敏。

> ⚠️ **想看内容怎么办**：内容不在日志里，在**产品数据**里。
> 用户问句原文在 `agent_chat_log`（有权限控制、有保留策略），用同一 `traceId` 去查：
> `GET /v1/agent/metrics/traces/{traceId}`（E-3）。日志负责"哪一环慢/断了"，数据库负责"内容是什么"。

## §8 怎么用

### §8.1 按 traceId 一次串起两侧（E-6 的验收动作）

PowerShell（本机默认）：

```powershell
$tid = '8f3c1a92d47b05e6'
Select-String -Path deploy\logs\*.jsonl* -Pattern $tid |
  ForEach-Object { $_.Line } | ConvertFrom-Json |
  Select-Object ts, service, event, level, durationMs, msg | Format-Table -AutoSize
```

Git Bash（等价，`--noproxy` 无关，这里是本地文件）：

```bash
grep -h "8f3c1a92d47b05e6" deploy/logs/*.jsonl* | python -m json.tool --json-lines
```

期望看到**两侧交替**出现（先 `agt_backend` 的 `agent.call`，再 `agt_python` 的 `chat.request`），
一眼看出"Java 发出了、Python 收到了、各花了多久"。

### §8.2 常用过滤

```bash
# 只要错误（两侧）
grep -h '"level":"ERROR"' deploy/logs/*.jsonl*

# 慢于 1 秒的请求
grep -h '"durationMs"' deploy/logs/*.jsonl* | jq -r 'select(.durationMs > 1000) | "\(.ts) \(.service) \(.event) \(.durationMs)ms"'

# 某个用户今天干了什么（userId 来自登录会话，不是前端传的）
jq -r 'select(.userId == "1") | "\(.ts) \(.service) \(.event)"' deploy/logs/*.jsonl
```

### §8.3 控制台捕获日志的收口

```powershell
# 先看会删什么（默认 DryRun 语义：-DryRun 时才只打印，不加参数就是真删）
powershell -File scripts\trim-logs.ps1 -DryRun
# 真清理：超过 20MB 的截掉、超过 14 天的删掉
powershell -File scripts\trim-logs.ps1 -MaxMB 20 -KeepDays 14
```

`start-all.ps1` 每次启动前会自动跑一次（不阻塞启动，失败只告警）。

## §9 与其它机制的分工（别重复建设）

| 机制 | 回答什么问题 | 留存 | 关系 |
|---|---|---|---|
| **日志（本规范）** | "这次请求哪一环断了/慢了" | 短（滚动覆盖） | 面向**排障**，可按 traceId 精确检索 |
| **埋点 / 数据中台**（E-3） | "这周检索命中率多少" | 长（SQLite，有备份） | 面向**度量**，结构化入库、不落内容 |
| **操作审计**（E-8） | "谁在什么时候改了什么东西" | 长（合规） | 面向**问责**，不可篡改诉求更强 |
| **指标端点**（E-9） | "现在健康吗" | 即时 | 面向**监控**，不落盘 |

一句话：**日志是排障用的短期证据，不能当审计用**（会被轮转覆盖），
也不能当指标用（非结构化聚合代价高）。

## §10 已知边界（如实记档）

1. **前端 `agt_web` 尚未产出结构化日志**：浏览器侧错误上报是 **E-12**，本规范先占位 `service=agt_web`。
2. **8060 是外部系统**：其 stdout 只有控制台捕获，字段不受本规范约束；排障时靠它的原始输出。
3. **`traceId` 在跨进程重启后会重复吗**：不会——随机 16 位 hex（64 bit），
   且只用于检索不用于唯一性判定；真要唯一请用埋点表的 `trace_id` + `ts`。
4. **定时任务日志的 `traceId` 为 `""`**：它不是请求，没有上游 id。
   若将来需要，可用 `task.run` + `event` 过滤定位（见 §3）。
