## §1 总览

### 1.1 四个服务

| 端口 | 服务 | 技术栈 | 职责 | 谁构建 |
|---|---|---|---|---|
| **8060** | jsdstu-3 无人机主控 | Spring Boot | 业务后端（用户/无人机/任务/围栏/媒体），**外部系统** | 独立仓库，本仓库不构建 |
| **8000** | `agt_python` | FastAPI + Milvus | 智能体：意图路由、RAG 检索、多智能体编排、数据中台 | 本仓库（Python，无需构建） |
| **8080** | `agt_backend` | Spring Boot 3.3.3 | 业务网关：对外供 Vue 调用，向内调用 8000 | 本仓库（Maven 打 jar） |
| **9090** | `agt_web` | Vue 3 + vue-cli | 前端页面 | 本仓库（npm） |

### 1.2 调用关系（决定了启动顺序）

```
浏览器 ──> 9090 (Vue dev server)
              │  /v1/**  (axios)
              ▼
            8080 (agt_backend) ──代理登录校验──> 8060 (jsdstu-3)
              │
              │  X-Agent-Key  ← S-1 服务间共享密钥
              ▼
            8000 (agt_python) ──> Milvus 19530 (向量库)
              │                └─> SQLite (data/*.db，四个库)
              └──工具调用──> 8060
```

**启动顺序固定为 8060 → 8000 → 8080 → 9090**（8080 依赖前两者的接口）。

### 1.3 一分钟启动（已经部署过、只想把服务拉起来）

```powershell
cd <仓库根>
powershell -ExecutionPolicy Bypass -File deploy\scripts\preflight.py     # 1. 部署前自检
powershell -ExecutionPolicy Bypass -File deploy\scripts\install-tasks.ps1 # 2. 注册计划任务（只需一次）
powershell -ExecutionPolicy Bypass -File deploy\scripts\start-all.ps1     # 3. 一键启动
powershell -ExecutionPolicy Bypass -File deploy\scripts\status.ps1        # 4. 看状态
```

> 首次部署请从 §3 开始，别跳。

### 2.1 为什么 Python 必须是 conda `python311`

项目依赖 `pydantic_settings` 等包。**隔离环境（例如 WorkBuddy 自带的 python）没装这些依赖**，
用它启动 8000 会在 import 阶段就崩。自检脚本会显式检查这一项（`pydantic_settings` 能否导入）。

### 2.2 目录约定

```
<工作区>/
├── drone-agent001/          ← 本仓库（部署脚本在 deploy/scripts/）
│   ├── agt_python/          ← 8000
│   ├── agt_backend/         ← 8080
│   ├── agt_web/             ← 9090
│   ├── deploy/
│   │   ├── scripts/         ← 本手册用的全部脚本
│   │   ├── secrets/         ← 服务间密钥（gitignore，不进版本库）
│   │   ├── logs/            ← 四服务日志

│   └── docs/
```

## §3 首次部署

### §3.1 获取代码

```bash
git clone <仓库地址> drone-agent001
cd drone-agent001
```

如果拿到的交付包（`dist/<version>/`）没有 `.git`，属于正常——版本号会显示成 `no-git`（见 §3.4）。

### §3.2 服务间共享密钥（S-1，必做）

**是什么**：8000 除探针外**全部接口**都要求请求头 `X-Agent-Key`；8080 访问 8000 时自动带上。
两侧值必须**完全相同**，否则每一个请求都会收到 `{"code":4010}`。

**为什么 fail-closed**：密钥为空时 8000 **拒绝启动**。宁可起不来，也不能以"无鉴权"的姿态上线。

**怎么做（三步）**：

```bash
# 1) 生成一个密钥（43 字符左右）
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

```bash
# 2) 写到 Python 侧：agt_python\.env 里的 AGENT_SHARED_KEY=
#    （.env 不在版本库里；从 .env.example 复制而来，见 §3.3）
```

```bash
# 3) 写到 Java 侧：deploy\secrets\agent.key（单行，只放密钥本身）
#    8080 的启动脚本 deploy\start-backend.cmd 会读它并注入环境变量 AGENT_SHARED_KEY
```

> **两个文件必须同值**。这是排查"全链路 4010"的第一现场，
> 自检脚本会直接比对这两个值并报 `两侧密钥不一致`。

⚠️ 不要用 `set KEY=... && java -jar ...` 的方式内联启动：cmd 的引号剥离规则会把它弄坏，
而且密钥会明文出现在任务计划程序的任务参数里。

> **轮换密钥（E-10）**：不要"改两侧然后祈祷同步完成"——8000 与 8080 都要重启，
> 中间那段窗口会全链路 4010。轮换走**双密钥过渡**：本服务先同时收两把 → 再换 Java → 最后停用旧的。
> 完整步骤（含顺序论证与自检输出长什么样）见 **`docs/密钥与配置管理.md` §3**，
> 一句话版本是：`.env` 里 `AGENT_SHARED_KEY=<新>` + `AGENT_SHARED_KEY_PREV=<旧>`，
> 重启后 `agent_shared_key_prev` 让旧密钥继续可用，直到
> `agt_degrade_events_since_start_total{path="auth_key_legacy_used"}` 不再增长再清空它。

### §3.3 配置 `agt_python/.env`

```bash
cd agt_python
cp .env.example .env
```

必填项（自检脚本会逐个检查）：

| 项 | 说明 | 留空的后果 |
|---|---|---|
| `AGENT_SHARED_KEY` | 见 §3.2 | **8000 拒绝启动** |
| `LLM_API_KEY` | 对话模型密钥（DeepSeek / 智谱等） | 业务链路不可用 |
| `EMBEDDING_API_KEY` | 向量模型密钥 | RAG 检索不可用 |
| `HOST` | 保持 `127.0.0.1` | 改成 `0.0.0.0` 会把 agent 暴露到网络（S-1 只有一层密钥防线） |

其余上百项都有可用默认值，按需再调（全量说明见 `.env.example` 的注释）。

### §3.4 构建产物

```bash
# ① 版本打戳（改了 VERSION、或首次 clone 后必须做一次）
python scripts/stamp_version.py
#    → 生成三端版本产物；忘了做，`--check` 会报不一致

# ② 后端（8080）：产物固定为 target\agt_backend.jar（不带版本号，E-2 统一命名）
cd agt_backend
mvn clean package -DskipTests
#    ⚠️ Windows 会锁住正在运行的 jar → 重新打包前必须先停 8080（stop-all.ps1）

# ③ 前端依赖（9090）
cd ../agt_web
npm install

# ④ jsdstu-3（8060，外部系统）：在它自己仓库里 mvn package，或用 IDEA 直接跑
```

版本号看哪里：**仓库根 `VERSION`** 是唯一来源，运行时通过
`GET :8000/v1/health`、`GET :8080/v1/version`、`GET :9090/version.json` 三处暴露。

### §3.5 Milvus（向量库）

```bash
cd deploy/milvus
docker compose -p milvus up -d          # etcd / minio / standalone，依赖顺序由 depends_on 保证
```

**就绪判据（别只看容器状态）**：

```bash
# 容器都是 healthy 不够，用真实业务接口确认
curl -s --noproxy '*' http://127.0.0.1:8000/v1/health -H "X-Agent-Key: <你的密钥>"
# 或部署后看 /v1/kb/stats 是否能返回 docCount / chunkCount
```

> ⚠️ **项目隔离**：本机还有另一个 compose 项目 `lbb`（rabbitmq/qdrant/nacos/minio/mysql8/redis7），
> 操作前先确认 `docker inspect <容器> --format '{{index .Config.Labels "com.docker.compose.project"}}'`
> 是 `milvus`，别误伤无关容器。

### §3.6 部署前自检

```bash
python deploy/scripts/preflight.py
```

它会检查五组共 22 项：工具链 / 配置与密钥 / 构建产物 / 端口 / 外部依赖。
**退出码非 0 = 有阻塞项，不要继续启动**（`start-all.ps1` 也会先跑它并据此拒绝启动）。

状态含义：

| 状态 | 含义 | 影响 |
|---|---|---|
| `OK` | 通过 | — |
| `INFO` | 信息（如"本系统已在运行"） | 不阻塞 |
| `WARN` | 建议修（外部系统未起、可降级的项） | 不阻塞，但会提醒 |
| `FAIL` | **阻塞** | 带着它启动要么起不来，要么服务是残废的 |

加 `--json` 可输出机器可读结果（给 CI / 看板用）。

## §4 启动 / 停止 / 查看

### §4.1 注册计划任务（只需一次）

```powershell
powershell -ExecutionPolicy Bypass -File deploy\scripts\install-tasks.ps1
```

- **幂等**：可反复执行，会覆盖旧定义。
- 注册四个任务 `drone-agent-{8060,8000,8080,9090}-*`，运行主体是 **S4U 非交互主体**。
- 卸载：`install-tasks.ps1 -Uninstall`（只删任务定义，不删代码/数据/日志）。
- 想开机/登录自动起：加 `-StartAtLogon`。

> **为什么必须 S4U**（2026-09-24 实测的教训）：默认的交互式主体会给每个服务**弹出一个可见 cmd 窗口**，
> 窗口一被关（点 X / Ctrl+C），整棵进程树以 `0xC000013A` 一起死。
> 症状是"服务跑得好好的突然全没了"，极易误判成产品 bug。S4U 让进程跑在 session 0，无窗口，
> 用户注销也不受影响。核验方式见 §4.4 的 `SessionId` 列。

### §4.2 一键启动

```powershell
powershell -ExecutionPolicy Bypass -File deploy\scripts\start-all.ps1
```

流程：自检 → **收口 `deploy/logs/*.log`（`trim-logs.ps1`）** → 检查任务已注册 → 按 8060→8000→8080→9090 顺序启动并**逐个等待就绪** → 汇总状态。

- **幂等**：已在运行的会跳过；缺哪个补哪个。
- `-Restart`：先停再起（改了代码想让它生效时用）。
- `-SkipPreflight`：跳过自检（不推荐）。
- 某个服务超时未就绪 → 打印它日志的最后 25 行 + 排查方向；非可选服务失败会中止后续启动。
- 日志收口是**独立进程 + 失败只告警**：`.log` 超 20MB 轮转、超 14 天删除，**文件被占用就跳过**，
  任何异常都 `exit 0` —— 它**绝不影响启动**（E-6）。

### §4.3 停止

```powershell
powershell -ExecutionPolicy Bypass -File deploy\scripts\stop-all.ps1
powershell -ExecutionPolicy Bypass -File deploy\scripts\stop-all.ps1 -SkipPorts 8060   # 别动 8060
```

倒序停（9090→8080→8000→8060）。两步走：停计划任务实例，再清理端口上残留的监听进程
（java/python 是 cmd 的子进程，父进程停了子进程可能还占着端口）——最后一定复查端口并如实报告。

**任务定义不会被删除**，下次直接 `start-all.ps1` 即可。

### §4.4 查看状态

```powershell
powershell -ExecutionPolicy Bypass -File deploy\scripts\status.ps1
powershell -ExecutionPolicy Bypass -File deploy\scripts\status.ps1 -LogTail 10   # 附带日志尾部
powershell -ExecutionPolicy Bypass -File deploy\scripts\status.ps1 -Json         # 给监控用
```

判断"是否真的健康"要看三样，缺一不可：

| 列 | 含义 | 异常怎么读 |
|---|---|---|
| 状态 | `UP` / `UNHEALTHY` / `DOWN` | `UNHEALTHY` = 端口在监听但探针失败（内部依赖挂了） |
| **SessionId** | **`0` = S4U 非交互（正确）**；`1` = 交互桌面会话（危险） | 出现 `1` 说明有可见窗口，窗口被关会连带死；用 `install-tasks.ps1` 重建后重启 |
| 探针 | `HTTP 200` / `TCP ok` | 失败说明服务不健康 |

### §4.5 8060（外部系统）

8060 属于 jsdstu-3，**本仓库不构建它**。两种启动方式：

1. **IDEA**（推荐）：打开 `jsdstu-3`，运行 `cn.tedu.drone.DroneApplication`。
2. 命令行：`java -jar <jsdstu-3>\drone\target\drone-0.0.1-SNAPSHOT.jar`。

登录令牌头是 `X-Token: <t>`（或 `Authorization: Bearer <t>`），**不是** 8080 用的那一套。

### §4.6 不用计划任务的手动启动（调试用）

```bash
# Milvus
cd deploy/milvus && docker compose -p milvus up -d

# 8000（改代码必须重启，非 reload）
cd agt_python
<conda-python311> -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 8080（先停旧进程，Windows 锁 jar；用包装脚本注入密钥）
cd deploy && cmd /c start-backend.cmd

# 9090
cd agt_web && npm run serve
```

## §7 故障对照表

> 排查顺序建议：先 `preflight.py`，再 `status.ps1 -LogTail 20`，最后看 `deploy/logs/` 里的完整日志。

### §7.1 端口被别的进程占用（自检报 `FAIL`）

**现象**：`preflight.py` 报 `端口被**别的进程**占用（探针 ... 返回 xxx）`；启动时服务起不来。

**为什么能识别**：自检不是简单探"端口有没有人听"，而是调用本服务独有的探针——
8000 看 `/v1/health` 的 `code=2000`、8080 看 `/v1/version`、9090 看 `/version.json`、8060 看响应体的 `"code"`。
所以"别人占了这个端口"和"本系统已在运行"能被区分开。

```powershell
# 找出占用者
netstat -ano | findstr :9090
Get-Process -Id <pid> | Select-Object Id,ProcessName,Path
# 确认无用后结束
Stop-Process -Id <pid> -Force
```

若是本系统自己的**残留进程**（上个实例没停干净），直接跑 `stop-all.ps1`。

### §7.2 Milvus 不可达 / 知识库报 `3010`

**现象**：`/v1/kb/stats` 返回 `3010 知识库暂不可用：MilvusException`；
`preflight.py` 报 `Milvus 19530 不可达`。

**根因**（本机实测两次）：`milvus-etcd` / `milvus-minio` 处于 `Exited (255)`
（Docker Desktop 重启后常见），standalone 等不到 `etcd:2379` 而**无限重启**；
它的 healthcheck 打的是 9091，所以容器**表面仍可能显示 healthy**，很有迷惑性。

```bash
cd deploy/milvus
docker compose -p milvus down      # 不带 -v，数据卷安全
docker compose -p milvus up -d     # depends_on 保证 etcd/minio 先起
docker compose -p milvus ps        # 三个都 Up (healthy) 再看业务接口
```

⚠️ `down` 前先确认项目隔离（见 §3.5）。就绪判据用真实业务接口，别只看容器状态。

### §7.3 全链路 `4010`（密钥未配 / 不一致）

| 现象 | 原因 | 处置 |
|---|---|---|
| 8000 **起不来**，日志有 `RuntimeError` | `AGENT_SHARED_KEY` 为空 | §3.2 生成并写入 `.env` |
| 8000 **起不来**，日志有 `RuntimeError` 且提示 `AGENT_SHARED_KEY_PREV` | `AGENT_SHARED_KEY_PREV` **与当前密钥同值**（E-10 有意拒绝） | 两把一样不构成轮换：PREV 应填**要被停用的那把旧密钥**；轮换结束是**清空**它 |
| 8080 每个请求都 4010 | `deploy/secrets/agent.key` 与 `.env` 不同值 | 让两侧同值；`preflight.py` 会直接报"两侧密钥不一致" |
| 8080 起不来，日志 `IllegalStateException` | `agent.key` 缺失（fail-closed） | §3.2 生成密钥文件 |
| **轮换期**：8080 全 4010，但 8000 侧 `auth_key_rejected` 在涨 | 顺序做反了（Java 先换了新密钥，而 8000 还不认它） | 先让 8000 同时收两把（配 `AGENT_SHARED_KEY_PREV`）再改 Java；或把 Java 改回旧密钥，按 `docs/密钥与配置管理.md` §3.3 重做 |
| 轮换后**某些定时任务**报 4010 | 有调用方还在用已停用的旧密钥（清 PREV 清早了） | 把旧密钥填回 `AGENT_SHARED_KEY_PREV` 重启，观察 `auth_key_legacy_used` 定位是哪个调用方 |

**归因技巧**：看 8000 的 `/v1/agent/metrics/overview` → `faultCounters.auth_key_rejected` 有没有 +1。
**没涨**说明不是 Python 侧拒绝，去 Java 侧找（多半是令牌头用错，见 §7.5）。

**轮换相关的两个计数要分清**（都在 `/v1/ops/metrics`）：

| 指标 | 含义 | 怎么用 |
|---|---|---|
| `...{path="auth_key_rejected"}` | 真被拒绝 | 涨 = 有调用方进不来 |
| `...{path="auth_key_legacy_used"}` | 用的是**上一把**密钥但**被放行**（请求成功处理） | 持续为 0 = **可以清掉 `AGENT_SHARED_KEY_PREV` 了** |

⚠️ 后者**不进故障数**（它不是故障）。把两者混起来看，会把"轮换正常进行"误判成"有攻击"。

### §7.6 顶栏状态灯 / `/v1/ops/health` 怎么读（E-3）

灯的颜色与 `data.status` 一一对应，**判据不是"有没有组件挂"，而是"缺了能不能干活"**：

| 灯 | `status` | 含义 | 典型原因 | 处置 |
|---|---|---|---|---|
| 🟢 绿 | `up` | 全部组件正常 | — | — |
| 🟡 黄 | `degraded` | 服务仍在，**某项能力降级** | Milvus 挂 / 某个 SQLite 库不可写 / 8060 不可达 / 定时任务报错 | 悬停看明细，按组件名处置：Milvus → §7.2；8060 → §4.5 |
| 🔴 红 | `down` | **核心链路不可用** | 8080 连不上 8000（`python-service: down`） | 先 `status.ps1` 看 8000，再按 §7.2 |

⚠️ **两个最容易读错的地方**：

1. **组件 `status` 与顶层 `status` 是两件事**。停掉 Milvus 时，`components` 里
   `milvus.status=down`（它真的挂了），而顶层是 `degraded`（对话/看板/画像仍能用）。
   只看顶层会以为"一切正常"，只看组件会以为"系统全挂了"。
2. **`degrade` 组件恒 `up`，不代表没发生过降级**。它只是"降级计数器已采集"；
   计数器非零是**历史观测数据**（比如 `rag_degraded=3` 表示出现过 3 次检索降级），
   不是当前故障——故意不参与健康判定，否则接口会永远黄着，人就不看了。

排障入口按"从粗到细"三级：顶栏灯 → `curl :8080/v1/ops/health` 看组件 →
`curl :8000/v1/ops/health?fresh=true`（带密钥）看更细的延迟与原因。

### §7.7 日志怎么看（E-6）

**最常用的一条命令 —— 用 traceId 串起一次请求的全部日志（跨 Java / Python 两侧）**：

```bash
grep -h "<traceId>" deploy/logs/8080-agt_backend.jsonl deploy/logs/8000-agt_python.jsonl
```

traceId 从哪拿（三处任选，**都是同一个值，由 Java 生成**）：
① 浏览器 F12 → 任意接口响应头 `X-Trace-Id`；
② 前端聊天流每轮的 SSE `meta` 事件里的 `traceId`；
③ 直接看 `.jsonl` 最后几行（字段 `traceId`）。

**字段含义**（九字段逐字同名，Java/Python 同一套）：`ts`（带时区）· `level` · `service` ·
`traceId` · `userId`（匿名请求为空）· `event`（`域.动作`，如 `agent.call`）· `durationMs` ·
`msg` · `err`。完整契约与 `event` 命名法见 `docs/日志规范.md`。

⚠️ **三个容易踩的点**：

1. **`.jsonl` 与 `.log` 用途不同，别混着看**。`.jsonl` 是应用写的结构化日志（能 grep traceId、
   字段稳定）；`.log` 是计划任务捕获的原始控制台流 —— **"服务起不来"时 `.jsonl` 可能是空的或滞后的，
   真正的报错只在 `.log` 里**（因为应用还没初始化到能写日志）。
2. **日志里的密钥一定是脱敏后的**（`Bearer`/`token`/`X-Agent-Key` 会被替换成掩码）。
   若你看到"日志里像是有个 token 但读不到全值"——那是**设计如此**，不是日志被截断了。
3. **轮转不会无限增长**：`.jsonl` 由应用按 50MB×10 自己轮转（备份名 `.1`~`.10`）；
   `.log` 由 `trim-logs.ps1` 在每次 `start-all.ps1` 启动前收口（超 20MB 轮转 `.1`、超 14 天删除；
   被占用则跳过，**绝不影响启动**）。看"有没有新日志"要连 `.1` 一起看，别只看主文件。

> 排查"日志里某个字段莫名消失"这类问题时，先确认两侧 `service` 字段是否同值 ——
> 若 Java 侧有、Python 侧没有，通常是**转发出站时漏加链路头**（流式走 JDK HttpClient，
> 不共享 RestClient 的 defaultHeader，必须单独加），参考 `AgentClient.chatStream`。

### §7.8 指标怎么看（E-9）

**两个端点都在，但权限不同（与 §7.5 的健康聚合同向）**：

| 端点 | 鉴权 | 用途 |
|---|---|---|
| `GET :8000/v1/ops/metrics` | 需 `X-Agent-Key` | Python 侧全量指标（21 个必需族） |
| `GET :8080/v1/ops/metrics` | **匿名** | 抓取入口：Java 段 + 透传 Python 段，**双段合并** |

响应是 **Prometheus 文本格式**（`text/plain; version=0.0.4`），零新依赖手写，**不接 Prometheus/Grafana**
（规约决策 D3：需要接时接线已经在了）。

**最快的自检**（`--noproxy '*'` 是必须的，见 §7.4）：

```bash
# 匿名走 8080，应当同时含 agt_java_* 与 agt_* 两段
curl -s --noproxy '*' http://127.0.0.1:8080/v1/ops/metrics | head -40

# 关键一行：1=Java 段成功拼上了 Python 段，0=Python 不可达（已降级）
curl -s --noproxy '*' http://127.0.0.1:8080/v1/ops/metrics | grep agt_java_python_section_ok

# 带密钥直连 8000（看纯 Python 侧）
curl -s --noproxy '*' -H "X-Agent-Key: <key>" http://127.0.0.1:8000/v1/ops/metrics | head -40
```

**口径说明（三个最容易读错的点）**：

1. **`_total` 是"建表以来累计"（单调递增），窗口量一律是 gauge**。带 `_total` 的才用 `rate()`/`increase()`；
   `agt_chat_duration_seconds` 这类是**最近 24h 窗口内的观测**，**不要对它做 `rate()`**。
   窗口可用 `?window=<小时>` 调整，缓存可用 `?fresh=true` 绕过。
2. **`agt_degrade_events_since_start_total` 是"本进程口径"**：它读 `fault_counters.json`，该文件
   **只写不读**，进程重启即归零 —— 因此与 `agt_faults_total`（建表以来累计）**口径不同**，
   **不要拿两者做一致性检查**。
3. **`agt_java_python_section_ok 0` 不等于端点坏了**。Python 不可达时 8080 **降级返回**：HTTP 仍 200，
   只给 Java 段 + 一行 `#` 注释写明原因。此时前端健康灯也会变红（§7.6），两处可互证 ——
   **一个 URL 抓不到，比一个 URL 直接 500 有用**。

⚠️ **抓取端注意**：同名 + 同标签的序列若重复出现，**整次抓取会失败**（`duplicate sample for timestamp`）。
本端点已内置去重（重复序列静默丢弃），但你在中间接自研 exporter 时要注意自己防重。

> **不接监控时零影响**：数据源全部复用既有 ODS 四表 + 内存计数器 + `scheduler.status()`，**不新增埋点通道**；
> SQLite 一律 `mode=ro` 打开且先判文件存在，**不创建库文件**。`/v1/ops/metrics` 已加入两侧 quiet paths，
> 高频抓取不会稀释业务日志。

### §7.9 审计怎么看（E-8）

**先分清"谁在问"**：审计里含操作人、来源 IP、traceId，属敏感数据，所以**两个服务的权限不一样**。

| 端点 | 鉴权 | 谁用 |
|---|---|---|
| `GET :8000/v1/kb/governance/audit` | 需 `X-Agent-Key` | 服务间 / 排障 |
| `GET :8000/v1/kb/governance/audit/export` | 需 `X-Agent-Key` | 服务间 / 排障 |
| `POST :8000/v1/kb/governance/audit` | 需 `X-Agent-Key` | **Java 侧补录用**，不给人调 |
| `GET :8080/v1/kb/governance/audit` | **需管理员 Bearer** | 人 / 前端治理面板 |
| `GET :8080/v1/kb/governance/audit/export` | **需管理员 Bearer** | 导出 CSV |

> 与 §7.5 同一条规律：**8080 的只读接口不是全都匿名**。审计、文档登记、工单这几类要看**身份与角色**
> （4011 = 令牌有效但角色不够，4010 = 没令牌/令牌无效）——**别把 4011 当成"服务没起"**。

**七维字段**（一张表回答"谁/何时/从哪/对什么/做了什么/结果如何"）：

| 字段 | 含义 | 备注 |
|---|---|---|
| `actor`（列名仍是 `operator`） | 操作人 | 拿不到身份时写 `anonymous` / `system`，**不编造** |
| `action` | 动作码 | 全表见 `docs/审计清单.md` §3 |
| `target` | 作用对象 | 统一前缀 `doc:` / `tool:` / `user:` / `backup` / `config:` / `service:` |
| `result` | `SUCCESS` / `FAILED` / `DENIED` | **三者必须分开看**（见下） |
| `ip` | 来源 IP | 优先 `X-Forwarded-For`；**目前只有账号事件带** |
| `traceId` | 链路 ID | 与 §7.7 的日志是同一个值，**可一次 grep 串起日志与审计** |
| `at`（列名仍是 `ts`） | 时间 | ISO 秒级字符串，**字典序即时间先后** |

**最快的自检**（`--noproxy '*'` 是必须的，见 §7.4）：

```bash
# 最近 3 条（8080，需要管理员令牌）
TOKEN=$(curl -s --noproxy '*' -X POST http://127.0.0.1:8080/v1/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"123456"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

curl -s --noproxy '*' -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8080/v1/kb/governance/audit?pageSize=3"

# 只看"工具类"动作（前缀匹配，一次捞出所有确认门事件）
curl -s --noproxy '*' -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8080/v1/kb/governance/audit?target=tool:&pageSize=20"

# 按时间窗（两个都是闭区间，格式 YYYY-MM-DD HH:MM:SS）
curl -s --noproxy '*' -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8080/v1/kb/governance/audit?from=2026-09-24%2000:00:00&to=2026-09-24%2023:59:59&pageSize=50"
```

导出走服务端（带上当前筛选条件即可）：

```bash
curl -s --noproxy '*' -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8080/v1/kb/governance/audit/export?target=tool:" \
  | python -c "import sys,json;d=json.load(sys.stdin)['data'];open(d['filename'],'w',encoding='utf-8').write(d['content']);print(d['filename'],d['rows'],'truncated=',d['truncated'])"
```

**口径说明（五个最容易读错的点）**：

1. **`result` 三值不能合并理解**。`SUCCESS` = 做了且成了；`FAILED` = 做了但没成（系统问题）；
   `DENIED` = 按规则根本不该做（权限/风险问题）。**把 `DENIED` 读成"故障"是最常见的误判**——
   它恰恰说明防线在工作。
2. **`target` 筛选是"前缀匹配"，不是精确匹配**。`target=tool:` 会捞出所有工具类动作；
   想精确到某一个工具就写全 `target=tool:create_flight_task`。
3. ⚠️ **老数据的 `target` 是"读取时算出来的"，库里仍是 NULL**。E-8 之前的行没有这一列，
   为了不破坏"审计只增不改"的性质，没有回填，而是读的时候用 `target = COALESCE(target, 'doc:'||doc_id)` 派生。
   → **后果**：老行里**只有和文档相关的**（有 `doc_id`）才能按 `target=doc:` 筛到；
   老行里的账号/工具事件（当时压根没记）筛不到——这是**数据本来就不存在**，不是筛选坏了。
4. **`ip` 目前只有账号事件有**（Java 侧拿得到 `HttpServletRequest`）。治理动作那部分 `ip` 为空，
   是**已知边界**（`docs/审计清单.md` §10 记档），不代表"没记录人"。
5. **导出到顶会标注 `truncated=true`**，上限 2 万行。**看到 `truncated=true` 就说明这是一份子集**，
   要么收窄时间窗、要么分次导出——不要把它当全量证据用。另外导出内容**开头有 BOM**，
   若用脚本二次处理，注意别把 `\ufeff` 当成第一个字段名。

> **审计只增不减**：没有任何"清空审计"的入口（连彻底删除文档之后，审计行也照留）。
> 要清理只有整库归档这一条路，目前未做——见 `docs/审计清单.md` §10。

### §7.10 前端错误怎么看（E-12）

**这套东西解决的是**：页面在白屏 / 按钮点了没反应的时候，**服务端日志里可能什么都没有**——
因为错误根本没发出请求，它在浏览器里炸了。E-12 在浏览器侧装了三处收口，把这类错误捞回来。
三个收口点是：Vue 的 `app.config.errorHandler`（组件渲染/生命周期里抛的）、
`window.onerror`（其它同步脚本错误）、`unhandledrejection`（Promise 没接住的拒绝）。

**端点与权限**（与 §7.5 同一条规律：8080 只读接口多为匿名，但**写入口只有这一个**）：

| 端点 | 鉴权 | 谁用 |
|---|---|---|
| `POST :8080/v1/ops/client-error` | **匿名** | **浏览器唯一写入口**（前端上报走这里） |
| `GET :8080/v1/agent/metrics/client-errors` | **匿名** | 看板「前端错误」页 / 总览卡 |
| `POST :8000/v1/ops/client-error` | 需 `X-Agent-Key` | Java 带密钥转发进来，**不给人直连** |
| `GET :8000/v1/agent/metrics/client-errors` | 需 `X-Agent-Key` | 服务间 / 排障 |

> **为什么写入端点必须匿名**：崩溃最常发生在**还没登录**的时候（登录接口 500、token 解析炸了、
> 登录页脚本报错）。如果上报要求先登录，那恰恰在"最需要上报的时刻"收不到——**这是有意的取舍，不是漏配**。
> 它读不到任何东西、也改不了任何业务状态，所以风险可控（详见 `docs/权限矩阵.md` §3.2）。
> 浏览器**无法持有服务间密钥**，所以前端只能打 8080，由 8080 带密钥转 8000。

**最快的自检**（`--noproxy '*'` 是必须的，见 §7.4）：

```bash
# 1) 造一条上报（8080 匿名，无需令牌；试完看板里能搜到这条 message）
curl -s --noproxy '*' -X POST http://127.0.0.1:8080/v1/ops/client-error \
  -H 'Content-Type: application/json' \
  -d '{"page":"/debug","source":"window.onerror","message":"手册自检：前端错误通道","appVersion":"manual"}'

# 2) 查最近明细（8080 匿名）
curl -s --noproxy '*' "http://127.0.0.1:8080/v1/agent/metrics/client-errors?hours=24&limit=5"

# 3) 直连 8000 复核（需密钥；8080 有 8KB 体积闸门，直连没有——排障时可用来确认"是 8080 挡的还是 Python 没写进"）
curl -s --noproxy '*' -H "X-Agent-Key: $AGENT_KEY" \
  "http://127.0.0.1:8000/v1/agent/metrics/client-errors?hours=24&limit=5"
```

浏览器里还可以自查收口是否装上：登录后在控制台执行 `window.__agtClientErrorSelfTest()`，
返回 `{"vue":true,"window":true,"promise":true}` 表示三处都挂上了；
`window.__agtClientErrorStats()` 看本次会话已上报/被去重/被采样丢弃的计数。

**口径说明（六个最容易读错的点）**：

1. ⚠️ **`total` 是"下界"，不是"报错次数"**。看板里的 `total` 是各行 `count` 的**和**，
   而前端**每次页面加载对同一个错误只报一次**（防刷屏）。所以真实的抛错次数通常**大于** `total`。
   要看"有多少**类**错误"就看得 `distinct`（按指纹去重后的类别数）。
2. **同一错误在同一个 1 分钟窗口内会被合并成一行**（`count` 累加），这是**固定的时间桶**不是滑动窗口。
   → **后果**：横跨桶边界（如 10:00:59 与 10:01:01）的同一个错误会**分成两行**，看起来像两个错误。
   看板行数 **既不等于错误种类数、也不等于发生次数**，别拿它当精确计数用。
3. **采样率可调**（`CLIENT_ERROR_SAMPLE_RATE`，0~1）。设成 0.5 时**一半的上报被直接丢弃**，
   而不是"少记一半再乘以 2 还原"——`total` 不会自动补偿，低采样下它离真实值更远。
   配置项一览（`agt_python/.env`）：`CLIENT_ERROR_ENABLED` / `CLIENT_ERROR_SAMPLE_RATE` /
   `CLIENT_ERROR_DEDUP_SECONDS`（合并桶宽，默认 60）/ `CLIENT_ERROR_MAX_MESSAGE`（默认 500）/
   `CLIENT_ERROR_MAX_STACK`（默认 2000）。
4. **看板故意没有"查会话"链接**。表里的 `trace_id` 是**上报这次请求自己**的链路 ID，
   **不是出错那次操作的**（前端记不住上一次会话的 traceId）→ 拿它去查必 404，所以干脆不放。
5. **列表按 `count` 降序**，回答的是"现在什么**最吵**"，不是"什么**最严重**"。
   高频的小错误（如某组件反复报同一句）会排在偶发的大错误前面。
6. **上报是"发完不管"（fire-and-forget）**：它**永远不阻塞用户操作**，代价是网络断了/接口挂了
   这条错误就**丢了**——这是有意的取舍，不要指望它做到"一条不漏"。
   另外 `/v1/ops/client-error` 与探针一样是**静默路径**：**成功时**不写结构化访问日志
   （否则一次会话几十条上报会把日志淹没），**失败时照记**——所以"日志里没有这条"不等于"上报没发生"。

### §7.11 成本与配额怎么看（E-13）

**这套东西解决的是**：`agent_chat_log` 里 token 数**早就有了**，但没有人把它折成钱——
"这个月大模型花了多少钱"只能去问供应商账单，且**事后才知道**。E-13 补齐：流式链路的
真实 usage（此前流式 token 恒记 0）→ 按价目表折算 → 按模型/用户/部门聚合 → 单用户日配额。

**端点与权限**（与其他 metrics 读端点同锁）：

| 端点 | 鉴权 | 谁用 |
|---|---|---|
| `GET :8080/v1/agent/metrics/costs` | **匿名** | 看板「成本与配额」页 |
| `GET :8000/v1/agent/metrics/costs` | 需 `X-Agent-Key` | 服务间 / 排障 |

**最快的自检**（`--noproxy '*'` 是必须的，见 §7.4）：

```bash
# 1) 成本聚合（data.totals / byModel / byUser / byDept / daily / quota）
curl -s --noproxy '*' "http://127.0.0.1:8080/v1/agent/metrics/costs?days=7"

# 2) 直连 8000 复核（需密钥）
curl -s --noproxy '*' -H "X-Agent-Key: $AGENT_KEY" \
  "http://127.0.0.1:8000/v1/agent/metrics/costs?days=7"

# 3) 配额留痕（超限事件，每用户每日至多一条）
grep quota_exceeded agt_python/data/metrics/observability.db 2>/dev/null || true
```

**口径说明（五个最容易读错的点）**：

1. **成本 = 查询期折算，不在 DWS 冻结**。价目配置 `LLM_PRICE_JSON`（**元/百万 token**）只存一份，
   改价后历史按新价重算——看板回答的是"按现在的价格值多少钱"。要对某张历史账单，
   得用当时的价目重算。这是刻意取舍：预聚合冻结价格会让改价后历史口径整体漂移。
2. **未配价 ≠ 免费**。模型名不在价目表里时成本记 ¥0 但 token 照记，看板单列
   `unpricedTokens`。⚠️ 历史数据的主力模型名是 **`deepseek-flash`**——不做这一节的人
   看到成本全是 0 会以为计量坏了，其实只是没配价。
3. **流式与估算**：`usage_source='api'` 的行是服务端返回的真实用量（可对账）；
   `'estimate'` 是上游没给、`TokenEstimator` 本地估算的（**可看趋势、不可对账**）。
   E-13 之前的行这一列为空（那时流式 token 记 0，是已知的历史欠账，不是新代码丢了数据）。
4. **部门 = 画像里声明过的 `department` 键**（读取期派生、不回填），没声明的归 unknown——
   本系统没有组织架构，这个维度回答"哪些人在用"，不是"哪个组织在用"。
5. **配额超限不拒绝服务**（规约原文的降级要求）：用户收到黄条提示（SSE `quota` 事件 /
   响应 `quota` 字段），系统落 `quota_exceeded` fault **每用户每日至多一条**。
   看到用户"超限了还能聊"不是 bug，是设计。两个配置：
   `QUOTA_USER_DAILY_TOKENS`（0=不限）与价目表，改完必须重启 8000。

## §8 部署形态二：容器化（E-14，实测可跑）

规约 D1 决定交付**双轨**：形态一 = Windows 原生 + 计划任务（§3，本文档主体描述的就是它）；
形态二 = **容器化**（本节）。两种形态共用同一份代码与配置口径，数据**互不相通**（各自独立部署）。

### 8.1 交付物清单（6 个文件）

| 文件 | 作用 |
|---|---|
| `agt_python/Dockerfile` | 8000（FastAPI）；依赖层缓存 + 容器内 0.0.0.0 监听 + python 一行式健康检查 |
| `agt_backend/Dockerfile` | 8080（Spring Boot）；两阶段（maven 构建 → jre 运行），命令行参数覆盖 `agent/drone.base-url` |
| `agt_web/Dockerfile` | 9090；两阶段（node 构建 → nginx），生产构建进镜像 |
| `deploy/nginx/nginx.conf` | 浏览器唯一入口：`/v1` → 8080（**SSE 关缓冲 + 300s 读超时**）、SPA 回退、静态长缓存；**与 S-2 是同一份，不写两份** |
| `deploy/docker-compose.app.yml` | 三服务编排 + 命名卷 + external 接入 `milvus-net` |
| `.dockerignore` + `deploy/docker/maven-settings.xml` | 构建上下文瘦身（密钥/数据/缓存不进镜像）+ Maven 阿里云镜像源 |

三个 Dockerfile 的**构建上下文都是仓库根**（`docker build -f agt_xxx/Dockerfile .`）——
这样 Python 侧才能 `COPY VERSION`（E-1 版本唯一来源），容器里 `/v1/health` 才答得出版本号。

### 8.2 启动顺序与拓扑

```
① deploy/milvus/docker-compose.yml   （Milvus 独立栈，建 milvus-net 网络）
② deploy/docker-compose.app.yml      （三服务；经 external 网络 milvus-net 接入）
```

```bash
cd deploy/milvus  && docker-compose up -d          # 先起 Milvus（已在跑则跳过）
cd ..             && docker-compose -f deploy/docker-compose.app.yml up -d --build
```

- 编排用 healthcheck 驱动依赖顺序：agt-python 健康 → agt-backend 起 → agt-backend 健康 → agt-web 起。
- **端口策略**（S-1"8000 只服务本机 Java"的容器等价物）：
  `agt-web 9090:80`（浏览器唯一入口）、`agt-backend 8080:8080`（运维直连）、
  **agt-python 无宿主端口**——宿主机与浏览器都摸不到，只有同网络的 agt-backend 带 `X-Agent-Key` 能访问。
- **密钥不进镜像**：三个服务用 `env_file` 读宿主机 `agt_python/.env`
  （`AGENT_SHARED_KEY` / `LLM_API_KEY` 只存在于宿主文件与容器环境）。
- **数据不进镜像**：命名卷 `agt-data` 挂 `/app/data`（`DATA_ROOT` 外置），
  `down` 不丢数据，`down -v` 才会。与形态一的 `agt_python/data` **互不相通**。
- 无人机主控（8060）不在 compose 里（在 jsdstu-3 主控机）：8080 经 `host.docker.internal:8060` 找它，
  不在场时 drone 类工具走既有降级路径（fault_event 有账）。

### 8.3 实测验收（2026-09-24 全过）

| # | 命令/动作 | 期望 |
|---|---|---|
| 1 | `curl -o /dev/null -w "%{http_code}" http://127.0.0.1:9090/` | `200`（nginx 页面） |

| 5 | 登录后 `POST /v1/agent/chat/stream`（经 9090） | SSE 逐字：`meta` → `delta`×N → `done`（实测 19 个 delta，usage `source=api`）——**nginx 必须带 SSE 三件套，漏了就是"卡半天蹦全段 + 504"** |

### 8.4 国内网络实测坑（交付前必读）

- **基础镜像拉取**：Docker Hub 直连拉 `python:3.11-slim` 卡死 25 分钟层都不解压。
  实测可用做法：经国内镜像源预拉再打回正名——
  `docker pull docker.m.daocloud.io/library/<镜像> && docker tag … <镜像>`；
  拉取"Download complete 后卡住不动"时**杀掉重拉**，层缓存生效后几十秒完成（maven 镜像实测）。
- **pip 源**：清华 pypi 的 `/simple/` 索引能拿到、`/packages/` CDN 对容器内请求回 **403** → 用阿里云源
  （`mirrors.aliyun.com/pypi/simple/`）。
- **Maven**：走阿里云镜像源（`deploy/docker/maven-settings.xml`）。⚠️ 该文件是 XML——**注释里不能写
  `#`，注释内部也不能出现 `--`**（两种写法都实测让构建报 `Non-parseable settings`）。
- **npm**：`npm config set registry https://registry.npmmirror.com` 后 `npm ci`，2.5 分钟出构建。
- **端口冲突**：形态一在跑时 9090/8080 被占。干净机器无此问题；同机切换形态时先停另一形态。
- 沙箱/脚本环境里 docker build 的**管道输出会被 SIGTERM**：一律 `> 日志 2>&1` 再看日志。

## §9 CI 门禁（改完立刻知道有没有改坏）

**先用这一条**：改完代码，跑

```bash
bash scripts/ci.sh
```

约 **73 秒**拿到三端结论（本地实测 python ~19s + java ~17s + web ~24s + matrix ~1s + deps ~2s）。

### 9.1 本地门禁（日常就用这个）

```bash
bash scripts/ci.sh                  # 五作业全跑：Python 单测 / Java 单测 / 前端构建 / 权限矩阵 / 依赖漏洞扫描
bash scripts/ci.sh python java      # 只跑指定作业（只改后端时省时间）
bash scripts/ci.sh matrix           # 只跑权限矩阵门禁（秒级；改权限/治理相关代码后先跑它）
bash scripts/ci.sh deps             # 只跑依赖漏洞扫描（秒级、离线；改了依赖后先跑它）
bash scripts/ci.sh --list           # 列出可用作业
bash scripts/ci.sh --fresh          # 前端强制重装依赖（npm ci）后再构建
```

- **退出码**：`0` = 全过；非 `0` = 有作业失败 → 可直接挂到 `pre-push` 钩子。
- 完整输出落 `deploy/ci-logs/<job>.log`；控制台只给结论 + 失败输出末尾 25 行。
- **不依赖任何外部服务**：不需要 Milvus、8060，也不需要 8000/8080 在跑。
- ⚠️ **让它在前台跑完**：同一条命令，前台执行 web 作业 **16s**；若命令被挂到后台执行，
  实测 vue-cli 自报 `Time: 2897207ms`（≈48 分钟）——而 python/java 作业不受影响。
  这是**执行环境节流**，不是仓库或构建配置的问题：**看到 web 作业莫名几百秒别改 webpack 配置**，
  先做「同命令前台重跑」对照再归因（完整定位过程见 `DEV_ISSUES.md` §6.77）。

### 9.2 五个作业各在验什么

| 作业 | 命令（口径） | 现状 | 耗时 |
|---|---|---|---|
| python | `python -m pytest`（口径在 `agt_python/pytest.ini`） | **338 passed** / 4 项既有基线**显式 deselect** | ~19s |
| java | `mvn -B test`（含透传契约与权限端到端） | **151 passed / 0 failed** | ~17s |
| web | `npm ci && npm run build` | 构建通过 | ~24s |
| matrix | `python scripts/check_permission_matrix.py` | **49 行 / 49 端点 / 22 处判定点全部覆盖** | ~1s |
| deps | `python scripts/scan_deps.py`（离线快照口径） | **Critical 0**（7 条已处置）· High 11（告警不阻断） | ~2s |

五作业前台实测合计 **≈73s**（规约要求 ≤10 分钟）。

> **第四个作业（matrix）在验什么**：`docs/权限矩阵.md` 与代码必须一致——
> 矩阵每一行的 `文件:行` 都要能在源码里找到、且片段确实存在；反过来代码里的端点与判定
> 也不能有未登记项。它守的是**"文档写了代码没做"**这类漂移。
> 零第三方依赖、断网可跑，所以**不接任何外部服务**。
> 代价是它只认 `<!-- PERMISSION-MATRIX:BEGIN/END -->` 标记块内的行，块外散文表格不校验。

> **第五个作业（deps）在验什么**（E-11）：交付包**不能带已知未处置 Critical**。
> 它扫三端依赖闭包（Python / Java / npm）→ 走 **OSV** 查漏洞 → **Critical 阻断、High 告警**。
> **离线可跑**（读入库的 `security/*.json` 快照，不联网），故与 matrix 一样不依赖外部服务。
> ⚠️ **退出码有两个**，别混：`1` = 有未处置 Critical（或豁免台账违规）；
> `2` = **快照过期**（改了依赖没刷新快照）——2 也是失败，但含义不同，看报告最后一行。
> ⚠️ **别只看退出码**：退出码 0 只保证"无未处置 Critical"，`High` 与 `UNKNOWN` 严重度都要看报告；
> `UNKNOWN` **不等于安全**，是本工具对"数据库没给分级"的**显式列出**。
> 要联网刷新快照：`python scripts/scan_deps.py --refresh`（日常 CI 不用跑这个）。
> 详见 `docs/依赖与漏洞处置.md`。

> **关于那 4 项既有基线失败**：它们是 `test_agent_api.py` 里「业务关键词路由」重构后未同步的旧断言，
> 与后续改动无关。`pytest.ini` 用 `--deselect` **逐条显式列出**，而不是忽略失败——
> 这 4 项之外任何失败都会让退出码非 0。
> 想看含这 4 项的全量：`python -m pytest --override-ini="addopts="`。

> **Java 测试为什么值得单独说**：E-5 之前 Java 侧是 **0 测试**。现在 151 项里最要紧的一组是
> **透传契约**——它守着「每个直连 Python 的出口都带 `X-Agent-Key`」。漏掉这个头不会有编译错误，
> 只会让那个业务域**整体 4010**（前端弹「登录已过期」），排查方向极易被带到会话上去。
> 想验证这组测试真的有效：删掉 `AgentAuth.withKey` 里的 `defaultHeader`，
> `AgentClientContractTest` 会立刻红 **5 项**。

### 9.3 远端流水线（push 后自动跑）

| 文件 | 平台 | 说明 |
|---|---|---|
| `.workflow/ci.yml` | **Gitee Go（主力）** | 仓库托管在 Gitee，用这个 |
| `.github/workflows/ci.yml` | GitHub Actions（备选） | 将来迁到 GitHub 时沿用，与本地五作业逐条对应 |

> ⚠️ **远端 yml 尚未同步第五作业 `deps`**（本地 `scripts/ci.sh` 已五作业）。
> 按项目约定代码未 push、远端流水线本就未激活，故首次 push 时**一并补齐** `deps` 作业再验证首次全绿。

**⚠️ 光 push `ci.yml` 不会自动创建流水线**，需在网页端建立一次：

1. 打开仓库 → 顶部 **DevOps** → **Gitee Go**；
2. **新建流水线** → 代码视图 / 从仓库导入，选中 `.workflow/ci.yml`；
3. 保存。此后 push 到 `master` 才会按 `triggers` 自动触发。

**分支保护**（建议，需仓库管理员权限）：

1. 仓库 → **管理** → **分支设置** → 保护分支规则，添加 `master`；
2. 勾选**状态检查通过后才允许合并**并选中本流水线；
3. 保存后，CI 未过就无法合入 `master`。

> **现状（如实记录）**：本地门禁已实测通过，并**验红一次**（删掉鉴权头 → 5 项变红，已还原）。
> 远端流水线的「首次全绿」**尚未验证**——按项目约定代码未 push，
> 且 Gitee Go 需先在网页端建立流水线对象。

## §10 卸载与清理

```powershell
# 1) 停服务（不删任务定义）
powershell -ExecutionPolicy Bypass -File deploy\scripts\stop-all.ps1

# 2) 删计划任务
powershell -ExecutionPolicy Bypass -File deploy\scripts\install-tasks.ps1 -Uninstall

# 3) 停 Milvus（保留数据）
cd deploy/milvus && docker compose -p milvus down

# 4) 彻底清库（⚠️ 数据全灭，先备份）
#    docker compose -p milvus down -v   并且删除 deploy/milvus/volumes/
```

> 业务数据（`agt_python/data/`）与日志（`deploy/logs/`）**不会被任何脚本自动删除**——
> 需要清理时请人工确认后删除。
