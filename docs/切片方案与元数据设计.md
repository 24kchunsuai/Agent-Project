# 切片方案与元数据设计

> 起因：用户质疑「你是按固定大小切的 chunk 吗？600 字基本等于 1k token 了，
> 筛几条就接近五六 k token」，并建议参考 AgentCraft 的切片方案
> （100~500、按语义段落切、短块合并、长段定长切 + overlap）。
>
> 核查结论：**质疑成立，而且我上一轮的结论有实验方法缺陷。**

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| 我原来是固定大小切吗 | **不是纯定长**，但**无标题文档会退化成近似定长**（缺陷，已修） |
| 600 字有多大 | 实测片长均值 402 字、p90 575 字；**top5 共 2010 字 ≈ 1340~2010 token** |
| 该用多大 | **建议 400（预算制硬上限）+ overlap 80 + 最小区块 100** |
| AgentCraft 的参数 | `CHUNK_SIZE=500 / CHUNK_OVERLAP=50 / MIN_CHUNK_SIZE=100` ✅ 您记得对 |
| AgentCraft 的 overlap | ⚠️ **死配置**，`split_text()` 里根本没实现 |
| 元数据 | 原来只存 6 个字段，**`owner`（鉴权）与引用定位信息全丢了**（已补齐至 19 个） |
| 上一轮"切片不宜缩短"的结论 | ❌ **错误**，实验用 `truncate` 截断而非语义切分，方法有缺陷 |

## 二、出发点：核查 AgentCraft 的真实切片实现

配置文件 `core/config.py`：

```python
self.CHUNK_SIZE = int(os.getenv("CHUNK_SIZE", "500"))
self.CHUNK_OVERLAP = int(os.getenv("CHUNK_OVERLAP", "50"))
self.MIN_CHUNK_SIZE = int(os.getenv("MIN_CHUNK_SIZE", "100"))
```

算法在 `core/text_splitter.py` 的 `SemanticChunkerSplitter`，流程是：

```
_clean_text          清理多余空白、全角空格
  ↓
_split_by_paragraphs 按 \n\s*\n 或 \n 切段
  ↓
段落依次累加到 chunk_size=500 上限
  ↓ 单段 > 500
_split_long_paragraph 按句子切（。！？；\n）
  ↓ 单句 > 500
_split_by_punctuation 按标点切
  ↓
_merge_small_chunks  长度 < min_chunk_size(100) 的与下一段合并
```

**值得借鉴的地方**：段落聚合 + 句子下探的分层思路是对的，`min_chunk_size` 抑制碎片的意识也对。

### 但有两个实现缺陷

#### 缺陷 1：`chunk_overlap` 是死配置

```python
def __init__(self, chunk_size=500, chunk_overlap=50, ...):
    super().__init__(chunk_size=chunk_size, chunk_overlap=chunk_overlap)
    self.fallback_splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size, chunk_overlap=chunk_overlap, ...)   # ← 定义了

def split_text(self, text):        # ← 但全文没有任何 overlap 逻辑
    ...
    chunks = self._merge_small_chunks(chunks)
    return chunks                   # fallback_splitter 从未被调用
```

配置里写着 50 的 overlap 实际完全不生效。**用户以为的"有 overlap"是假的。**

#### 缺陷 2：`_merge_small_chunks` 无上界检查

```python
for i in range(1, len(chunks)):
    if len(current) < self.min_chunk_size and i < len(chunks):
        current += self.separator + chunks[i]      # 只累加，不检查是否超过 chunk_size
    else:
        merged.append(current.strip())
        current = chunks[i]
```

连续短段会被累加成一个**远超 500 的巨块**，且只做向后吸收（前片无容量时不处理）。

## 三、我的实现的两个问题

### 问题 1（严重）：`max_chars` 名不副实

原实现：

```python
for piece in recursive_split(content, CHUNK_SIZE, SEPARATORS):   # 正文 ≤ 600
    prefix = f"【{title}】" + (f"「{heading}」" if heading else "")  # 前缀额外叠加
    ...
chunks[i]["text"] = prev[-80:] + "\n" + chunks[i]["text"]          # overlap 再叠加
```

**`max_chars` 只约束正文，标题前缀与 overlap 是额外开销。**

实测（配置 600）：

| 指标 | 数值 |
|---|---|
| 最大片长 | **835**（超出 39%） |
| p90 | 688 |
| **超过 600 字的片占比** | **30.9%** |
| 拆解 | 80(overlap) + 1 + 154(最长前缀) + 600 = **835** ✓ 完全吻合 |

这意味着"chunk 大小"这个参数**名不副实**，配 600 实际拿到的是 300~835 的混合分布。

### 问题 2：无标题文档退化成近似定长切

`split_sections()` 按 markdown 标题切段。第三方语料里有整篇没有 `#` 标题的文件，
此时整个 body 变成一个 giant section → 直接进 `recursive_split` 硬切。

**这正是"固定大小切"的真实来源。** 已修：检测到"单 section 且无标题"时，
退化为按空行切段。

### 修复：预算制切分

```python
prefix = f"【{title}】" + (f"「{heading}」" if heading else "")
cap = int(max_chars * 0.3)
if len(prefix) > cap:
    prefix = prefix[:cap]              # 前缀过长时截断，保证正文预算

# 最终片长 = 前缀 + 正文 + overlap段 + 换行 ≤ max_chars
budget = max(max_chars - len(prefix) - overlap - 2, 80)
for piece in recursive_split(content, budget, SEPARATORS):
    ...
```

修复后**所有方案最大片长精确等于配置值**（599 / 500 / 400 / 300），超限率 0%。

## 四、五方案离线对比

语料：76 篇（自有 25 + 第三方 51）/ 41.5 万字。
参数含义：`max_chars / overlap / min_chunk`。

| 方案 | 合并策略 | 片数 | 最小 | 中位 | 均值 | p90 | 最大 | <100字 | <150字 | **>上限** |
|---|---|---|---|---|---|---|---|---|---|---|
| A 600/80/200 | 向前 | 1196 | 60 | 416 | 402 | 575 | 599 | 0.4% | 2.5% | **0.0%** |
| B 500/50/100 | 双向 | 1476 | 75 | 302 | 314 | 461 | 500 | 1.4% | 3.7% | **0.0%** |
| **C 400/80/100** | **双向** | **1965** | 65 | 296 | 285 | 386 | 400 | **0.3%** | 6.3% | **0.0%** |
| D 300/60/100 | 双向 | 2567 | 42 | 238 | 224 | 291 | 300 | 3.0% | **14.1%** | **0.0%** |
| E 400/80/100 | 向前 | 1992 | 57 | 292 | 281 | 386 | 400 | 0.6% | 6.8% | **0.0%** |

对比修复前的方案 A（供参照）：**934 片 / 中位 474 / 均值 480 / p90 688 / 最大 835 / 超限 30.9%**

### 上下文预算（取 top5 切片）

| 方案 | 期望总字数 | 乐观 token(1.5字/tk) | 保守 token(1字/tk) | 相对 A |
|---|---|---|---|---|
| A 600 | 2010 | 1340 | 2010 | — |
| B 500 | 1568 | 1045 | 1568 | −22% |
| **C 400** | **1423** | **949** | **1423** | **−29%** |
| D 300 | 1118 | 746 | 1118 | −44% |

> **关于 token 估算**：GLM / DeepSeek 官方口径约 1 token ≈ 1.5~1.8 个汉字，
> 即 600 字 ≈ 333~400 token。您估的「600 字 ≈ 1k token」（1.67 字/token）
> 偏保守，但**方向完全正确**——top5 取到 2010 字时，实际开销确实在 1300~2000 token 区间。

### 三个可读出的结论

1. **400 是甜点**：碎片率（<100 字）仅 0.3%，与 600 方案持平，但上下文开销省 29%
2. **300 太小**：<150 字的碎片率跳到 14.1%，是 400 方案的 2.2 倍。
   短碎片信息量不足、向量语义模糊，反而拉低召回——**300 是下界信号**
3. **合并策略影响不大**：C（双向）1965 片 vs E（向前）1992 片，差异 1.4%。
   说明只要上界检查到位，单向/双向差别有限；**但上界检查必须要有**（AgentCraft 就缺）

### 与 AgentCraft 参数的关系

AgentCraft 的 500 对应本表 B，处在 A 与 C 之间。**它比我原来的 600 合理，
但比 400 略大。** 考虑到它切的是 PDF/OCR 混合来源（文本更碎），500 对它是合适的；
我们的语料以结构清晰的 markdown 为主，可以更激进地用 400。

## 五、参数建议（已落地到 `app/rag/chunker.py`）

```python
@dataclass(frozen=True)
class ChunkConfig:
    max_chars: int = 400          # 最终片长硬上限（预算制）
    overlap: int = 80             # 相邻片重叠
    min_chunk: int = 100          # 低于此长度的段落尝试合并
    min_section: int = 40         # 低于此长度的段落直接丢弃
    prefix_ratio_cap: float = 0.3 # 标题前缀最长占 max_chars 的比例
```

同步写入 `app/core/config.py`（可从 .env 覆盖）：

```
RAG_CHUNK_SIZE=400
RAG_CHUNK_OVERLAP=80
RAG_CHUNK_MIN=100
```

## 六、元数据设计（对应您说的「鉴权过滤 + 引用追踪」）

### 原实现丢了什么

语料 frontmatter 里本来就很丰富：

```yaml
# 自有语料
doc_id / title / category / source / version / updated / owner

# 第三方语料
doc_id / title / category / source / source_type / source_commit_date
license / owner / lang / imported_by
```

但原建库 schema **只存了 5 个**：`chunk_id / doc_id / title / category / origin / text`。

**丢弃的字段**：`owner`（鉴权隔离的关键）、`source`（溯源）、`version`/`updated`（时效）、
`license` / `source_type`（合规）、`lang`。
**缺失的字段**：任何引用定位信息（章节路径、片序号、字符偏移）。

### 新 schema（19 个字段，三类用途）

| 用途 | 字段 | 说明 |
|---|---|---|
| **主键** | `id` | INT64 自增 |
| **引用追踪** | `chunk_id` | `{doc_id}#{n}`，全局唯一，增量更新锚点 |
| | `doc_id` | 文档标识 |
| | `doc_title` | 文档标题（引用卡片显示） |
| | `heading` | 所属章节标题（引用卡片显示） |
| | `chunk_index` / `total_chunks` | 在文档中的位置（"第 2/10 段"） |
| | `char_start` / `char_end` | 在正文中的字符偏移（前端原文高亮定位） |
| **鉴权过滤** | `owner` | 归属主体，检索时 `filter` 使用 |
| | `visibility` | `public` / `private` |
| **分类与时效** | `category` | 分类（可按类过滤检索） |
| | `source` | 来源（`caac` / `self` / `github:xxx`） |
| | `source_type` | `official` / `self` / `third_party_github` |
| | `doc_version` / `doc_updated` | 时效性过滤与展示 |
| | `lang` | 语种 |
| **内容** | `text` | 原文（中文分析器 + BM25 来源） |
| | `char_len` | 片长（可用于过滤异常片） |
| **向量** | `dense` | 稠密向量（GLM embedding-3，2048 维） |
| | `sparse` | 稀疏向量（BM25 Function 自动生成） |

### 鉴权过滤用法

```python
client.hybrid_search(
    collection_name=coll,
    reqs=[sparse_req, dense_req],
    ranker=RRFRanker(),
    limit=20,
    filter='owner in ["default", "user_123"] and visibility == "public"',
)
```

`owner` / `visibility` / `category` / `doc_id` 需建 **INVERTED 标量索引**，
否则过滤会退化成全表扫描。

### 引用追踪用法

```python
# 前端引用卡片：文档标题 + 章节 + 位置
f"《{hit['doc_title']}》· {hit['heading']}（第 {hit['chunk_index']+1}/{hit['total_chunks']} 段）"
# 原文定位：拿 char_start / char_end 回原文档高亮
```

## 九、本次踩坑（已同步至 DEV_ISSUES.md）

1. ⭐ **chunk 参数必须约束"最终片长"而非"正文长度"**，否则前缀与 overlap 叠加，
   实测超限 39%（配 600 出 835 字片）
2. ⭐ **AgentCraft 的 `chunk_overlap` 是死配置**——读别人的代码要验证参数是否真的生效，
   不能只看配置文件
3. ⭐ **缩短切片要用"语义完整的小块"，不能用 `truncate` 截断**——
   截断破坏语义，得到的结论是错的（这正是上一轮误判的根源）
4. **Milvus 标量过滤字段必须建 INVERTED 索引**，否则全表扫描
5. **GLM 错误码 1113 = 余额不足**（返回 HTTP 429，容易被误判为限流；
   若只看到 429 会误以为重试能解决，实际重试必然失败）
6. **限流保护三件套**：批次间 sleep + 429 指数退避 + 查询向量预计算复用
