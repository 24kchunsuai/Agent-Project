## 1. 版本

| 项 | 值 | 来源 |
|---|---|---|
| 版本号 | 见仓库根 `VERSION` | **唯一来源**，其它任何位置不得独立定义版本 |
| 变更记录 | `CHANGELOG.md` | Keep a Changelog 格式 |
| 构建画像 | `version` / `gitCommit` / `gitBranch` / `gitDirty` / `buildTime` | `scripts/stamp_version.py` 打戳产物 |

**唯一版本来源原则**：`VERSION` 是唯一可写版本号的地方。
三端（Python `app_version`、Java `build-info.properties`、前端 `version.json`）
都从这里派生，派生动作由脚本完成，人不再手工改第二处。

变更版本的正确顺序（顺序反了会被门禁拦下）：

1. 改 `VERSION`
2. 在 `CHANGELOG.md` 顶部补 `## [新版本]` 条目
3. 跑 `scripts/stamp_version.py`
4. 跑 `scripts/stamp_version.py --check` 确认一致

## 3. 部署前置

### 3.1 运行环境

| 组件 | 版本要求 | 说明 |
|---|---|---|
| Python | 3.11+ | agent 端；实测 3.11.15 |
| JDK | 17+ | 后端；实测 17 |
| Node.js | 16+ | 仅前端**构建**时需要；运行时由 nginx 托管静态文件 |
| Docker | 任意近期版本 | 跑 Milvus 依赖栈（etcd + minio + standalone） |

### 3.2 必须准备的外部依赖

1. **Milvus 向量库**：`cd deploy/milvus && docker compose -p milvus up -d`
   等待约 60~90 秒完成初始化。
2. **LLM API Key**：写入 `agt_python/.env` 的 `LLM_API_KEY`（未配置时 `/v1/health` 报 `llmConfigured:false`，服务仍可启动但无法回答）。
3. **服务间共享密钥**（S-1 铁律，**两边必须同值**）：
   - 生成：`python -c "import secrets; print(secrets.token_urlsafe(32))"`
   - Python 侧：`agt_python/.env` 的 `AGENT_SHARED_KEY`
   - Java 侧：环境变量 `AGENT_SHARED_KEY`（本机走 `deploy/secrets/agent.key` + `start-backend.cmd`）
   - **留空则 Python 服务拒绝启动**（fail-closed 设计，不是故障）

### 3.3 端口占用

| 端口 | 服务 | 绑定 |
|---|---|---|
| 8000 | agt_python | **127.0.0.1**（只服务本机，S-1） |
| 8080 | agt_backend | 对外 |
| 9090 | agt_web | 对外（生产由 nginx 托管，见 E-14） |
| 8060 | jsdstu-3 无人机主控 | 外部既有系统 |
| 19530 | Milvus | 本机 |

## 4. 验收步骤

以下命令均为**只读**，可在生产环境直接执行。
Windows 上如遇代理干扰，`curl` 加 `--noproxy '*'`。

### 4.1 版本可回答（E-1 核心验收）

```bash
# agent 端：版本 + 提交 + 构建时间 + 工作区是否干净
curl -s -H "X-Agent-Key: $AGENT_SHARED_KEY" http://127.0.0.1:8000/v1/health
```

期望：`code=2000`，且 `data` 中

- `version` 等于包内 `VERSION` 的内容
- `gitCommit` 为短 hash，或显式标记 `unborn@<分支>` / `no-git`（**不会是空串**）
- `gitDirty=false`（若为 `true`，说明这份包含未提交改动，**不可复现**，应退回）
- `buildTime` 非空
- `versionSource=stamp`（交付包应为打戳产物；`runtime` 说明漏跑打戳）

```bash
# 后端：Java 侧版本（含 Java 运行时信息）
curl -s http://localhost:8080/v1/version
```

期望：`stamped=true`、`version` 与包内 `VERSION` 一致。

```bash
# 前端：静态版本文件
curl -s http://localhost:9090/version.json
```

期望：`version` 与包内 `VERSION` 一致。页面「关于」页底部同时展示该信息。

### 4.2 三端一致性（一条命令验完）

```bash
python scripts/stamp_version.py --check
```

期望：输出 `版本一致性校验通过`。它同时核对 `VERSION` / `CHANGELOG` /
三端产物 / `package.json`，任何一处不同版本都会列出并返回退出码 1。

### 4.3 链路可用

```bash
curl -s -H "X-Agent-Key: $AGENT_SHARED_KEY" http://127.0.0.1:8000/v1/kb/stats
```

期望：`code=2000` 且带 `docCount` / `chunkCount` —— 这是 Milvus 真正可用的判据
（容器 `healthy` 不算，见 `three-tier-agent-scaffold` 技能里的坑）。

### 4.4 日志可按 traceId 串起来（E-6）

```bash
# 1) 任意接口的发现在响应头里（traceId 由 Java 生成）
curl -s -D - -o /dev/null http://127.0.0.1:8080/v1/kb/stats | grep -i x-trace-id
# 2) 用该 traceId 串 Java 与 Python 两侧
grep -h "<上一步的 traceId>" deploy/logs/8080-agt_backend.jsonl deploy/logs/8000-agt_python.jsonl
```

期望：第 2 步能同时打出两侧日志、且字段里有同一个 `traceId`（一次请求跨两端）。
仅 Java 侧有、Python 侧没有 → 转发出站漏加链路头（见 `docs/部署手册.md` §7.7）。
字段含义与脱敏口径见 `docs/日志规范.md`。

### 4.5 指标可被 Prometheus 抓取（E-9）

```bash
# 匿名走 8080（推荐）：Java 段 + 透传 Python 段，双段合并
curl -s --noproxy '*' http://127.0.0.1:8080/v1/ops/metrics | head -40

# 关键一行：1=Python 段已拼上，0=Python 不可达（端点已降级，但 HTTP 仍是 200）
curl -s --noproxy '*' http://127.0.0.1:8080/v1/ops/metrics | grep agt_java_python_section_ok

# 带密钥直连 8000，只看 Python 侧
curl -s --noproxy '*' -H "X-Agent-Key: <key>" http://127.0.0.1:8000/v1/ops/metrics | head -40
```

**期望**：`Content-Type: text/plain; version=0.0.4`；含 `HELP`/`TYPE` 成对声明；
`agt_java_python_section_ok 1`。**不接 Prometheus 时也零影响**（只读既有 ODS 表与内存计数器，
SQLite 以 `mode=ro` 打开且不创建库文件）。口径与三个易读错的点见部署手册 §7.8。

### 4.6 操作可追溯（E-8）

**判据原文是"能回答谁在什么时候改了什么"**，所以验收要真跑一遍三类动作、再回审计里找出来。

```powershell
$t = (Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/v1/auth/login `
      -ContentType 'application/json' -Body '{"username":"admin","password":"123456"}').data.token
$h = @{ Authorization = "Bearer $t" }

# ① 先做三件事：登录（上一步已完成，已留痕）→ 危险操作 → 停用一篇文档
#    （三件事的具体命令见 §4.3；这里只查结果）

# ② 按 id 倒序取最近 3 条：应能看出"登录 → 危险操作 → 停用文档"这一序列
(Invoke-RestMethod -Uri 'http://127.0.0.1:8080/v1/kb/governance/audit?pageSize=3' -Headers $h).data.items |
  Select-Object id, action, target, result, ip, traceId, ts

# ③ 按对象筛选：前缀匹配，一次捞出所有工具类动作
(Invoke-RestMethod -Uri 'http://127.0.0.1:8080/v1/kb/governance/audit?target=tool:&pageSize=20' -Headers $h).data.total

# ④ 导出（服务端导出，返回 JSON 信封，内容在 data.content，含 BOM）
$d = (Invoke-RestMethod -Uri 'http://127.0.0.1:8080/v1/kb/governance/audit/export' -Headers $h).data
"$($d.filename)  rows=$($d.rows)  truncated=$($d.truncated)"
```

**期望**：

1. 第 ② 步三条按时间序能读出**一条完整动作链**，每条七维齐全；`traceId` 与 §4.4 日志里的**是同一个值**。
2. 第 ③ 步能筛出确认门事件（`TOOL_CONFIRM_ALLOW` / `TOOL_CONFIRM_DENY`）。
3. 第 ④ 步 `rows>0`、文件以 `audit_` 开头、用 Excel 双击打开**中文列名不乱码**（BOM 生效）。
4. **无令牌时三条审计接口都返回 4010**；非管理员令牌返回 **4011**（有身份但权限不够）。

**三个必须知道的边界**（否则会把"正常"当成"坏了"）：

| 现象 | 真相 |
|---|---|
| 老数据按 `target=doc:` 只筛出一部分 | E-8 之前的行**库里没有 `target`**，是**读取时**用 `doc_id` 派生的；当时没记账号/工具事件，所以筛不到——**数据本来就不存在**，不是筛选坏了 |
| 治理动作那部分 `ip` 为空 | 目前**只有账号事件带 `ip`**（Java 侧才拿得到请求来源），已知边界见 `docs/审计清单.md` §10 |
| 停掉 8000 后登录仍成功、但查不到这次登录的审计 | **有意的取舍**：审计是事后能力，**不能反过来变成"登录失败"的原因**。宁可丢一条审计，也不拒绝登录 |

口径与五个最容易读错的点见 `docs/部署手册.md` §7.9。

### 4.7 密钥可轮换 + 权限可核（E-10）

**判据 C5 的第二半**：密钥换得动、权限说得清，而且**两件事都被机器校验**，不靠人记得。

```bash
# ── ① 权限矩阵与代码一致（五项校验，退出码 0 = 通过）──
python scripts/check_permission_matrix.py
python scripts/check_permission_matrix.py -v      # 逐行打印核对结果
```

**期望**：`49 行 / 49 端点 / 22 处判定点全覆盖` + `通过：...`。
若出现 `[A]` 说明**加了端点没登记进矩阵**；`[B]` 说明**矩阵引用的代码不存在**（文档写了代码没做）；
`[C]` 说明**标了权限但其实没判**；`[D]` 说明**代码加了校验但矩阵漏登记**；
`[E]` 说明**受保护的端点被错标成匿名**。

```bash
# ── ② 双密钥轮换能力（不停服换密钥的前提）──
python -c "import secrets; print(secrets.token_urlsafe(32))"      # 生成新密钥 K2

# 在 agt_python/.env 里：AGENT_SHARED_KEY=<K2>  AGENT_SHARED_KEY_PREV=<K1>  然后重启 8000
# 自检会报"轮换进行中：Java 仍在用旧密钥"（这是**正常中间态**，不是 FAIL）
python deploy/scripts/preflight.py | grep -A1 轮换
```

**期望**：轮换期**两把密钥都能通过鉴权**。可直接验：

```bash
# 两把都应放行（走到路由层 → 3002 而不是 4010）
curl -s --noproxy '*' -H "X-Agent-Key: <K2>" http://127.0.0.1:8000/v1/definitely-not-a-route
curl -s --noproxy '*' -H "X-Agent-Key: <K1>" http://127.0.0.1:8000/v1/definitely-not-a-route

# 旧密钥的使用被计数（用它当"能不能清掉 PREV"的判据；它**不进故障数**）
curl -s --noproxy '*' -H "X-Agent-Key: <K2>" http://127.0.0.1:8000/v1/ops/metrics \
  | grep auth_key_legacy_used
```

⚠️ **顺序不能反**：必须**先**让 8000 收两把，**再**把 Java 换成 K2（改 `deploy/secrets/agent.key` 并重启 8080）。
反过来做会在中间稳定 4010。完整步骤与三个坑见 `docs/密钥与配置管理.md` §3.3/§3.4。

⚠️ `AGENT_SHARED_KEY_PREV` **与当前密钥同值会被拒绝启动**（服务起不来是**期望行为**，不是故障：
两把一样说明"以为在轮换其实没换"）。

### 4.8 依赖无已知未处置 Critical（E-11）

**判据 C1 的第二半**：交付包里不能带着"已知能被打的漏洞"。一条命令验完，**断网可跑**：

```bash
python scripts/scan_deps.py                 # 控制台报告；退出码见下
python scripts/scan_deps.py --markdown      # 输出 Markdown（可贴工单）
python scripts/scan_deps.py --refresh       # 联网刷新 security/*.json 快照后再扫
```

**退出码**（可挂 CI / 发布门禁）：

| 码 | 含义 |
|---|---|
| `0` | 通过（无未处置 Critical；豁免台账合规；快照未过期） |
| `1` | **阻断**：存在未处置 Critical，或豁免台账违规（缺字段 / 已过期 / 日期格式错） |
| `2` | **快照口径问题**：`security/*.json` 与当前依赖闭包不一致（说明改了依赖没刷新快照） |

**期望**：本版本退出码为 `0`，报告里 **Critical = 0**（原 7 条已通过覆盖 `tomcat-embed-core` 至 `10.1.60` 消除）；
`High` 会列出但**不阻断**（当前 11 条，均在 Spring 托管的 Jackson 栈内，处置路径见 `docs/依赖与漏洞处置.md`）。

⚠️ **两种"看起来正常"的陷阱**（详见 `docs/依赖与漏洞处置.md` §6）：

| 现象 | 真相 |
|---|---|
| 报告里有 `UNKNOWN` 严重度条目 | **不是"安全"**，而是数据库没给分级。本工具会**显式列出**而不是丢弃——见到 `UNKNOWN` 要人工判一次，不能当无事 |
| `deps` 作业退出码 0、但仍想确认 | **别只看退出码**：退出码 0 只保证"无未处置 Critical"，`High` 与 `UNKNOWN` 一律要看报告 |

### 4.9 前端报错可在看板看到（E-12）

**判据 C3 的第四半**（前三半是 E-3 健康聚合 / E-6 日志 / E-9 指标）：**浏览器侧**崩了要留痕。
分两段验——**服务端链路**可以用命令验完，**浏览器那一段**只能用真浏览器验。

**① 服务端链路（命令可验，断网可跑；不需要浏览器）**

```bash
KEY=$(cat deploy/secrets/agent.key)

# 1) 8000 直连上报：身份走查询参数，body 里塞 userId 必须无效
curl -s --noproxy '*' -X POST "http://127.0.0.1:8000/v1/ops/client-error?user_id=42" \
  -H "X-Agent-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"page":"/x?docId=1#h","source":"vue","message":"probe","appVersion":"1.0.0","userId":999}'
# 期望 code=2000，data.accepted=true，data.bucket 是当前分钟（如 2026-09-24T17:04:00）

# 2) 无密钥必须被拒（S-1）
curl -s --noproxy '*' -X POST "http://127.0.0.1:8000/v1/ops/client-error" -d '{}'
# 期望 code=4010

# 3) 8080 匿名转发（浏览器打的是这个；浏览器不可能持有服务间密钥）
curl -s --noproxy '*' -X POST "http://127.0.0.1:8080/v1/ops/client-error" \
  -H 'Content-Type: application/json' -d '{"page":"/y","source":"promise","message":"probe2"}'
# 期望 code=2000（登录页崩溃时也要能上报，故刻意匿名）

# 4) 看板数据源（聚合 + 合并口径）
curl -s --noproxy '*' "http://127.0.0.1:8000/v1/agent/metrics/client-errors?hours=24" -H "X-Agent-Key: $KEY"
```

**期望**：`distinct` = 不同错误**类数**（按 `页面+来源+消息` 指纹去重），`total` = `count` 之和；
`byPage[].name` 里**不应出现 `?` 或 `#`**（查询串与 hash 已在服务端剥掉）。

**② 合并去重（口径验收：同一错误 1 分钟合并）**

把上面第 1 条**在 1 分钟内连发两次**，然后查第 4 条：
**期望**：`/x` 那一行 **count = 2、行数仍是 1**（同一 `(指纹, 1 分钟桶)` 合并写）。
跨分钟的两次同错会各占一行——这是**固定桶**的已知代价（换来的是"同一分钟必然合并"的确定性）。

**③ 浏览器端（必须真浏览器；这是规约验收的原文："人为抛错能在看板看到"）**

```text
1. 打开 http://127.0.0.1:9090，用 admin / 123456 登录
2. F12 → 控制台执行：__agtClientErrorSelfTest()
   期望返回 {"vue":true,"window":true,"promise":true}  ← 三条收口都接上了
   （其中 vue 那条是直接调用已安装的 handler：浏览器不允许外部伪造一次组件渲染异常，
     故它验的是"handler 已装上且能发包"，而不是"Vue 会把组件异常交给它"）
3. 再执行一次真实抛错：setTimeout(() => { throw new Error('E-12 验收') }, 0)
4. 执行：__agtClientErrorStats()
   期望 installed=true / enabled=true / appVersion 非空 / count ≥ 3
5. 打开左侧「数据中台 · 观测 → 🐞 前端错误」
```

**期望**：第 3 步的消息出现在**最新报错首行**，来源 `window.onerror`，**版本 `1.0.0`**
（空版本说明 `version.json` 未取到或别名没生效），**用户**是当前登录用户的 userId（由 Java 注入，
不是前端自报）；「按页面」「按版本」两张聚合图上能看到它。

**④ 可配置项**（规约验收的第二半："采样率与去重有配置项"）

| 配置 | 默认 | 含义 | 改法 |
|---|---|---|---|
| `CLIENT_ERROR_SAMPLE_RATE` | `1.0` | 采样率 0~1（1=全收）；配错值**收敛**到 [0,1] 而不是拒绝启动 | `agt_python/.env` |
| `CLIENT_ERROR_DEDUP_SECONDS` | `60` | 合并窗口；同一错误在该窗口内只占一行、count 累加 | 同上 |
| `CLIENT_ERROR_ENABLED` | `true` | 总开关；false 时接口仍返回 2000 但 `data.stored=false` + reason 说明 | 同上 |
| `CLIENT_ERROR_MAX_MESSAGE` / `_MAX_STACK` | `500` / `2000` | 入库前的截断长度（完整 stack 常有数 KB） | 同上 |

改完**必须重启 8000**（`python` 服务非 reload）。

**⑤ 两个易误判的口径**（先看这两条，再去查 bug）

| 现象 | 真相 |
|---|---|
| 看板 `total` 小于"我明明抛了很多次" | **正常**：前端同一页面加载内同一错误只上报一次（防网络风暴），`total` 是真实次数的**下界**；服务端再按 1 分钟合并。两处口径都不改 |
| 同一错误出现两行、时间差不到 1 分钟 | 两行必然**跨了桶边界**（如 `10:00:59` 与 `10:01:01`）。固定桶的已知代价，不是合并失效 |

### 4.10 成本可回答、配额可触发（E-13）

**① 成本数字与手工核算一致**（判据 C7 的第一半）

```bash
# 直连 8000（需密钥）：看成本聚合
curl -s --noproxy '*' -H "X-Agent-Key: $(cat deploy/secrets/agent.key)" \
  "http://127.0.0.1:8000/v1/agent/metrics/costs?days=7"

# data.byModel / byUser / byDept / daily；data.quota：{capTokens, exceededEventsToday}

# 8080 匿名同口径（看板走这条）
curl -s --noproxy '*' "http://127.0.0.1:8080/v1/agent/metrics/costs?days=7"
```

**手工核算口径**：`成本 = prompt_tokens × P₁ + completion_tokens × P₂`（P 单位**元/百万 token**，
配置在 `LLM_PRICE_JSON`）。例：价目 `{"m": {"prompt": 2.0, "completion": 8.0}}`、
窗口内 1,000,000 prompt + 1,000,000 completion → **¥10.00**，`costs_summary` 必须同值
（`tests/test_cost_quota.py` 里就有这道题）。

**浏览器**：登录 9090 → 「数据中台 · 观测 → 💰 成本与配额」：
四张 KPI 卡 + 按模型 BarList + 按用户/按部门表 + 日趋势。看板页脚就是口径出处。

```bash
# 2) 用任意账号在聊天页发一句话（或直接调 /v1/agent/chat/stream）：
#    期望：回答**照常返回**（超限不拒绝），流末多一个 quota 事件：

# 4) 验完把 QUOTA_USER_DAILY_TOKENS 还原为 0 并重启 8000
```

**③ 可配置项**

| 配置 | 默认 | 含义 | 改法 |
|---|---|---|---|
| `LLM_PRICE_JSON` | 空 | 价目表 JSON（元/百万 token）；未配价模型成本记 0、token 照记并单列 `unpricedTokens` | `agt_python/.env` |

**④ 三个易误判的口径**

| 现象 | 真相 |

| 症状 | 真相 |
|---|---|
| `docker build` 拉基础镜像卡 20+ 分钟不动 | 国内直连 Docker Hub 的常态，不是构建坏了。经 `docker.m.daocloud.io` 预拉再打回正名；"Download complete 后长期不动"就杀掉重拉（层缓存生效，秒级完成） |

| 容器里无人机工具全部降级 | 8060 主控在无人机主控机上，不在 compose 里；8080 经 `host.docker.internal:8060` 找它，不在场走既有降级路径 |

## 6. 发布流程（谁在什么时候跑什么）

```bash
PYTHON=/d/install/python/anaconda/envs/python311/python.exe \
  bash scripts/release.sh --dry-run      # 先演练：只检查、只打印
```

演练通过后正式执行（去掉 `--dry-run`）。脚本按序做六件事：
读 VERSION → 打戳 → 门禁校验 → 构建 → 归档 + 校验和 → 打 tag。

**门禁是硬性的**（刻意不提供 `--force`）：仓库无提交、工作区不干净、
tag 已存在、版本不一致——任一条不过就中断。理由：一个能跳过检查的发布脚本，
在赶工期时一定会被用来发布"源码与版本号对不上"的包。

脚本会排除 `deploy/secrets/`、`.env`、`data/` 等敏感与运行期内容，见 §2。
