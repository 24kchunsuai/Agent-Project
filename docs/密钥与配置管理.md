# 密钥与配置管理（企业级落地规约 E-10）

> `docs/审计清单.md` §7（密钥不进审计）；`docs/日志规范.md` §7（脱敏）。

本文回答企业客户在安全问询里必问的三件事：**有哪些密钥、放在哪、怎么换**。
第四件事是"换了会不会停服"——这是 E-10 的重点，答案见 §3。

## §1 密钥清单

| # | 名称 | 用途 | 存放位置 | 轮换周期 | 轮换方式 |
|---|---|---|---|---|---|
| 1 | `AGENT_SHARED_KEY` | **服务间共享密钥**：Java(8080) → Python(8000) 全部请求的 `X-Agent-Key`（S-1 信任边界） | ① `agt_python/.env`<br>② `deploy/secrets/agent.key`（8080 启动脚本读取） | **90 天**，或人员离开/疑似泄漏时立即 | **双密钥过渡**（本文 §3，可不停服） |
| 2 | `AGENT_SHARED_KEY_PREV` | 轮换**过渡窗口**内仍被接受的上一把共享密钥；非轮换期**留空** | `agt_python/.env`（可选） | 仅轮换期存在，轮换结束后立即清空 | 清空 + 重启（旧密钥即刻失效） |
| 3 | `LLM_API_KEY` | 对话大模型（DeepSeek / 智谱等） | `agt_python/.env` | 180 天，或按厂商策略 | 单侧替换 + 重启（**无对端**，不需要过渡窗口） |
| 4 | `LLM_BACKUP_API_KEY` | 对话模型备用厂商（主备切换用） | `agt_python/.env` | 同上 | 同上 |
| 5 | `EMBEDDING_API_KEY` | 向量化模型（RAG 入库与检索） | `agt_python/.env` | 180 天 | **需重新入库**：见 §4.3 |
| 6 | `RERANK_API_KEY` | 重排模型（检索结果精排） | `agt_python/.env` | 180 天 | 单侧替换 + 重启 |
| 7 | jsdstu-3 用户令牌 / 口令 | 智能体业务工具**以当前用户身份**调用无人机主控（8060） | 仅存内存（`DroneSession`），**不落盘** | 随 jsdstu-3 会话过期自动重登 | 本系统不管理，由 jsdstu-3 负责 |

**不在这里的密钥，就是不该存在的密钥**：本系统不维护第二套账号体系（用户体系复用 jsdstu-3）。

## §2 存放与保护

| 措施 | 现状 | 证据 |
|---|---|---|
| 不进版本库 | `.env`、`deploy/secrets/` 均在 `.gitignore` | `.gitignore:32,96` |
| 不进交付包 | `release.sh` 排除 `deploy/secrets/`、`.env` | `docs/交付物清单.md` §2 |
| 不进日志 | Python `register_secret()` / Java `LogRedactor.registerSecret()` 登记**字面量**，命中替换为 `***`；另加正则兜底 | `app/core/logging_setup.py:70`、`base/log/LogRedactor.java:76` |
| 不进审计表 | 配置留痕按**键名**判定敏感（`key`/`secret`/`password`/`token`/`credential`/`api_key`），命中只记 `sha256:<12 位>` | `app/services/config_audit.py`、`docs/审计清单.md` §7 |
| 不随响应外泄 | 8000 的 `direct` 探针与 `/v1/health` 均**不回显**密钥（只报长度） | `deploy/scripts/preflight.py`（"值不外显"） |
| 启动即校验 | 密钥为空 → **拒绝启动**（fail-closed） | `app/core/auth.py:assert_shared_key_configured` |

⚠️ **`AGENT_SHARED_KEY_PREV` 必须与当前密钥一起脱敏**（E-10 已修）：
过渡窗口内它**仍是有效凭据**，漏掉它会让"正在被淘汰的密钥"以明文出现在日志里——
一把密钥写进日志就等于已泄露，而它此刻还能开门。

## §3 共享密钥轮换（双密钥过渡窗口）

### 3.1 为什么需要过渡窗口

本服务（8000）是**非 reload** 部署：改配置必须重启。Java（8080）同理。
若只支持一把密钥，轮换时必然出现"一边已换、一边未换"的窗口，**那个窗口里全链路 4010**。

双密钥把"无缝轮换"从**调度问题**变成**配置问题**：轮换期两把都收，谁先重启都不会断。

### 3.2 轮换顺序：先消费者、后生产者

```
   ① 消费者(8000) 两把都收        ② 生产者(8080) 换新密钥       ③ 停用旧密钥
   ┌────────────────────┐        ┌────────────────────┐      ┌────────────────────┐
   │ AGENT_SHARED_KEY=K2│        │ agent.key=K2       │      │ 清空 PREV          │
   │ AGENT_SHARED_KEY_  │  ───▶  │ AGENT_SHARED_KEY=K2│ ───▶ │ 重启 8000          │
   │   PREV=K1          │        │ 重启 8080          │      │ K1 即刻失效        │
   │ 重启 8000          │        └────────────────────┘      └────────────────────┘
   └────────────────────┘                 ▲                          ▲
    K1、K2 都能进                  此时 Java 用 K2，Python 收 K2    观察 legacy 计数
```

**反过来做（Java 先换）会在 ①③ 之间稳定 4010** —— 生产者拿着新钥匙敲一把还不认它的门。
这不是"更严格"，是"自己把服务打挂"。

### 3.3 逐步操作

```bash
# ── 准备工作：生成新密钥（不要复用旧值、不要用弱随机）─────────────
cd /d/install/java/javaworkspace/drone-agent001
python -c "import secrets; print(secrets.token_urlsafe(32))"     # 得到 K2
```

**① 消费者先行：8000 同时接受 K1 与 K2**

```ini
# agt_python/.env
AGENT_SHARED_KEY=<K2>            # 当前密钥 → 换成新的
AGENT_SHARED_KEY_PREV=<K1>       # 上一把 → 填**要被停用的那把旧密钥**
```

```bash
powershell -File deploy/scripts/stop-all.ps1      # 或只重启 8000
powershell -File deploy/scripts/start-all.ps1
```

自检（应报 **OK「轮换进行中：Java 仍在用旧密钥」**，不是 FAIL——那是正常中间态）：

```bash
python deploy/scripts/preflight.py | grep -A1 轮换
```

**② 生产者跟进：8080 换成 K2**

```bash
echo -n "<K2>" > deploy/secrets/agent.key          # 注意不要带换行
```
```powershell
powershell -File deploy/scripts/stop-all.ps1
powershell -File deploy/scripts/start-all.ps1
```

自检应变为 **OK「轮换：Java 已用新密钥」**。

**③ 观察，然后停用旧密钥**

```bash
# legacy 计数：还在拿旧钥匙的请求数（0 表示可以停用了）
curl -s --noproxy '*' "http://127.0.0.1:8000/v1/ops/metrics" -H "X-Agent-Key: <K2>" \
  | grep auth_key_legacy_used
```

确认该计数**连续一段时间（建议 ≥ 24h，覆盖所有定时任务）不再增长**后：

```ini
# agt_python/.env —— 只删除/清空这一行，不要填成 K2
AGENT_SHARED_KEY_PREV=
```
```bash
powershell -File deploy/scripts/stop-all.ps1 ; powershell -File deploy/scripts/start-all.ps1
```

K1 即刻失效。轮换结束。

### 3.4 三个必须记住的点

1. **`AGENT_SHARED_KEY_PREV` 与当前密钥同值 → 服务拒绝启动**。
   这不是洁癖。两把一样说明"以为在轮换其实没换"：操作者观察 legacy 计数会看到恒为 0
   （命中的永远是当前密钥），据此得出"可以停用旧密钥"——而真相是**旧密钥从未被停用**。
   静默的安全债远比启动失败危险。（校验点：`app/core/auth.py:assert_shared_key_configured`）
2. **旧密钥放行只计数、不落 `fault_event`**。请求是**成功处理完的**，把它算进看板故障数
   就是让看板说谎。它走 `telemetry.count_event`（计数器 + 指标），不走 `record_fault`。
   （校验点：`app/core/auth.py:_report_legacy_used`）
3. **`AGENT_SHARED_KEY_PREV` 只是"过渡窗口"，不是"备用密钥"**。
   长期留着一把旧钥匙 = 一个已离职的人手里还有门禁卡。轮换的最后一步**必须**执行，
   而执行条件由指标给出，不是凭感觉。

### 3.5 忘了轮换会怎样（现状与残余风险）

- 系统**不会**因为密钥"太老"而告警——当前没有密钥有效期机制，`§1` 的周期靠**制度**保证。
  这是如实记档的边界，不是"已经做了"。
- 过渡窗口**没有超时**：忘了第 ③ 步，就不存在任何提醒。缓解手段是 `preflight.py`
  在轮换期会持续报 WARN 级别的"轮换进行中"，每次部署自检都会看见。

## §4 其余密钥的轮换要点

### 4.1 LLM / RERANK / LLM_BACKUP（无对端，直接换）

单侧配置项，没有"两侧一致性"问题：改 `.env` → 重启 8000。**不需要过渡窗口**
（双密钥机制只为"两侧必须同值"的共享密钥存在）。

⚠️ 新旧 Key 的**权限边界可能不同**（如旧 Key 可用的模型在新 Key 上未开通）。
换完要跑一次真实问答验证，不能只看服务起来了。

### 4.2 备用模型（主备切换）

`LLM_BACKUP_*` 是主模型不可用时的降级通道。**它的 Key 要独立于主 Key**——
同账号同 Key 的"备用"在主账号欠费时一起失效，等于没有备用。

### 4.3 EMBEDDING（换之前先想清楚）

⚠️ **换 embedding 模型/账号会改变向量空间**：旧向量与新查询向量不可比。
换之前必须：① 重建全库向量（重新入库）；② 接受期间检索质量下降。
**建议把 embedding 的轮换与"模型升级"合并规划**，不要作为例行密钥轮换的一部分。

### 4.4 jsdstu-3 凭据

本系统**不保存**用户口令与令牌到磁盘（仅 `DroneSession` 内存态，见
`base/auth/DroneSession.java` 类注释）。用户改密码后由本系统在下一次调用时静默重登，
不需要在本系统做任何操作。

## §5 泄漏应急处置

**疑似泄漏（密钥出现在聊天记录/日志/截图/提交里）→ 按"已泄漏"处理，不抱侥幸**：

1. **立即轮换**：走 §3 的流程。若时间紧迫可跳过过渡窗口——
   直接改两侧 + 同时重启（有短暂 4010，但比继续用泄漏的密钥安全）。
2. **查审计**：`GET /v1/kb/governance/audit`（需管理员）按时间窗查
   `LOGIN_OK` / `LOGIN_FAIL` / 治理动作，看是否有非预期来源的操作。
   ⚠️ 注意审计**不含密钥本身**（设计如此），所以它回答"谁做了什么"，不回答"谁拿到了密钥"。
3. **查拒绝计数**：`faultCounters.auth_key_rejected`
   （`GET /v1/agent/metrics/overview`）在轮换后若出现尖峰，说明有旧调用方还在用泄漏的密钥。
4. **归档证据**：导审计 CSV（`GET /v1/kb/governance/audit/export`，需管理员）。
5. **复盘**：泄漏路径大概率是 §2 里某条防护被绕过（最常见：把密钥写进了临时脚本或
   截图进了文档）。**补回防护，而不是只换密钥。**
