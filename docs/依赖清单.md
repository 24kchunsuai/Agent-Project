## 1. 这份清单怎么来的（可复核）

三份数据**全部由脚本产生**，不是手抄的：

```bash
# 人类可读报告（含逐条漏洞与许可证）
python scripts/scan_deps.py --report security/deps-report.md

# 控制台结论（CI 用的是这个口径，离线）
bash scripts/ci.sh deps

# 刷新快照（联网；只有依赖变更或定期复扫时才需要）
python scripts/scan_deps.py --refresh
```

脚本是**零第三方依赖**的（只用 Python 标准库），所以"工具装不上导致查不了依赖"这件事
在本项目不会发生。快照落在 `security/`：`sbom.json`（闭包）/ `vuln-snapshot.json`（漏洞库）
/ `licenses.json`（许可证）/ `deps-allowlist.json`（豁免台账）。

## 2. 闭包总览（2026-09-24 实测）

**只扫运行期闭包，不扫开发/测试依赖**——对齐规约里 `npm audit --omit=dev` 的口径：
进不了生产的东西，不该占用阻断预算。

| 端 | 闭包来源（怎么拿到的） | 包数 |
|---|---|---|
| Python | 从 `requirements.txt` 的直接依赖出发，用 `importlib.metadata` **走传递闭包**（含 `uvicorn[standard]` 这类 extras） | **41** |
| Java | Spring Boot fat jar 的 `BOOT-INF/lib/*.jar`，再回本地 `.m2` 反查 groupId | **47** |
| 前端 | `package-lock.json` 中 `dev != true` 的包（含传递依赖） | **57** |
| | **合计** | **145** |

漏洞态势：**Critical 0 ｜ High 11 ｜ 中危 21 ｜ 低危 9**（无豁免）。

> ⚠️ **为什么不扫"整个解释器环境"**：实测共享 conda 环境 77 个包里有 15 条命中，
> **全部来自与本项目无关的 jupyter 生态**（accelerate / Django / sqlparse / pip 本身）。
> 扫环境 = 大量误报，然后门禁被人当成噪声绕过。所以只扫闭包。

## 4. Java 直接依赖

`agt_backend/pom.xml` 里声明了 5 项，但其中只有 1 项会作为 jar 进运行期：

| 声明项 | 说明 |
|---|---|
| `knife4j-openapi3-jakarta-spring-boot-starter` | 接口文档 UI（**唯一直接进 `BOOT-INF/lib` 的**，Apache-2.0） |
| `spring-boot-starter-web` | **POM 聚合器**，本身没有 jar；它拉进来的 `spring-web/spring-webmvc/tomcat-embed-*` 才是被扫的对象 |
| `spring-boot-starter-validation` | 同上（拉 `hibernate-validator` 等） |
| `spring-boot-starter-test` | 测试作用域，**不进运行期闭包** |
| `lombok` | 编译期注解处理器，**不进运行期闭包** |

所以"直接依赖 5 项、运行期闭包 47 项"并不矛盾：**starter 是目录，不是构件**。
真正需要盯的是那 47 个构件——它们才是攻击面。

关键构件与许可证：

| 构件 | 版本 | 许可证 |
|---|---|---|
| `org.springframework.boot:spring-boot` | 3.3.3 | Apache License, Version 2.0 |
| `org.springframework:spring-core` | 6.1.12 | Apache License, Version 2.0 |
| `org.springframework:spring-webmvc` | 6.1.12 | Apache License, Version 2.0 |
| `com.fasterxml.jackson.core:jackson-databind` | 2.17.2 | The Apache Software License, Version 2.0 |
| `org.apache.tomcat.embed:tomcat-embed-core` | **10.1.60** | Apache License, Version 2.0 |

> `tomcat-embed-core` 的版本是**显式覆盖**的（`pom.xml` 的 `<tomcat.version>`），
> 原因见 `docs/依赖与漏洞处置.md` §4：Spring Boot 3.3.3 托管的 10.1.28 有 7 条 Critical，
> 而"顺手升 Spring Boot 小版本"到 3.3.13 只到 10.1.42、**仍有 6 条 Critical**。

## 7. 已知限制

1. **不扫非运行期依赖**：Python 的 dev 工具、Java 的 `test`/`provided` 作用域、
   前端的 `devDependencies` 都不在闭包内。这是**有意的**，但意味着"测试链上的漏洞"不会被报。
2. **Java 闭包依赖构建产物**：`BOOT-INF/lib` 来自 `mvn package` 的 fat jar。
   改了 `pom.xml` 必须重打 jar 并 `--refresh`，否则快照是旧世界的。
3. **4 项依赖未能评估**（计入报告、**不阻断**）：
   - Python：`exceptiongroup` / `tomli`（`python_version < 3.11` 标记不成立）、
     `uvloop`（Windows 平台不装）
   - Java：`spring-boot-jarmode-tools-3.3.3.jar`（Spring Boot 内部工具 jar，
     本地 `.m2` 里没有它的 groupId 索引）
4. **CVSS 只实现了 v3.1**：v4 向量不解析（返回 `UNKNOWN`，进报告不阻断），
   而不是猜一个分数。定级优先用 GHSA 自带的 severity，CVSS 只是第三档兜底。
5. **不做容器镜像/运行时 SCA**：只覆盖"声明与锁定在仓库里的依赖"，
   不覆盖镜像层、操作系统包、运行期动态加载。
