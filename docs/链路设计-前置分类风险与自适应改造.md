# 链路设计讨论：前置分类的风险与自适应改造

> 背景：drone-agent001 下一步要做 RAG 知识库问答 + 无人机自然语言控制。本文先校准 AgentCraft 的真实链路（读代码核实，非凭印象），再讨论「前置分类判错 → 后面全错」的架构性风险与改造方案。

## 一、先校准：AgentCraft 到底有几个 agent

您记忆里的「1 个前置分类 + 1 个证据评估 + 1 个生成 = 3 个 agent」，**方向对，但实现细节对不上**。实际是：**两层分类 + 四条链路 + 两个"看起来像 agent 的步骤"**。

### 1.1 分类其实是两层，且第二层是纯关键词规则

| 层 | 位置 | 方式 | 输出 |
|---|---|---|---|
| 第一层：意图识别 | `intent/classifier.py:138` | **LLM 优先**（带 `confidence`/`reasoning`），失败 fallback 到关键词打分 | chitchat / knowledge_qa / admin_operation / knowledge_inspection / identity_query / unknown |
| 第二层：复杂度判定 | `workflows/router_agent.py:215` | **纯字符串规则，无 LLM、无语义** | simple(L1) / medium(L2) / complex(L3) |

第二层的判定规则原文（`router_agent.py:225-238`）：

```python
l3_indicators = ["对比", "比较", "优缺点", "区别", "异同", "分析", "总结", "归纳", "评估", "权衡"]
if any(ind in input_text for ind in l3_indicators) and len(input_text) > 15:
    return "complex"
l2_indicators = ["它", "这个", "那个", "上面", "之前", "刚才"]
if has_pronoun or len(input_text.strip()) < 10:
    return "medium"
return "simple"
```

**这就是决定「走哪条链路」的真正开关，而它是字符串匹配。** 换句话说：整个系统的成本与质量分级，压在一个 `in` 判断上。

### 1.2 四条链路（比您说的三条多一条）

| 链路 | 入口 | 做了什么 | 关键参数 |
|---|---|---|---|
| 闲聊 | `chitchat_agent.chat` | **完全不检索**，直接生成 | — |
| L1 | `KnowledgeQAAgent._ask_l1` | 检索 + 生成 | `k=5, threshold=0.7, use_rerank=False` |
| L2 | `KnowledgeQAAgent._ask_l2` | 改写 + 检索 + **重排** + 生成 | `RetrievalAgent.retrieve(use_rewrite=True, use_rerank=True, top_k=5)`，内部召回 `top_k*3=15` 再重排取 5 |
| L3 | `ReasoningAgent.reason` | LLM 拆子问题（最多 4 个）→ 逐个检索推理 → 汇总 | — |

### 1.3 「证据评估」和「生成」都不是 agent

- **证据充分性评估**：`agent/planner.py:211 evaluate_retrieval_sufficiency()`，一个**启发式函数**，不是 LLM 判断：
  ```python
  if not chunks: return 不足("未检索到任何相关文档")
  low_score_count = sum(1 for s in scores if s < 0.6)
  if low_score_count > len(scores) * 0.5: return 不足("大部分相似度低")
  coverage = min(1.0, len(chunks) * 0.3)
  if coverage < 0.5: return 不足("覆盖度低")     # 即 chunk 数 < 2
  return 充足(confidence=0.85)
  ```
  置信度全是硬编码（0.7 / 0.8 / 0.85），**没有 LLM 参与，也没有真正读内容**。
- **生成**：`agent/executor.py:252 _execute_answer_generation()`，一个**执行步骤**。

### 1.4 三个致命事实（比"分类会错"更严重）

**事实一：带证据评估的那套链路，主接口根本没用。**
- `/api/ask`、`/api/ask/stream`（Java 前端实际调的）→ 走 `RouterAgent`（workflow 版），**里面完全没有 sufficiency 评估**。
- `/api/agent/run` → 才有 `Orchestrator + Planner.evaluate_retrieval_sufficiency`。
- 两套并行实现，评估逻辑只活在没人走的那套里。

**事实二：流式链路是残废的。**
`KnowledgeQAAgent.ask_stream()` 里只有两行实质逻辑：

```python
docs = self.vector_store.search(query=question, k=5, similarity_threshold=0.7, use_rerank=False)
# ... 直接流式生成
```

**它不走 classify_complexity、不改写、不重排。** 而前端用的恰恰是流式。同一个问题走 `/ask` 和 `/ask/stream` 会得到质量不同的答案——这比"前置分类会错"更直接地决定了用户体验。

**事实三：「不足则重试」是设计意图，不是实现。**
`is_sufficient` 只被写进 `state.add_intermediate_conclusion()` 和 step 输出/事件里，**没有任何分支消费它去重试**。`Orchestrator` 里的 `retry_count` 只针对**代码抛异常**（`policies.should_retry(retry_count, e)`），跟"证据不够"无关。

**事实四：默认重排器不是语义重排。**
`config.py:47 RERANKER_TYPE = "simple"` → `SimpleReranker`（`core/reranker.py:191`）算的是关键词 **Jaccard + 覆盖率**：

```python
jaccard = len(intersection) / len(union) if union else 0
return (jaccard + coverage) / 2
```

BGE / Cohere 都有实现但默认不用。所以 AgentCraft 里"走完整 L2"的收益比宣传的小——这也解释了它为什么默认关掉 rerank。

**小结**：它不是一个"三 agent 流水线"，而是「一个关键词规则决定分级 → 四条各自独立的链路 → 评估和生成是链路内部的步骤，且评估结论无人消费」。

## 二、您的判断成立，且有两处代价不对称

### 2.1 级联错误的具体形态

```
用户问题
   ↓
[分类] ← 错了，后面全错，且没有任何一处会发现"前面错了"
   ↓
闲聊？ → 不检索 → 模型凭记忆答 → 「明明是知识库里的问题，却给了编造的答案」
L1  ？ → 不改写不重排 → 「专有名词/口语化问题检索不到，却直接生成」
L2  ？ → 花了改写的钱和延迟 → 「问题本来就简单，白花成本」
L3  ？ → 拆子问题 → 「问题不需要分解，拆完反而答偏」
```

**根因**：这是一个**单向不可逆的门（irreversible gate）**。入口处的分类一旦落下，后续所有环节都在"错误的前提"下工作，而系统内部没有任何信号能发现这个前提错了。

### 2.2 两处代价不对称（这是设计的关键依据）

**不对称一：意图误判的两个方向代价不同**

| 误判方向 | 后果 | 可逆性 |
|---|---|---|
| 闲聊 → 误判为知识问答 | 最多答"知识库没有找到" | ✅ 可逆，体验差 |
| **知识问答 → 误判为闲聊** | **不检索，直接凭模型记忆答 → 幻觉** | ❌ 不可逆（用户已被误导） |

所以**默认方向必须偏向"检索"**：拿不准时宁可多检索一次，绝不能跳过检索。

**不对称二：无人机控制场景，误判代价是物理性的**

| 误判方向 | 后果 | 可逆性 |
|---|---|---|
| 控制指令 → 误判为知识问答 | 用户以为要执行，实际只回了一段说明 | ✅ 可逆（只是困惑） |
| **知识问题 → 误判为控制指令** | 用户问"起飞流程是什么" → **真的把无人机起飞了** | ❌ **不可逆，可能造成财产/安全损失** |

**结论：控制类意图不能靠"分类准确率"兜底，必须靠"写操作二次确认"兜底。** 任何 `risk=write` 的动作，都必须走「参数抽取 → 回显给用户 → 用户确认 → 执行」，与分类置信度无关。这是架构约束，不是优化项。

### 2.3 更深一层的判断：分类器在做一件信息不足的预测

"这个问题需不需要重排"——分类器只能看到**问题文本**；而真正决定"需不需要重排"的信息在**检索结果**里（top1 分数、分数分布、命中文档数）。

**用问题文本预测检索行为，是拿信息量少的东西去预测信息量多的东西。** 正确做法是：先花一次便宜的检索（向量检索很快，几十毫秒），拿到**真实证据**，再决定要不要升级——这就是自适应检索（adaptive RAG / self-RAG 的核心思想）。

## 三、改造方案：把「一次性硬分类」换成「可升级的阶梯」

### 3.1 五条设计原则

1. **分类只做路由提示（hint），不做能力裁剪（gate）**：分类结果决定"从哪开始"，不能决定"到哪结束"。
2. **深度决策交给检索信号，不交给问题文本**：是否改写/重排，由 top1 分数、分数间隔、命中数决定。
3. **升级要便宜，降级要安全**：升级只多花延迟；降级绝不能丢安全网（检索为空时必须如实说"知识库未覆盖"，绝不退回模型记忆瞎答）。
4. **不可逆的动作必须二次确认**：控制类写操作 = 参数抽取 + 回显确认，与分类置信度无关。
5. **每一步留痕**：分类置信度、检索分数、充分性结论、是否升级/重试——直接对接您要建的过程级指标与 pipeline tracing。

### 3.2 新链路（五段式，替代原三条硬分叉）

**Stage 0 · 轻量理解**（一次小模型调用，结构化输出）
```json
{ "domain": "chitchat | kb | drone_control | admin",
  "needs_kb": true,
  "risk": "read | write",
  "slots": { "drone_id": "1号", "action": "起飞", "params": {"height": 10} },
  "confidence": 0.87 }
```
- 关键：`domain` 与 `needs_kb` **解耦**。"无人机指南针怎么校准" domain 是 drone 但 needs_kb=true（知识问题）；"把 1 号起飞到 10 米" domain 是 drone 且 risk=write（控制问题）。
- 低置信度（< 0.6）不二选一，而是**双跑取优**：闲聊回答很便宜，检索也很便宜，两条都跑的成本远低于一次幻觉的代价。

**Stage 1 · 召回**（一次向量检索，先不重排）
- `topK=20`，阈值放低（0.3~0.35），目标只有一个：**把可能的都捞回来**。
- 这一步极快（Milvus 几十毫秒），是整个自适应设计的成本基础。

**Stage 2 · 质量信号 → 决定是否升级**（纯计算，不调 LLM）
| 信号 | 计算 | 含义 | 触发动作 |
|---|---|---|---|
| `top1_score` | top1 相似度 | 有没有明显最相关的 | < 0.45 → 升级 |
| `score_gap` | top1 − top5 | 区分度好不好 | < 0.05 → 升级（说明都很像，向量分不开，需要语义重排） |
| `hit_count` | 命中块数 | 召回够不够 | < 3 → 升级 |
| `has_entity` | 是否含型号/编号/专有名词 | 向量弱区 | 是 → 加 BM25 混合检索 |

- **升级 = 改写 query + 混合检索（向量+BM25/RRF）+ 语义 rerank，取 top-n**
- 这一步把"分类器的一次性赌博"换成了"每次都能看到真实证据的决策"。

**Stage 3 · 证据充分性判断**（LLM judge，输出结构化决策）
```json
{ "sufficient": false, "missing": ["电池仓尺寸参数"], "action": "rewrite_retry" }
```
- 允许最多 1~2 轮重试（改写 query / 换检索策略），**必须有预算上限**（否则就是死循环烧钱）。
- 仍然不足 → **如实回答"知识库未覆盖" + 说明缺什么**，可选附模型自身知识但必须标注来源。
- 注意：LLM judge 自己也会错。**建议第一阶段先不上 LLM judge**，只用 Stage 2 的信号规则（可预测、便宜、无额外调用）；等评估体系建起来、能量化 judge 的收益后再加。

**Stage 4 · 生成**（带引用与证据等级）
- 引用标注 score 与来源；
- prompt 明确：仅依据给定证据作答，证据不足时声明。

### 3.3 方案对比

| 方案 | 平均延迟 | 误判后果 | 复杂度 | 建议 |
|---|---|---|---|---|
| 现状：关键词硬分类 | 最低 | **静默劣化，无信号** | 低 | — |
| 永远走完整链路（全量 rerank） | +0.5~2s/次 | 无 | 低 | 小知识库可接受 |
| **自适应升级（推荐）** | 平均接近 L1，最差接近 L2 | 有兜底 | 中 | ✅ 目标形态 |
| 先做简化版：**永远检索 + 信号决定重排** | 略高于 L1 | 有兜底 | 低 | ✅ 第一步落地 |

**落地建议：分两步走。** 第一步（低成本、立刻见效）：取消"闲聊/知识"的硬分叉，**所有问题都先检索**（闲聊也可检索，命中就带证据，未命中就走闲聊能力）；是否重排由 Stage 2 信号决定。第二步：引入改写重试与 LLM judge，同时把评估体系（问题→期望命中文档集）建起来，用数据验证每一步的真实收益。

## 四、对 drone-agent001 的落地映射

现有 `agt_python` 已具备的基础（可复用，不需重写）：
- 意图路由三级策略（rule → LLM → fallback）→ **保留，但降权为 hint**
- SSE 流式链路（meta → delta → done）→ 新链路继续复用，只是把 meta 事件扩展为携带 `domain/confidence/signals/retrieval_round`
- 会话记忆 `SessionMemory` → 保留

建议的分支结构：

```
用户输入
  ↓ Stage0 轻量理解（复用现有 IntentRouter，扩展输出 domain/needs_kb/risk）
  ↓
  ├─ domain=drone_control & risk=write → 参数抽取 → 回显确认 → 执行 → 结果回执
  │                                        （禁止一次分类直接执行）
  ├─ domain=drone_control & risk=read  → 走知识链路（"怎么校准"是知识问题）
  ├─ domain=kb      → 统一检索骨架（Stage1-4）
  └─ domain=chitchat→ 先走检索骨架（命中即带证据），未命中再走闲聊能力
                      ★ 而不是"跳过检索直接生成"
```

**关键差异点（相对 AgentCraft）**：它把 `chitchat` 做成"完全不检索"，我们反过来——**默认都检索，只有确认无命中才降级到闲聊**。这一条就能消掉"知识问题被误判为闲聊 → 幻觉"这条最贵的错误路径。

## 五、待确认的决策点

1. **第一步落地范围**：先做「永远检索 + 信号决定重排」（推荐，改动小），还是直接上完整的五段式（含改写重试 + LLM judge）？
2. **升级触发的实现位置**：放在 Python 的检索编排里（推荐，链路自治），还是由 Java 侧根据返回的信号决定二次调用？
3. **LLM judge 是否引入**：先用纯信号规则，还是第一天就上 LLM 评估证据充分性？
4. **重试预算**：允许几轮重试（建议 ≤2），以及单次问答的总延迟上限（建议 ≤8s）？
5. **无人机控制的确认方式**：文字回显确认（"即将把 1 号无人机起飞到 10 米，确认吗？"）还是需要更强的二次输入（如输入"确认"两字）？
