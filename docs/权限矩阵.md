## §1 角色定义（按实测，不是按假设）

⚠️ **与规约原文的一处有意偏离**：规约 E-10 写的是 `admin / operator / viewer` 三角色。
**实测本系统的角色不叫这三个名字**，故矩阵按真实取值写，偏离据实记档在这里。

| 角色 | 来源 | 代码里是否被差异对待 |
|---|---|---|
| `admin` | jsdstu-3 的 `RoleEnum`（经 `LoginUser.permission` 传入） | ✅ 是 |
| `pilot` | 同上 | ❌ **与 repair 完全等价**（都是"非 admin"） |
| `repair` | 同上 | ❌ 同上 |

**结论：本系统实际只有「admin / 非 admin」两档。** 证据：

| 事实 | 证据 |
|---|---|
| 全仓只比较过 `"admin"` 这一个角色 | `GovernanceServiceImpl.java:28` `ROLE_ADMIN = "admin"`、`KbServiceImpl.java:22` 同 |
| 判定用 `equalsIgnoreCase`，故 `ADMIN`/`Admin` 也算管理员 | `GovernanceServiceImpl.java:246`、`KbServiceImpl.java:160` |
| 主代码里**没有任何** `"pilot"` / `"repair"` 的分支比较 | `grep -rn '"pilot"\|"repair"' agt_backend/src/main/java` → 无命中（仅测试与文档里作为构造值出现） |
| 单元测试也从没区分 pilot 与 repair | `GovernanceServiceImplPermissionTest.java`、`PermissionEndToEndTest.java` 只构造 `admin` / `pilot` / `ADMIN` 三态 |

> **为什么不用规约里的三角色**：`viewer` 在本系统里根本没有对应物（没有"只读账号"这一档，
> 匿名就是只读的极限）；而 `operator` 与 `pilot`/`repair` 的对应关系是**猜的**。
> 按规约的三分法写矩阵，每一行都会指向一个**不存在的校验点**——那正好违反本文件的验收标准。
> 若将来 jsdstu-3 引入差异化角色，矩阵与 `ROLE_ADMIN` 常量需同步演进（登记在 §7）。

## §2 判定发生在哪里（三层，只有一层会拒绝）

```
   请求 ─▶ AuthInterceptor  ─▶ Controller      ─▶ Service 实现类
          （可选认证）          （取 session）      （requireLogin / requireAdmin ← 唯一拒绝点）
          有合法 Bearer 就挂
          session；没有就放行
          匿名 —— **本身不拒绝**
```

| 层 | 文件 | 行为 | 证据 |
|---|---|---|---|
| ① 拦截器 | `base/auth/AuthInterceptor.java` | **可选认证**：有合法 `Authorization: Bearer` 就把 `DroneSession` 挂到请求属性，没有则 **放行匿名**。`preHandle` 恒定 `return true` | `AuthInterceptor.java:57` |
| ② Controller | 各 `*Controller.java` | 从请求属性取出 `session`（或 `agent.loginSession`）后透传给 Service | `GovernanceController.java:78` `session(request)` |
| ③ **Service 实现** | `GovernanceServiceImpl` / `KbServiceImpl` / `AuthService` / `AgentController.currentUserId` | **真正的拒绝**：`requireLogin` 抛 4010、`requireAdmin` 抛 4011 | `GovernanceServiceImpl.java:216,234`、`KbServiceImpl.java:141,158` |

**这条"拒绝只在第③层"的性质很重要**：它意味着**只要某个端点没调 `requireLogin/requireAdmin`，
它就是匿名可达的**——不管它看起来多"内部"。矩阵里所有"匿名"行都是这么判定的，
不是靠命名猜的（§6 的脚本会反向核对这件事）。

### 3.1 三档的语义差异（读表时最容易混的两处）

| 看似同类，实际不同 | 说明 |
|---|---|
| 「登录」的 `disable` / `enable` vs 「管理员」的 `rollback` | disable/enable **不是**管理员专属：非管理员可以用，但**只能动自己上传的**（Java 下发 `isAdmin=false`，Python 按 `owner` 过滤：`KbServiceImpl.java:165` `return isAdmin(session) ? SCOPE_ALL : SCOPE_MINE;`）。回滚则一律管理员 |
| 「匿名」的 `GET /v1/kb/documents` vs 「登录」的 `POST /v1/kb/documents` | 匿名**能看**（只看 `public` 范围），但**不能传**。知识问答对所有人开放在这个项目里是刻意的产品决定（见 `AuthInterceptor` 类注释） |
| 「匿名」的 `POST /v1/ops/client-error`（E-12 唯一匿名**写入**端点）vs 其余写入端点 | 前端报错上报**必须匿名**：崩溃最常发生在**未登录**时（登录接口 500、token 解析炸了、登录页脚本报错），要上报就得先登录的话，恰好在"最需要上报的时刻"收不到。代价是匿名者可写入（噪声）——防护是三重的：① 8080 侧 **8KB 体量闸门**；② 服务端按 `(指纹, 1 分钟桶)` **合并**（同一错误只占一行，刷不出表爆炸）；③ 采样率可调。它**读不到任何东西**，也**改不了任何业务状态** |

⚠️ **`DELETE /v1/kb/recycle/{docId}`（彻底删除）是矩阵里唯一"管理员判定写在 if 里而不是 `requireAdmin` 里"的行**。
行为与 `requireAdmin` 一致（抛 4011），但它绕过了统一入口——**这是一处可改进的写法**，
已记入 §7，未改代码（E-10 的边界是"文档对齐代码"，不是"顺手重构"）。

### 3.2 匿名可达 ≠ 无防护

表里"匿名"行**不是**"对外公开"：8080 本身是否可达由部署决定，
且 8000 侧**没有任何匿名端点**（除探针）——见 §4。把这张表和 `docs/密钥与配置管理.md` §2 一起看，
才是完整的信任边界图。

## §4 Python 8000 侧的权限处理

### 4.1 身份一律由 Java 注入，Python 只做"消费 + 兜底"

| 事项 | 实现 | 证据 |
|---|---|---|
| 服务间入口 | 所有非探针请求必须带 `X-Agent-Key`（**与用户角色无关**，是服务身份） | `app/core/auth.py:SharedKeyMiddleware` |
| 角色接收 | Java 以查询参数/请求体注入 `is_admin` / `owner` / `operator` | `GovernanceClient.java:278,355` 注入 `is_admin` |
| 对话链路身份 | Java 把 `metadata.identity`（含 `permission` 与 `droneToken`）注入聊天请求 | `AgentController.java` `injectIdentity(...)`；`app/services/agent_service.py:222` 注明"未登录为 None" |
| **兜底①**：彻底删除 | `gov_purge_require_admin`（默认 **True**）为真时 Python 再判一次 | `app/core/config.py:140`、`app/services/kb_service.py:1555` |
| **兜底②**：版本回滚 | `gov_rollback_require_admin`（默认 **True**）同上 | `app/core/config.py:160`、`app/services/kb_service.py:1843` |
| **兜底③**：对话里的写工具 | 独立再判：`permission != "admin"` → `BizError` | `app/services/guard.py:27` `WRITE_ROLE = "admin"`、`guard.py:118` |

**为什么要"再判一次"**：Java 是唯一注入方，Python 完全信任它会更快；但那样一旦有人**绕过 8080 直连 8000**
（本机其它进程、或临时把 `--host` 开到 `0.0.0.0` 的调试实例），角色校验就整段消失了。
兜底①②把"最不可逆的两件事"（彻底删除、覆盖在库内容）钉在末端，
代价是每次多一次布尔判断。**取舍是刻意的：不可逆的操作值得多一道门。**

### 4.2 与 HTTP 矩阵的对应关系

§3 的每个"管理员"行，在 Python 侧对应的是 **`is_admin=true` 才被放行到业务逻辑**；
也就是说同一件事**在两侧各判一次**（Java 判身份、Python 兜底）。
两侧都判不是冗余：Java 防"越权用户"，Python 防"绕过 Java 的调用"。

## §5 反向：Python → 8060 无人机主控用什么身份

| 事项 | 实现 | 证据 |
|---|---|---|
| 用**当前用户自己**的 token，绝不偷用系统账号 | 业务工具调用统一传 `token=identity.get("droneToken")` | `app/tools/__init__.py`（多处）；`app/biz/__init__.py:4` 注释明确此设计 |
| 匿名时 | `droneToken=None` → 8060 返回 4010 → 智能体提示"请先登录"；**无系统账号兜底** | `app/biz/__init__.py:28` |
| 效果 | 数据范围与写权限天然由 jsdstu-3 的角色体系收敛（pilot 查不到别人的任务） | `base/auth/DroneSession.java` 类注释 |

**这条设计的价值**：本系统**不需要**维护"哪个用户能看哪些无人机数据"的第二套规则——
那个规则在 8060 侧已经存在且是权威的。少一套规则 = 少一套会和权威打架的规则。

## §6 自动校验（本文件的验收手段）

```bash
python scripts/check_permission_matrix.py          # 退出码 0 = 通过
python scripts/check_permission_matrix.py -v       # 打印每一行的核对结果
```

脚本做**五项**检查（缺一项就只防住一半）：

| # | 检查 | 防的是什么 |
|---|---|---|
| A | **端点覆盖**：把全部 Controller 的映射注解解析成路径，逐个断言在 §3 表里出现（双向） | "新加了端点但矩阵没登记"，以及"矩阵登记了不存在的端点" |
| B | **证据真实**：每行 `校验点` 的 `文件:行` 存在，且该行**确实包含** `依据` 列写的代码片段 | "文档写了代码没做"（凭空引用） |
| C | **约束语义**：标 `登录` 的行证据必须含 `requireLogin\|UNAUTHORIZED`；标 `管理员` 的必须含 `requireAdmin\|PERMISSION_DENIED\|isAdmin` | "标了权限但其实没判" |
| D | **反向完整**：全部 `requireLogin(session` / `requireAdmin(session` 调用点，必须**逐条**落在矩阵某行所引用的**方法区间**内（方法内部的自调用除外） | "代码加了校验但矩阵漏登记"。按"方法"而非"单行"覆盖，是因为一个端点可以有两处判定（见 §3.1 末尾那条） |
| E | **匿名行结构**：标 `匿名` 的行，证据必须是 **Controller 的映射注解** | "把受保护的端点错标成匿名"——若不查这条，只要把证据从那行 `requireAdmin` 换成 `@GetMapping` 就能同时躲过 C 和 D |

**E 与 D 是一对**：E 让"匿名行"无法引用 Service 层的判定行，D 又要求每个判定点必须被某行的方法区间覆盖；
两者合起来使得"受保护的端点被标成匿名"**无法**表达——想把判定点覆盖掉就得引用它所在的方法，
而那样又违反 E。这两条是被**验红**逼出来的：最初只有 A~D 时，"管理员→匿名 + 证据换成 Controller 行"
这一组合能完整逃逸（见 `DEV_ISSUES.md §6.82`）。

**验证脚本本身也验红过**：改坏矩阵的四种方式——① 删一行（A+D 红）② 换成不存在的代码片段（B+D 红）
③ 约束错标（E 红）④ 约束错标 + 证据换到 Controller 行（D 红）——均已确认会判失败。
一个从没红过的检查等于没有检查。

行号漂移（代码上移/下移导致 `文件:行` 对不上，但片段仍在同文件里）报 **WARN** 并打印实际行号，
不算失败——否则每次改代码都要手工修文档，没人会愿意维护。

## §7 已知边界（如实记档）

1. **只有 admin / 非 admin 两档**（§1）。规约假设的 `operator` / `viewer` 在本系统无对应物。
   引入差异化角色需要同时改 `ROLE_ADMIN` 常量、两个 `requireLogin/requireAdmin` 实现、本矩阵与 §6 的脚本。
2. **`AuthInterceptor` 是可选认证，不是强制登录**。它"不拒绝"这件事本身是个**设计决定**
   （公共问答域），但意味着**任何忘记加 `requireLogin` 的新端点默认是匿名的**。
   §6 的检查 A/C 正是为了在评审时把这个默认值暴露出来，而不是靠人记得。
3. **`DELETE /v1/kb/recycle/{docId}` 未走 `requireAdmin` 统一入口**（§3.1），行为正确但写法不一致。
4. **Python 侧的角色兜底可被配置关掉**（`gov_purge_require_admin=false`）。
   默认全开；关掉等于放弃"绕过 8080"这一层的防护，属于**故障排查期**的临时手段，不应长期保留。
5. **矩阵不覆盖 8060（无人机主控）的内部权限**——那是 jsdstu-3 的职责，本系统只消费它的判定结果（§5）。
6. **矩阵不含 9090（前端）**：前端不做权限判定（判定都在 8080），只按返回码提示（4010 → 请重新登录 / 4011 → 权限不足）。
   前端的可见性控制是**体验**，不是安全边界。
7. **检查 D 只扫两个 Service 实现的统一判定入口**（`GovernanceServiceImpl` / `KbServiceImpl`），
   这是刻意的：全仓扫 `requireLogin` 会引入误报，而**误报的门禁会被关掉**。
   代价是：若将来有人用**另一种机制**加判定（不叫 `requireLogin/requireAdmin`），D 不会发现，
   只能靠检查 A（端点覆盖，它总会发现"新端点没登记"）兜住一半。
   新增判定机制时**必须同步把它加入 `_CHECK_D_FILES` 的扫描口径**。
