# 检索过滤与证据充分性 —— 设计评审与精化

> 评审对象：用户提出的 RAG 链路设计（意图识别 → 混合检索 top20 → rerank → 动态阈值过滤 → 证据评估 → 压缩 → 生成）
> 评审时间：2026-09-16
> 结论：**方向正确，但有 1 个事实性前提错误、1 个数学缺陷、1 个判据错位，并缺少 3 条关键路径。**
>
> ⚠️ **重要更新（2026-09-16 接入 reranker 后实测）**：本文第 2 节提出的"三件套"过滤中，
> **「绝对安全网」与「相对自适应」已确认失效** —— GLM rerank 分数饱和，
> 完全无关的文档（如"红烧肉的做法"）对无人机查询也能得 0.9958 分。
> **请先读第九节，再采纳第 2 节的参数建议。**

---

## 一、先修正事实前提：没有"40 分"这回事

设计里写「取 max(平均分和 40 分)」，但 reranker 的输出**不是百分制**：

| Reranker 类型 | 原始输出 | 归一化后 | 证据 |
|---|---|---|---|
| 智谱 `rerank` API（推荐） | — | **0 ~ 1 小数** | 官方示例 `"relevance_score": 0.99866986`；有 `return_raw_scores` 开关，默认 false 即已归一化 |
| BGE-reranker（本地） | **logits，约 -10 ~ +10，可为负** | sigmoid → 0~1 | BAAI 模型卡：分数不绑定特定范围；`CrossEncoder.predict()` 返回原始 logits |
| 阿里 gte-rerank-v2 / qwen3-rerank | — | 0.0 ~ 1.0 | 官方文档明确标注 |

**所以"40 分"在这套体系里应写作 `0.4`。**

> ⚠️ **顺带发现 AgentCraft 的一个真实 bug**：`core/reranker.py` 的 `BGEReranker.rerank()` 直接 `float(score)` 存原始 logits（**没有 sigmoid**），而 `agent/planner.py:222` 却用 `s < 0.6` 判低分。logit 与概率阈值含义完全不同——`sigmoid(0)=0.5`，所以 logit 在 `0 ~ 0.405` 区间的片段全被判成"低分"。这是**阈值与分数制不匹配**的教科书级案例，也正好说明本节的必要性。

**规则**：任何阈值都必须和分数制绑定声明。换 reranker 必须重新标定阈值，不能沿用。

## 二、数学缺陷：`max(avg, 0.4)` 不是自适应，是双重收紧

原设计的意图是"分布不同 → 阈值不同"，但用 avg 实现达不到这个效果：

```
threshold = max(avg, 0.4)
```

### 问题 1：`max` 永远取更严格者，只会收紧不会放宽

- 少数高分 + 多数低分 → avg 被拉低（如 0.22）→ `max` 取 **0.4**（比 avg 严）
- 普遍高分 → avg 高（如 0.71）→ `max` 取 **0.71**（比 0.4 严得多）

两种情况都在往严的方向走。**"自适应"变成了"永远选更狠的那个"。**

### 问题 2：avg 是位置统计量，对任何分布都会砍掉接近一半

avg 的数学性质决定它必然位于分布中部偏上（右偏分布时），用 avg 做门槛等于"**砍掉分数低于平均的所有片段**"——这至少是半数候选。

**反例（情况 B 的实际后果）**：

```
候选分数：[0.95, 0.92, 0.88, 0.85, 0.80, 0.78, 0.75, 0.52, 0.48, 0.45, 0.41, 0.38, ...]
avg ≈ 0.55 → threshold = max(0.55, 0.4) = 0.55
结果：只剩 7 条，把 0.41~0.52 这一段"虽不顶级但仍可能有用"的片段全部丢弃
```

而这些被砍掉的片段，可能是唯一覆盖问题某个侧面的证据。**"最多 8 条"的上限本来已经能控量，不需要靠 avg 再砍一刀。**

### 问题 3（最根本）：reranker 分数不可跨请求比较

阿里官方文档原话：

> Scores are relative to the current request and **cannot be compared across requests**.

同一个 0.6 分，在一个 query 下可能是当批最高分，在另一个 query 下可能是中游。**绝对阈值本质上不可靠**，因为分数没有跨请求校准。

### ✅ 替代方案：三件套（绝对安全网 + 相对自适应 + 保底/封顶）

```python
# 1) 绝对安全网：低于此分一律丢弃（防噪音）
score >= FLOOR_ABS            # 建议 0.30，召回优先

# 2) 相对自适应：跟着本次 top1 走（解决跨请求不可比）
score >= top1_score - DELTA   # 建议 0.15
#    或 ratio 形式：score >= top1_score * 0.75

# 3) 保底 + 封顶
min_keep = 3   # 过滤后不足 3 条 → 回补 top3，避免全砍光
max_keep = 8   # 上限 8 条 ✅（原设计保留）
```

**进阶可选：断崖检测**（比 delta 更聪明）
排序后计算相邻分数落差，找最大落差处切分——天然适配"只有几条高分、其它断崖式下跌"的情况，无需人工定 delta。

## 三、判据错位：用"条数"判断证据够不够，是错的

原设计：

> 小于四条直接塞入生成 agent；大于四条才让评估 agent 评估

### 为什么错

**条数 ≠ 相关性。** 8 条 0.45 分的噪音，信息量远不如 2 条 0.92 分的精准片段。用条数当充分性代理指标，等于把"检索到了多少东西"误当成"检索到了多少**有用的**东西"。

### 最危险的是"少于 4 条直接生成"

请想这个场景：

```
检索 → 过滤 → 只剩 3 条，分数 0.42 / 0.40 / 0.38  ← 全是低分噪音，知识库其实没覆盖
您的规则：不足 4 条 → 直接生成
后果：模型拿到 3 条无关片段 + 一个它答不了的问题 → 幻觉
```

**"低分 + 少条数"是最该拦截的情况，恰恰被放行了。** 这正好对应上一轮结论：代价不对称，知识库未覆盖时必须如实告知，不能退回模型记忆。

### 正确的充分性信号

用 **分数信号**，不用条数：

| 信号 | 含义 | 建议阈值（起始值） |
|---|---|---|
| `top1_score` | 最佳证据的绝对质量 | `< 0.35` → 疑不足 |
| `high_score_count`（≥0.7 的条数） | 是否存在多角度支撑 | `< 2` → 疑不足 |
| 分数集中度（top1 - top3 均值） | 是否有"一枝独秀" | 过大 → 单点支撑，脆弱 |
| 覆盖度（是否命中问题多个侧面） | 多子问题场景 | 需 LLM judge 判 |

**判定为"不足"时，条数多少无关紧要。**

## 四、逻辑瑕疵：压缩环节的"答案"从哪来？

原设计：

> 评估 agent 评估完之后，根据问题和**答案**，压缩提供的 8 条证据

**评估 agent 不产出答案**——它只判断证据够不够，此时还没有生成结果。"根据答案压缩"缺少输入源。

### 两个修正方向

**方向 A（推荐，成本低）**：压缩只依据**问题**，做"逐条资格裁决 + 句子级裁剪"
- 对每条证据标注：`直接支撑 / 部分相关 / 无关`
- 只保留"直接支撑"条目中真正命中的句子/段落，砍掉冗余上下文
- 相邻重叠片段做去重合并
- 收益：省生成 agent 的 token、降噪、天然产出引用标注的位置信息

**方向 B（成本高）**：draft-then-verify —— 先生成草稿答案，再让评审 agent 对照草稿筛选证据。
- 缺点：多一次生成调用，token 反而增加，延迟翻倍。除非质量瓶颈明确在"证据筛选"，否则不推荐。

### 顺序也要改

```
❌ 原设计：评估 → 压缩 → 生成
   （若评估判定不充分，压缩白做了）

✅ 修正：评估 → 分支
        ├─ 充分 → 压缩 → 生成
        └─ 不充分 → 重试/兜底（此时不压缩）
```

## 五、缺失的三条路径 —— 这才是健壮性的关键

原设计的链路是"一条直线走到底"，但真实系统必须处理三种偏离：

### 1. 证据不充分 → 没有出口

您的流程里，评估 agent 判完"不够"就没有下文了。需要定义出口与预算：

| 出口 | 动作 | 预算 |
|---|---|---|
| ① 放宽召回 | 提高 topK（20→40）、降低 floor、开启 BM25 弱通路 | — |
| ② Query 改写重检索 | LLM 改写/拆子问题/HyDE 后重跑 Stage 1 | **最多 1 次** |
| ③ 如实告知 | "知识库未覆盖该问题"，给相近问题建议 | 终止 |

必须设**总延迟上限**（如 rerank + 检索总耗时 ≤ 3s），超时直接走出口 ③，不能无限重试。

### 2. 完全未命中 → 必须硬兜底

召回为空 / top1 低于绝对下限 → **直接返回兜底话术，绝不调用生成模型**。这是上一轮已确认的铁律（代价不对称：瞎答不可逆）。前端要显式区分"知识库未覆盖"与"模型作答"两种态。

### 3. 评估 agent 的成本 → 需要分级判断

一次额外的 LLM judge = **+1~3 秒延迟 + 一次 token 成本**，每条 RAG 请求都付这个代价值不值？

建议**分级判断**，只有模糊区才付费：

```
纯计算信号（0 成本，覆盖大部分情况）
  ├─ top1 >= 0.7 且 high_score_count >= 2   → 直接判"充分"，跳过 LLM
  ├─ top1 <  0.3 或 高分数 = 0              → 直接判"不充分"，跳过 LLM
  └─ 其余（模糊区，如 top1 ∈ [0.3, 0.7)）   → 调 LLM judge 裁决
```

预期能省掉 **60~80%** 的 judge 调用。

## 六、精化后的完整链路

```
用户问题
  │
  ├─ Stage 0  意图识别（只判"是否可能涉及知识库"，不做硬裁剪）
  │            ※ 判为闲聊也先探一次召回，避免"知识问题被误判为闲聊→幻觉"
  │
  ├─ Stage 1  混合检索：向量(Milvus) + BM25 关键词 → RRF 融合 → topK = 20
  │            ※ 本阶段输出只有"顺序"，不要拿 RRF 分去做阈值
  │
  ├─ Stage 2  rerank：智谱 rerank API（0~1 分），对 20 条打分
  │
  ├─ Stage 3  自适应过滤（三件套）★ 您设计的这一环，替换实现
  │            floor = max(0.30, top1 - 0.15)
  │            keep = {s >= floor}，封顶 8 条，保底 3 条
  │
  ├─ Stage 4  证据充分性（分级判断）
  │            纯计算信号 → 明确则直接定论（0 成本）
  │            模糊区 → LLM judge 裁决
  │
  ├─ 分支 ─┬─ 充分 ─→ Stage 5 证据压缩（逐条裁决 + 句子级裁剪）
  │        │            └─→ Stage 6 生成（SSE 流式 + 引用标注）
  │        │
  │        ├─ 不充分 → 重试出口（放宽召回 / Query 改写，预算 1 次）
  │        │            └─→ 仍不足 → 「知识库未覆盖」+ 相近问题建议
  │        │
  │        └─ 空召回/超低分 → 直接兜底话术，不调用生成模型
  │
  └─ 全程：总延迟上限 3s，超时降级到直答模式
```

### 与原设计的差异对照

| 环节 | 原设计 | 精化后 | 原因 |
|---|---|---|---|
| 阈值形式 | `max(avg, 0.4)` | `max(0.3, top1 - 0.15)` | avg 是位置量，不适合做下限；top1 相对量可跨请求自适应 |
| 保底 | 无 | `min_keep = 3` | 防止过滤后全空 |
| 充分性判据 | 条数（<4 直接生成） | 分数信号（top1 / 高分条数） | 条数≠相关性，低分少条数最该拦 |
| 压缩输入 | 问题 + 答案 | 仅问题（逐条裁决+句裁） | 评估阶段没有答案 |
| 压缩时机 | 评估后无条件压缩 | 确认充分后才压缩 | 避免重试时白做 |
| 重试出口 | 无 | 放宽召回 / 改写，预算 1 次 | 否则"不足"是死胡同 |
| 兜底 | 无 | 空召回直接话术 | 铁律：宁可说不知道 |
| 评估成本 | 每请求都调 LLM | 分级，仅模糊区付费 | 省 60~80% judge 调用 |

## 七、参数起始值建议（待在真实数据上标定）

| 参数 | 建议起始值 | 说明 |
|---|---|---|
| 召回 topK | 20 | 智谱 rerank 单次最多 128 条，20 条延迟可控 |
| `FLOOR_ABS` | 0.30 | 召回优先；精准优先场景（如参数查询）提到 0.5 |
| `DELTA` | 0.15 | top1 相对下浮 |
| `max_keep` | 8 | 保留原设计 |
| `min_keep` | 3 | 防全砍 |
| 充分性 `top1` 门槛 | 0.35 | 低于此判"疑不足" |
| 高分定义 | ≥ 0.70 | 用于统计 `high_score_count` |
| 重试预算 | 1 次 | 超过则走兜底 |
| 总延迟上限 | 3 s | 超时降级直答 |

### 阈值必须标定，不能拍脑袋

方法（约 30 分钟即可完成）：

1. 取 50~100 个**真实业务问题**（无人机手册类）
2. 对每个问题跑 Stage 1~2，导出 top20 的 rerank 分数
3. 人工标注每条的「真相关 / 真无关」
4. 统计两类分数的分布，取**两簇之间的分界点**作为 `FLOOR_ABS`
5. 抽检 10 个 query 的实际保留结果，漏得多就下调 0.05，噪音多就上调 0.05

> 这一步的产物就是「检索层评估数据集」，可直接复用为后续 rerank / 混合检索的效果对照基线——与您正在 fashion 项目里推进的评估体系是同一套方法论。

## 八、待确认决策点

1. **reranker 选型**：智谱 `rerank` API（复用现有 GLM key，0~1 分，零部署）还是本地 BGE（需 GPU/CPU，logits 需自行 sigmoid）？
2. **过滤策略**：采用「绝对下限 + top1 相对 delta」三件套，还是加一步「断崖检测」？
3. **充分性判断**：先只上纯计算信号（快、省、可解释），还是首版就带 LLM judge？
4. **压缩粒度**：句子级裁剪（保留原文、可做引用）还是 LLM 摘要（更短、丢原文）？建议前者。
5. **重试方式**：优先"放宽召回"（便宜）还是"Query 改写"（贵但可能更有效）？
6. **混合检索的 BM25 通路**：Milvus 2.5+ 内置全文检索可省掉 ES，是否接受把 Milvus 版本要求提到 2.5+？

## 九、⭐ 实测校准（2026-09-16）：reranker 分数饱和，绝对阈值全线失效

> ## ⚠️ 本节结论已被推翻（同日更新）
>
> 本节（以及文档开头"三件套已失效"的警示）基于一次**用错模型**的实验：
> 当时调用的是基础版 `rerank`，它对**完全无关**的文档也打 0.86~0.95 分，
> 才导致同一批候选分数全挤在 0.99999~1.0。
>
> **换成 `rerank-pro` 后，同质候选池的分数同样能拉开到 0.998 跨度，阈值可用。**
> 完整实测见 `docs/检索参数标定与rerank模型选型.md`。
>
> 本节仍然成立的部分：**「reranker 分数不可跨请求比较」的官方依据**，
> 以及由此推出的「**模型换型必须重新标定阈值**」这条原则——
> 只不过当时的结论把"模型太弱"误判成了"阈值天然不可用"。

> **本节结论推翻了本文第 1、2 节提出的"三件套"建议。**
> 三件套中的「绝对安全网」与「相对自适应」在实测数据上均失效，**仅「保底/封顶」仍然有效**。
> 提三件套时尚未接入 reranker，属于无 rerank 环境下的推演；接入后实测发现前提不成立。

### 9.1 实验设置

本地 Milvus 2.6.24 + GLM rerank 实测：
- 候选池：6 条真实无人机知识片段 + **4 条刻意加入的完全无关文档**
  （红烧肉做法、Python 列表推导式、北京地铁时刻表、咖啡豆烘焙）
- 查询：「黑飞会有什么后果」（口语术语，与法规原文零字面重合）

### 9.2 实测结果：无关文档也能拿 0.98~0.999

| 排名 | 文档 | rerank 分数 |
|---|---|---|
| #1 | reg-003 管制空域处罚（**正确答案**） | 0.9999999 |
| #2 | reg-002 实名登记 | 0.9999993 |
| #4 | man-001 起飞前检查清单（**BM25 的误召**） | 0.9999914 |
| #6 | **noise-3 北京地铁时刻表** | **0.9996417** |
| #9 | **noise-1 红烧肉做法** | **0.9958500** |
| #10 | **noise-4 咖啡豆烘焙** | **0.9806919** |

**与查询毫无关系的文档拿到 0.98~0.999，分数要到小数点后第 4 位才出现差异。**
另一查询「起飞前要检查什么」同样：无关文档普遍 0.99+，仅「咖啡豆烘焙」落到 0.7467。

### 9.3 三个直接结论

**结论 1：绝对阈值全线失效。**
`score >= 0.3 / 0.4 / 0.5` —— 任何 0.7 以下的阈值都筛不掉任何东西。
原设想的 `max(avg, 0.40)` 中 avg ≈ 0.997，阈值形同虚设。

**结论 2：相对自适应（top1 − δ）同样失效。**
top1 = 0.9999999，`top1 − 0.15 = 0.85`，而噪音文档得分 0.98~0.999，**全部通过**。
δ 要放大到 0.9 以上才有效果，但那样会把 0.99 的正常相关文档一起砍掉。

**结论 3：排序是正确的 —— 排名可用，分数不可用。**
正确答案稳定排 #1，BM25 的误召被压到 #4，无关文档被压到 #6 之后。
**reranker 的「排序能力」有效，「打分能力」无效。**

> 附带收获：这也回答了"reranker 能否兜住 BM25 的噪音" —— **能**。
> 上一轮（无 rerank）观察到的「RRF 放大 BM25 错误」问题，
> 在有 reranker 的完整链路中被解决了。**前提是正确答案必须已进入候选池**
> —— 这正是「语义 top10 + 关键词 top10」分路召回的价值：语义那一路不受 BM25 影响。

### 9.4 修正后的筛选策略（替代三件套）

```
混合召回（语义 top10 + 关键词 top10，去重）
  → rerank（只用排序，忽略分数绝对值）
  → 筛选 = 排名切片 top-N + 条数上下限（保底 3 / 封顶 8）
  → 充分性用其他来源的信号判断（见 9.5）
```

**关键认知：当分数没有区分度时，位置（排名）就是最可靠的信号。**
在这个前提下，「最少 3 条 / 最多 8 条」的**条数控制反而是正确且必要的设计**
—— 它同时承担「上下文预算控制」与「防极端情况」两个职责。

### 9.5 「证据够不够」该用什么判断？

reranker 分数既然不可用，可用的信号只剩：

| 信号 | 说明 | 可靠性 |
|---|---|---|
| **两路是否存在有效召回** | 两条路都没有超过最低门槛的内容 | 高（判定"完全无覆盖"） |
| **BM25 绝对分数** | 相对分，可设下限（实测正常 2.98~5.38 / 噪音 1.498） | 中 |
| **向量相似度** | 有区分度但随批量漂移，只适合同批内比较 | 中 |
| **LLM judge** | 直接问模型"这些证据够回答吗" | 高，但每次 +1~3 秒 |
| 条数 | **不构成充分性证据**（3 条低质 ≠ 3 条高质） | 低 |

**修正建议**：首版不引入 LLM judge，用「两路最低门槛都没过 → 直接判定未覆盖」这条硬规则兜底；
充分性精判留到有评估数据后再上。

### 9.6 两个必须说明的边界

1. **本结论受限于 GLM rerank 这一具体实现。** 换 reranker（BGE / Cohere / 阿里 gte-rerank）
   分数分布可能不同，**换模型必须重跑本实验再定策略**。
2. **语料规模会影响分数分布。** 本次仅 10 条候选；扩到数百 chunk、跨领域内容更多时，
   分数可能拉开。**本结论需在真实规模语料上复测后定稿**，
   但"不要依赖绝对阈值"这一保守原则在复测前应当先执行。
