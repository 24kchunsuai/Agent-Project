# drone-agent001 审计清单

> 版本：v1.0 ｜ 日期：2026-09-24 ｜ 对应规约：`docs/specs/企业级落地规约.md` **E-8**（判据 **C5 可追溯**）
>
> **本清单要回答四个问题**：哪些操作必须留痕、每条留痕长什么样、谁在写、以及**哪些没被覆盖**。
>
> E-8 的验收原话是：**"完成『登录 → 危险操作 → 停用文档』，审计页按时间序查出三条、导出 CSV 可用。"**
> 本文件里的每个动作码都与 `agt_python/app/services/governance_service.py` 的 `GovAction` 常量、
> `agt_backend/.../base/audit/AuditReporter` 的动作常量**逐字一致**——改名字要同时改三处（两处代码 + 本文件）。

---

## §1 什么算"要留痕的操作"

判据只有一条：**这件事发生了，事后需要有人能回答"谁、什么时候、对什么、成没成"。**

| 类别 | 为什么必须留痕 | 本系统覆盖情况 |
|---|---|---|
| **账号事件**（登录成功/失败、登出） | 失败尤其重要——撞库的痕迹只在这里 | ✅ E-8 |
| **危险写操作的确认门**（放行/拒绝） | 危险动作"用户到底点没点确认"是追责第一问 | ✅ E-8 |
| **文档治理动作**（入库/去重拦截/覆盖/停用/恢复/彻底删/回滚） | 改变的是**全体使用者可见的语料** | ✅ 治理域既有 |
| **巡检与工单**（开单/执行化/忽略） | 巡检判定带主观性，误判要能追溯依据 | ✅ 治理域既有 |
| **备份触发** | "有没有备份"和"谁触发的备份"是两件事 | ✅ E-8 |
| **配置变更** | 排障第一问常是"最近改过什么" | ✅ E-8（启动时比对指纹，见 §6.4） |
| **查询类操作**（对话、检索、看板） | ❌ **不审计**——它们不是"改变状态的动作"，归**日志/埋点**管（§8） | 故意不覆盖 |

## §2 统一维度契约

规约要求 `actor / action / target / result / ip / traceId / at` 七维。落库时的对应关系：

| 规约维度 | 实际列名 | 说明 |
|---|---|---|
| `actor` | `operator` | **历史命名**。改名会破坏既有查询与前端，故保留并在此声明等价 |
| `action` | `action` | 同名，取值见 §3 |
| `target` | `target` | 同名，E-8 新增列，写法见 §2.1 |
| `result` | `result` | 同名，`SUCCESS` / `FAILED` / `DENIED`（§2.2） |
| `ip` | `ip` | E-8 新增列 |
| `traceId` | `trace_id` | E-8 新增列（列名按库内既有 snake_case 习惯） |
| `at` | `ts` | **历史命名**，ISO 秒级字符串（字典序即时间序） |

另有治理域自有列：`doc_id` / `doc_name` / `version_no` / `detail`。`detail` 为 JSON 字符串，**只放"为什么"，不放内容**（§7）。

### §2.1 `target` 的写法（前缀约定）

`target` 是给**非文档类动作**用的统一指向——此前只有 `doc_id/doc_name`，登录、备份这类动作无处可放。

| 前缀 | 用途 | 示例 |
|---|---|---|
| `doc:` | 文档类动作 | `doc:kb_1712345_手册` |
| `tool:` | 工具确认门 | `tool:dispatch_task` |
| `user:` | 账号事件 | `user:admin` |
| `backup` | 数据备份（无前缀，全局唯一对象） | `backup` |
| `config:` | 配置变更 | `config:env` |
| `service:` | 服务级动作（预留） | `service:agt_python` |

**缺省规则**：治理域老调用点只传 `doc_id`，`log_audit` 会自动补成 `doc:<doc_id>`——
老调用点**不需要逐个改造**（改造 20 处调用点的风险远大于收益）。

**筛选语义**：按**前缀匹配**（`LIKE '<值>%'`），所以 `target=tool:` 能一次捞出所有工具确认，
`target=user:admin` 精确到一个人。

### §2.2 `result` 三值必须分开

| 值 | 含义 | 例子 |
|---|---|---|
| `SUCCESS` | 做成了 | 登录成功、备份完成、确认后执行成功 |
| `FAILED` | **做了但没成**（系统侧） | 上游不可达、备份时库读取失败、工具执行报错 |
| `DENIED` | **按规则不该做**（规则侧） | 角色不足、用户点了取消、登录态失效 |

⚠️ `FAILED` 与 `DENIED` 混成一个"失败"会让排查走偏——一个小权限问题看起来像一次系统故障。

## §3 动作码全表

### §3.1 账号事件（Java 侧产生，§6.2）

| 动作码 | 触发点 | `target` | `result` |
|---|---|---|---|
| `LOGIN_OK` | `AuthService.login` 成功签发本系统令牌后 | `user:<上游返回的用户名>` | `SUCCESS` |
| `LOGIN_FAIL` | `AuthService.login` 上游返回非 2000 **或抛异常** | `user:<入参用户名>` | `FAILED` |
| `LOGOUT` | `AuthService.logout` 本地会话删除后 | `user:<会话用户名>` | `SUCCESS` |

登录失败 `detail` 里放的是**失败原因文案**（如"用户名或密码错误"），**绝不含密码**。
`LOGIN_OK` 的 actor 取**上游返回的用户名**而非入参——两者不一致时（别名/大小写），审计要跟业务系统的事实一致。

登出未知令牌**不写审计**：没有会话就没有事实可记，写一条 `user:anonymous` 只是噪声。

### §3.2 危险写操作确认门（Python 侧产生，§6.3）

| 动作码 | 触发点 | `target` | `result` |
|---|---|---|---|
| `TOOL_CONFIRM_ALLOW` | 用户确认 → 执行（成功或失败都算放行） | `tool:<工具名>` | `SUCCESS` / `FAILED` |
| `TOOL_CONFIRM_DENY` | 用户明确取消 / 角色校验不过 / 登录态失效 | `tool:<工具名>` | `SUCCESS`（动作本身完成） |

`detail` 里带 `confirmed`（布尔）与 `reason`：

| `reason` | 含义 |
|---|---|
| `user_rejected` | 用户明确说"取消" |
| `role_denied` | 角色校验未通过（`detail.detail` 带原始提示） |
| `session_expired` | 确认时登录态已失效 |

⚠️ **工具参数不进审计**。参数可能含业务数据（任务内容、设备号），审计只留工具名与原因。
需要参数级追溯时走**日志**（`[trace]` 系列）——审计与日志的分工见 §8。

⚠️ 用户"改问别的导致待确认动作作废"**不写审计**：那是上下文切换，不是用户对确认门的裁决。
该事件仍有 `logger.info` 记录，可按会话排查。

### §3.3 备份触发（Python 侧产生，§6.5）

| 动作码 | 触发点 | `target` | `result` |
|---|---|---|---|
| `BACKUP_RUN` | `run_backup()` 每次调用（**定时任务与手工触发同一处置点**） | `backup` | `SUCCESS` / `FAILED` |

`detail`：`{ok, reusedExisting, backedUp: "4/4", dir, elapsedMs}`。

「复用当日已有备份」也写一条（`reusedExisting=true`）——它回答的是"**谁在什么时候尝试过备份**"，
与"今天有没有备份"是不同的问题。

### §3.4 配置变更（Python 侧产生，§6.4）

| 动作码 | 触发点 | `target` | `result` |
|---|---|---|---|
| `CONFIG_CHANGE` | 服务启动时比对配置指纹，发现变化 | `config:env` | `SUCCESS` |

`detail`：`{event, changed: {键: {from, to}}, added: [...], removed: [...], buildChanged, count, truncated, version, gitCommit}`。

### §3.5 文档治理与巡检（治理域既有，E-8 仅补维度）

`UPLOAD` · `DEDUP_INTERCEPT` · `VERSION_REPLACE` · `DISABLE` · `ENABLE` · `SOFT_DELETE` ·
`RESTORE` · `PURGE` · `TTL_PURGE` · `TICKET_OPEN` · `TICKET_CONFIRM` · `TICKET_DISMISS` ·
`BACKFILL` · `RECONCILE` · `ROLLBACK`

这些动作的 `target` 由 `doc_id` 自动派生为 `doc:<doc_id>`。

## §4 留痕落在哪

| 项 | 值 |
|---|---|
| 存储 | SQLite 表 `audit_log` |
| 文件 | `agt_python/data/governance/governance.db`（受 `DATA_ROOT` 控制） |
| 主键 | `id`（自增，**单调递增 ⇒ id 序即写入序**） |
| 索引 | `ts` / `action` / `doc_id` / `target` / `trace_id` |

**E-8 的升级方式**：`target` / `ip` / `trace_id` 三列用 `ALTER TABLE ADD COLUMN` 补，
**只加列不重建**（数据库规约 §2.6）。已存在的库靠 `_ensure_audit_columns()` 幂等补齐——
`CREATE TABLE IF NOT EXISTS` 对已存在的表**不会加列**，写错了的表现是"本地新库全绿、现场老库一查就报 no such column"。
老行新列为 `NULL`（不是空串），语义是"这条记录产生时还没有这个维度"。

**老行的 `target` 是读取期派生的**：E-8 之前的行 `target` 为 `NULL` 但有 `doc_id`，
语义上等价于 `doc:<doc_id>`。读取时用
`COALESCE(target, CASE WHEN doc_id IS NOT NULL AND doc_id <> '' THEN 'doc:' || doc_id END)`
（筛选与显示**用同一个表达式**）。

为什么不直接 `UPDATE` 回填：审计表"只增不改"是最硬的性质，回填的收益（少一个 COALESCE）
远小于风险（历史证据被改动且不可解释）。真机实测：475 行历史数据里，有 `doc_id` 的那些
现在也能被 `target=doc:` 筛到（439 条），且**库里仍是 `NULL`**。

## §5 谁在写（写点清单）

| # | 写点 | 代码位置 | 覆盖动作 |
|---|---|---|---|
| 1 | 治理服务门面 | `app/services/governance_service.py` → `audit()` | 全部治理动作（唯一入口） |
| 2 | 确认门 | `app/services/agent_service.py` → `_audit_confirm()` | `TOOL_CONFIRM_ALLOW/DENY` |
| 3 | 备份包装层 | `app/services/backup_service.py` → `run_backup()` / `_audit_backup()` | `BACKUP_RUN` |
| 4 | 配置留痕 | `app/services/config_audit.py` → `audit_config_change()` | `CONFIG_CHANGE` |
| 5 | Java 补录出口 | `cn.tedu.agt.base.audit.AuditReporter` → `GovernanceClient.auditEvent()` | `LOGIN_OK/FAIL/LOGOUT` |

**没有第六个写点。** 规约 E-8 明确要求"复用治理域既有 `audit()` 机制（**不新建第二套**）"，
所以 Java 侧的账号事件是**补录**进同一张表，不是再养一套存储。

三端调用链：

```
Vue(9090) ──► Java(8080) ──► Python(8000) ──► audit_log
                  │
                  └─ AuditReporter（登录/登出）──► POST /v1/kb/governance/audit
```

**审计写失败永不抛出**：Python 侧 `audit()` 吞异常只打 `[GOV-WARN]`，Java 侧 `AuditReporter.report()` 吞异常只打 WARN。
审计是"事后追责"能力，**不能反过来变成"登录失败"的原因**——一次 Python 抖动不该把所有人挡在门外。

## §6 各处怎么实现的（关键设计点）

### §6.1 `traceId` 自动取上下文

`sanitize` 不是调用方的负担：`governance_service.audit()` 在 `trace_id` 缺省时取当前请求上下文
（`app.core.trace.get_trace_id()`）。Java 侧由 `TracePropagationInterceptor` 把 `X-Trace-Id`
透传到 Python，Python 中间件采纳它 —— 所以**两侧的 traceId 是同一个值**。

验收动作：拿一个 traceId，一条命令同时捞到日志与审计：

```bash
grep <traceId> agt_python/data/logs/*.jsonl        # 日志
curl -s --noproxy '*' -H "X-Agent-Key: $KEY" \
  "http://127.0.0.1:8000/v1/kb/governance/audit?page=1&pageSize=5" | \
  python -c "import json,sys; [print(r['action'], r['target'], r['trace_id']) for r in json.load(sys.stdin)['data']['items'] if r['trace_id']=='<traceId>']"
```

### §6.2 Java 侧账号事件（为什么放 `base.audit` 包）

`AuthService` 要写审计，但审计表在 Python。做法是 `cn.tedu.agt.base.audit.AuditReporter`
持有 `GovernanceClient` 并**吞掉所有异常**。放在 `base` 而不是 `governance` 包下：
它是横切关注点（任何域都可能要补录），不是治理域的私有能力。

### §6.3 确认门：参数拼装只有一处

放行/拒绝两条分支各写一遍很容易漏掉 `target` 或 `operator`，所以收敛到 `_audit_confirm()` 一个函数。

### §6.4 配置变更：为什么只能在启动时观测

本系统**没有运行时改配置的入口**——Python 配置来自 `.env`，Java 来自 `application.properties`，
改动路径一律是"改文件 + 重启"。所以能观测到配置变化的唯一时刻就是**启动时**。

做法（`app/services/config_audit.py`）：

1. 对当前生效配置的**全部字段**算规范串（排序后 JSON）→ SHA-256 指纹；
2. 与上次快照（`data/ops/config_snapshot.json`）比对：
   - **首次运行**（无快照）→ 默认**不写审计**（"从无到有"信息量低还占一行），只建快照；
   - **指纹一致** → 什么都不做（重启是常态）；
   - **指纹不同** → 写 `CONFIG_CHANGE`，`detail` 里列出**变了哪些键、从什么变成什么**；
3. 快照更新。

**指纹不含 `buildTime`**：每次打包它都会变，算进去会让"重新构建"被记成"改配置"，
几次之后审计页就没人看了（告警疲劳）。指纹含 `version` 与 `gitCommit`——那是真正的可追溯信息。

### §6.5 备份：审计写在包装层

`run_backup()` 内部有三个 `return` 分支（复用当日已有 / 四个库都没备成 / 正常完成），
逐个加审计迟早会漏一个。所以把原实现降为 `_run_backup_impl()`，新增 `run_backup()` 包一层：
**每调用一次恰好一条**，时间戳与结果口径统一。

## §7 安全（三条硬约束）

### §7.1 不记内容，只记元数据

审计 `detail` 里**不出现**：工具参数、会话正文、用户输入原文、检索到的文档内容。
这与埋点铁律一致（元数据全量记、内容不落库）。

### §7.2 密钥永不进审计表

配置留痕会对**全部** `Settings` 字段取值，其中含 `AGENT_SHARED_KEY` / `LLM_API_KEY` 这类密钥。
判定按**键名**（含 `key` / `secret` / `password` / `token` / `credential` / `api_key` 即视为敏感），
敏感项只记 `sha256:<12 位前缀>`——足够判断"换没换"，不可反推原值。

⚠️ 保守偏置：`agent_router_intent_keywords` 名字里含 "key"，会被按敏感处理（值只存哈希）。
这是**有意的**：宁可少一份可读性，也不要"配置里新增一个 `xxx_token` 就悄悄明文落库"。
代价是这一项的变更只能看到"变了"，看不到具体值。

### §7.3 导出防公式注入

导出对象名/文档名是**用户可控**的。若以 `=` `+` `-` `@` 开头，Excel/WPS 打开会当公式求值（可外联取数）。
导出给的是**证据文件**，被"证据自己反咬一口"不可接受，故一律加 `'` 前缀；
纯数字的负值（如 `-5`）不算注入，不额外处理。

## §8 怎么用

### §8.1 前端：治理面板 →「审计流水」

按 动作 / 对象 / 操作人 / 文档 / 时间范围 组合筛选，分页浏览，展开看 `detail`、来源 IP 与 traceId。
另有「导出 CSV」按**当前筛选条件**导出全部匹配行。

### §8.2 直连接口（调试用）

```bash
# 按动作 + 对象类型查（Python 直连，需 X-Agent-Key）
curl -s --noproxy '*' -H "X-Agent-Key: $KEY" \
  "http://127.0.0.1:8000/v1/kb/governance/audit?action=LOGIN_FAIL&target=user:&page=1&pageSize=20"

# 导出 CSV（内容在 data.content）
curl -s --noproxy '*' -H "X-Agent-Key: $KEY" \
  "http://127.0.0.1:8000/v1/kb/governance/audit/export?from=2026-09-01%2000:00:00"
```

经 Java（前端实际走的路径）需管理员令牌：

```bash
# GET  /v1/kb/governance/audit
# GET  /v1/kb/governance/audit/export
# POST /v1/kb/governance/audit        ← 补录（服务间调用，供 Java 上报账号事件）
```

### §8.3 与日志/埋点的分工（别重复建设）

| 问题 | 去哪查 | 为什么 |
|---|---|---|
| 谁改了什么语料 / 谁登录过 / 备份跑没跑 | **审计**（本清单） | 状态变更，需长期留存（§9） |
| 一次请求为什么会失败 / 耗时卡在哪 | **日志**（`docs/日志规范.md`） | 过程细节，按 traceId 串，有轮转 |
| 今天有多少轮对话 / 降级几次 / 命中率 | **埋点与看板** | 统计口径，可聚合、可按天重算 |

三者都可能出现同一个 traceId，但**回答的不是同一个问题**——所以三套都留，不合并。

## §9 保留与权限

- **审计行永不删除**。这是它存在的意义：彻底删除文档后，审计是唯一的留痕
  （治理域连回收站都能清空，只有这张表不设 TTL）。
- **读取权限收在 Java 层**：审计查询与导出都要求**管理员**（`requireAdmin`），
  且判定发生在**调用 Python 之前**——越权请求不会变成一次真实的下游调用。
- Python 侧不加业务鉴权（与既有 kb 接口同一约定），仅要求服务间密钥 `X-Agent-Key`。

## §10 已知边界（如实记档）

| 边界 | 影响 | 现状 |
|---|---|---|
| **只有账号事件带 `ip`**，确认门/备份/配置变更的 `ip` 为空 | 这几类动作追不到"从哪台机器来的" | IP 只有 Java 侧（HTTP 入口）知道；Python 写的行拿不到。要补需在 Java→Python 的出站头上加一个 `X-Client-Ip`——**当前未做**（收件方是内网服务，IP 的追责价值低于账号事件） |
| **配置变更只知"变了"、不知"谁改的"** | `operator` 恒为 `system` | 配置在文件里改，无运行时入口 → 系统层面无法得知操作人。要回答"谁改的"只能靠版本库（`git log`） |
| **改配置的确切时刻不可知** | `ts` 是**发现时刻**（下次启动）而非修改时刻 | 同上 |
| **审计在 Python 不可达时会丢** | 那次动作没有留痕（日志里有 WARN） | 有意的取舍：宁可丢一条审计，也不能因审计不可用而拒绝登录（真机实测：停 8000 后登录仍 2000，仅一条 WARN） |
| **待确认动作"被改问作废"不写审计** | 该事件只在日志里 | 有意的：它不是用户对确认门的裁决（§3.2） |
| **8060 无人机主控自身的登录**不经过本审计 | 上游账号体系的动作看不到 | 账号体系在上游，本系统只是代理；**本系统视角**的登录已覆盖 |
| **前端 token 过期/被动失效**无审计 | 会话结束方式之一不可见 | 没有"动作"发生（用户没做什么），属会话生命周期而非操作 |
| **多实例部署**时 `user:` 不含租户维度 | 无法按租户切分 | 决策 D2 单机单租户，多租户不立项 |
| **JVM 侧的治理动作**（无） | — | Java 不直连 SQLite（规约 §13.4），所有治理动作都经 Python，故不会漏 |
