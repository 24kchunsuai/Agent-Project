# 统一响应体与状态码规范

## 一、统一响应体结构

Java 侧所有接口统一返回 `JsonResult`：

```json
{
  "code": 2000,
  "msg": "操作成功",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | 业务状态码，`2000` 为成功 |
| `msg` | string | 提示信息 |
| `data` | object | 业务数据，失败时通常为 null |

**设计要点**：HTTP 状态码统一返回 200，用**业务状态码**表达成功与失败。这样前端只需判断 `code`，不必同时处理 HTTP 层与业务层的两套错误语义。

## 二、状态码约定

| 码段 | 含义 | 具体码 |
|---|---|---|
| `2000` | 成功 | 通用成功 |
| `3000` 段 | 失败 | 通用业务失败 |
| | 智能体相关 | `3010` 智能体不可用、`3011` 智能体调用失败 |

**为什么用 2000/3000 而不是 200/500**：与 HTTP 状态码显式区分，避免混淆「网络层成功」与「业务层成功」。同时避免与 HTTP 语义耦合（例如 HTTP 200 也可能是业务失败）。

## 三、异常处理

- 业务异常统一抛 `ServiceException`，由全局异常处理器捕获并转换为标准响应体
- Python 侧对应 `ServiceException` → `3011`（调用失败），服务不可达 → `3010`
- 流式接口的异常通过 `error` 事件下发，不中断 HTTP 连接本身

## 四、前端统一处理

前端 axios 拦截器统一解包：

```javascript
// 响应拦截器核心逻辑
if (res.data.code === 2000) {
  return res.data.data   // 直接返回业务数据，调用方无需再判空
}
// 非 2000 则抛出错误，交由统一错误处理
```

**收益**：业务代码里不会出现散落的 `if (code === 2000)` 判断，错误处理集中在一处。

## 五、常见问题

**问：为什么不用 HTTP 状态码表达业务失败？**
答：因为 HTTP 状态码语义是「请求是否被正确接收与处理」，而业务失败（如参数校验不通过、下游不可用）在传输层其实是成功的请求。混用会导致代理、网关、监控等中间件误判。

**问：前端拿到的 data 为什么直接是业务对象？**
答：因为 axios 响应拦截器已经判断过 `code === 2000` 并解包，调用方拿到的就是 `data` 字段本身。
